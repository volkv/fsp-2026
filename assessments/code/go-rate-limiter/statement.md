API-шлюз ограничивает частоту запросов каждого клиента алгоритмом «ведро с токенами». Нужно воспроизвести решения шлюза по журналу запросов.

## Модель ведра

У каждого клиента своё ведро вместимостью `C` токенов, пополнение — один токен каждые `P` миллисекунд.

- Ведро создаётся полным в момент первого запроса клиента.
- Токены добавляются только целыми: если с момента отсчёта прошло `t` мс, добавляется `⌊t / P⌋` токенов, а остаток `t mod P` не пропадает — он идёт в зачёт следующего токена.
- В ведре не бывает больше `C` токенов. Пока ведро полное, время не копится: следующий токен начнёт «расти» с момента, когда ведро перестало быть полным.
- Запрос забирает один токен (`ALLOW`); если токенов нет — отклоняется (`DENY`) и ничего не меняет.

Пример при `C = 2`, `P = 100`: запросы в 0, 0, 0 → `ALLOW`, `ALLOW`, `DENY`, ведро опустело в момент 0. В 150 уже появился один токен, а 50 мс остатка идут в зачёт следующего → `ALLOW`. Следующий токен появляется ровно в 200, поэтому запрос в 250 → `ALLOW`, а второй запрос в 250 → `DENY`.

## Вход

```
C P
M
CLIENT C P      (M строк)
N
T CLIENT        (N строк)
```

- Первая строка — тариф по умолчанию.
- Затем `M` (0 ≤ M ≤ 10 000) персональных тарифов; каждый клиент упомянут не больше одного раза.
- Затем `N` (1 ≤ N ≤ 200 000) запросов в порядке неубывания времени `T` (0 ≤ T ≤ 10¹⁸); запросов с одинаковым временем может быть несколько, они обрабатываются по порядку.
- `1 ≤ C, P ≤ 10⁹`. Имя клиента — от 1 до 32 символов из латинских букв, цифр, `_` и `-`.

## Выход

`N` строк `ALLOW` или `DENY`, затем для каждого клиента, от которого был хотя бы один запрос, в лексикографическом порядке имён — строка `CLIENT ALLOWED DENIED`.

## Пример

Вход:

```
2 100
1
vip 5 10
8
0 alice
0 alice
0 alice
150 alice
200 alice
250 alice
250 vip
260 alice
```

Выход:

```
ALLOW
ALLOW
DENY
ALLOW
ALLOW
DENY
ALLOW
DENY
alice 4 3
vip 1 0
```

После трёх запросов в 0 ведро `alice` пустое, отсчёт идёт от 0. В 150 добавился токен (остаток 50 мс), в 200 — ещё один, в 250 и 260 токенов нет.
