# Демо-стенд

Стенд — https://fsp-career.volkv.com, сервер `ensi-new` (ssh-алиас), каталог `/root/fsp-career`. Сервер общий с другими
проектами: 4 CPU, 5,7 ГБ RAM. Стенд собран из [`docker-compose.prod.yml`](../docker-compose.prod.yml), выкатывается
[`scripts/deploy/deploy.sh`](../scripts/deploy/deploy.sh).

## Устройство

```
Интернет :443 → caddy (общий контейнер сервера, авто-TLS, сеть proxy)
                  ├── /realms/fsp, /realms/fsp/*  → fsp-career-fsp-mock:57610   (ФСП ID имитатора)
                  └── всё остальное              → fsp-career-app:3000
```

- В сети `proxy` только `app` и `fsp-mock` — их Caddy и достаёт; остальное — во внутренней сети `internal`, у `docparse` и
  `sandbox` — свои изолированные сети, где кроме них только шлюзы, у хранилища `storage` — своя сеть с `app` и `worker`
  (кроме S3 API процесс SeaweedFS отдаёт служебные API мастера, тома и filer без аутентификации), у моделей за туннелем —
  сеть `gpu` с `app`, `worker` и контейнером туннеля (раздел «Модели»). Все сети стенда внутренние (`internal: true`, выхода
  с сервера нет), кроме `egress`: в ней только те, кто ходит наружу, — `app` и `worker` (публичные профили Codeforces и
  GitHub, ленты вакансий, issuer ФСП ID по публичному адресу, Telegram) и `embedder` (файл модели с Hugging Face). Имитатор
  ходит наружу только вебхуками на публичный адрес приложения — через `proxy` и обратно через Caddy. Порты на хост не
  публикуются. `proxy` делят все проекты сервера, и там встречаются общие имена сервисов (`app`, `db`), поэтому все адреса в
  `docker-compose.prod.yml` — уникальные имена контейнеров `fsp-career-*`, а не имена сервисов. Инварианты сетей сверяет
  `src/worker/deployment.test.ts`.
- **Valkey** (BSD-3, совместим с Redis по протоколу; клиент и переменные `REDIS_*` прежние) — с паролем (`requirepass`, `REDIS_PASSWORD` из `.env.prod`); приложение и воркер получают его в `REDIS_URL`,
  проверка здоровья — через `REDISCLI_AUTH`. Процесс Valkey переписывает свой заголовок, пароль в списке процессов хоста не
  виден. Mailpit — без аутентификации, только в `internal`.
- Блок сайта — в `/root/caddy-gateway/Caddyfile` (не в этой репе). Правка: копия `Caddyfile.bak-<дата>`, затем
  `docker compose exec caddy caddy validate --config /etc/caddy/Caddyfile` и `… caddy reload …` в `/root/caddy-gateway`.
- **ФСП ID** — имитатор `fsp-mock` (доступа к настоящему нет). Его issuer — `https://fsp-career.volkv.com/realms/fsp`: одна
  строка и для браузера, и для приложения (приложение ходит к discovery и token endpoint тем же публичным адресом через
  Caddy). Путь `/realms` в приложении не занят. Из интернета через Caddy открыта только OIDC-часть имитатора; API
  достижений (`/v1`) и управляющие ручки (`/mock`) Caddy наружу не проксирует, приложение ходит к ним напрямую
  (`http://fsp-career-fsp-mock:57610`). Сетью они **не** закрыты: имитатор сидит и в общей сети `proxy`, поэтому
  `fsp-career-fsp-mock:57610` досягаем из любого контейнера других проектов сервера. Закрывают их токены, не сеть: в
  `/v1` данные спортсмена отдаются только с токеном ФСП ID (пользовательским или сервисным с подписанным утверждением,
  `FSP_ASSERTION_SECRET`), подписки вебхуков — только с сервисным токеном (`FSP_ID_CLIENT_SECRET`); справочники
  дисциплин и соревнований открыты без токена, как публичные данные (синтетика имитатора). `/mock` требует
  `FSP_MOCK_CONTROL_TOKEN`. Секреты генерирует `init-env.sh`. Вебхуки имитатор шлёт на публичный адрес приложения, как
  настоящая ФСП.
- **Адрес клиента.** Приложение берёт его из `X-Forwarded-For` (`ADDRESS_HEADER`), который Caddy заменяет адресом клиента.
  Запрос из интернета иначе, чем через Caddy, к приложению не попадает (портов на хосте нет), и без заголовка ручки с
  ограничением частоты (API, вебхуки, вход) отвечают ошибкой; исключение — `/api/health` для healthcheck контейнера.
  Остаточный риск: `fsp-career-app:3000` досягаем напрямую из общей сети `proxy`, и контейнер другого проекта сервера
  может прислать свой `X-Forwarded-For` — лимиты по адресу (вход, API, демо-сессии, ФСП ID) он обходит, подставляя
  разные адреса. Авторизацию это не обходит: сессии, ключи API, CSRF и подписи вебхуков от адреса не зависят, как и
  блокировка учётки при подборе пароля и лимиты по учётке (каталог, выгрузка данных). Здесь стенд доверяет соседям по
  серверу.
- **Эмбеддер** — свой сервис стенда `fsp-career-embedder` (llama.cpp на CPU, bge-m3; раздел «Эмбеддер»): семантический
  поиск включён без GPU. Пустые `EMBED_*` в `.env.prod` означают его; другой рантайм — `EMBED_BASE_URL`, `EMBED_MODEL` и
  `EMBED_SPACE_ID` вместе. **Разбор текста** (`extract`) — внешняя модель Claude Haiku через OpenAI-совместимый шлюз, с ключом
  в `.env.prod`; `rerank` и, вместо шлюза, `extract` могут прийти с машины с GPU через обратный туннель (раздел «Модели»). **Telegram** не настроен — без Telegram-уведомлений; включается заполнением переменных в `.env.prod` и
  перезапуском `app` и `worker`.

### Почта

SMTP-релея на сервере нет. Письма (подтверждение почты, сброс пароля, уведомления) уходят в Mailpit внутри стенда и
**наружу не доставляются**. Интерфейс Mailpit не опубликован; прочитать письма — через его API изнутри сети:

```sh
ssh ensi-new 'docker exec fsp-career-app node -e "fetch(\"http://fsp-career-mailpit:8025/api/v1/messages\").then(r => r.text()).then(console.log)"'
```

### Модели

Режимы, замеры и куда уходят данные — [`docs/models.md`](models.md), «Три режима».

**По умолчанию — внешняя модель по API.** Пустые `LLM_BASE_URL`, `LLM_RUNTIME` и `LLM_MODEL` в `.env.prod` означают
`https://llmgate.volkv.com/v1`, `api` и `claude-haiku:latest` (`docker-compose.prod.yml`). Ключ шлюза кладётся руками в
`LLM_API_KEY` в `/root/fsp-career/.env.prod` (раздел «Секреты»), затем `app` и `worker` перезапускаются; без ключа стенд работает
в режиме без модели, страница моделей показывает «Нет ключа API». В модель уходит текст резюме, потребностей и вакансий —
согласия и подписи на экранах это называют (`docs/models.md`, «Куда уходят данные»). Проверка через весь путь —
`scripts/deploy/deploy.sh models`: настоящий запрос из контейнера `app` (`extract: HTTP 200 in … ms`; `HTTP 401` — ключ не тот).

**Обязательные значения на стенде.** Пустые ключи берут значения по умолчанию, но стенд, созданный до внешней модели,
держит в `.env.prod` явные адреса туннеля — они перекрывают умолчания compose. Перед выкаткой `.env.prod` приводится к:

```sh
LLM_RUNTIME=api
LLM_BASE_URL=https://llmgate.volkv.com/v1
LLM_MODEL=claude-haiku:latest
LLM_API_KEY=<ключ шлюза>
EMBED_BASE_URL=                 # пусто — свой эмбеддер стенда http://fsp-career-embedder:8080/v1
RERANK_BASE_URL=                # пусто — без машины с GPU rerank не настроен
RERANK_MODEL=
RERANK_API_KEY=
```

Ключ шлюза не печатается и не попадает в историю шелла: строка дописывается на сервере из stdin
(`ssh ensi-new 'cd /root/fsp-career && umask 077 && … >> .env.prod'` с ключом во входном потоке), а проверяется по длине
значения, не по самому значению. Доступ к шлюзу с сервера: `ssh ensi-new 'curl -sS -o /dev/null -w "%{http_code}\n"
https://llmgate.volkv.com/healthz'` — `200`.

**Адреса — с путём версии.** `LLM_BASE_URL`, `EMBED_BASE_URL` и `RERANK_BASE_URL` — база OpenAI-совместимого API вместе с
`/v1`, как её публикует провайдер; адаптер добавляет `/chat/completions`, `/embeddings`, `/rerank`. Стенд, у которого в
`.env.prod` записан корень сервера (`http://fsp-career-gpu-tunnel:57810`), после выкатки этой версии получает `404` и путь без
модели — дописать `/v1`.

**Своя модель вместо внешней** (`LLM_RUNTIME=vllm`). `extract` и `rerank` работают на отдельной машине с GPU и приходят на стенд через обратный SSH-туннель: машина подключается к
sshd сервера ключом, которому разрешена только фиксированная команда `docker exec -i fsp-career-gpu-tunnel nc 127.0.0.1 2222`,
через неё — к sshd контейнера `fsp-career-gpu-tunnel` и пробрасывает туда свои порты 57810 и 57801; `app` и `worker` ходят к
ним по сети `gpu`. У контейнера нет опубликованных портов и других сетей. Устройство,
настройка машины и сервера, замеры и остаточные риски — [`docs/models.md`](models.md), «Модели вне стенда: обратный туннель».

- Машина выключена или туннель не поднят — порты в контейнере закрыты, операции сразу получают `unavailable`, продукт идёт по
  пути без модели (`docs/models.md`, «Без модели»). От туннеля ничего не зависит при старте стенда.
- **Не настроено:** автозапуск моделей и туннеля без входа человека (linger пользовательских служб),
  мониторинг туннеля и моделей, резервная машина с GPU. Модели и туннель работают в сессии человека на машине с GPU;
  выключенный ПК — стенд в режиме без модели.
- Живы ли модели через весь путь — `scripts/deploy/deploy.sh models` (настоящий запрос к каждой модели из контейнера `app`).
- Ключи туннеля — `/root/fsp-career/gpu-tunnel/` (раздел «Секреты»); строка ключа машины — в `/root/.ssh/authorized_keys`
  (`docs/models.md`).
- Перед показом без машины — выключить `extract` и `rerank` на странице моделей: иначе первые запросы ждут своего срока.
- Без машины `rerank` не настроен (пустой `RERANK_BASE_URL`): каталог и подборки ранжируются без уточняющей модели, поиск
  говорит об этом уведомлением упрощённого режима.

### Бюджет шлюза модели

У проекта `fsp-career` в шлюзе месячный кап — 30 USD (границы месяца — UTC); на 80 % шлюз шлёт уведомление в Telegram, на
100 % отвечает `429` на каждый запрос до начала следующего месяца. Тариф `claude-haiku:latest` (Claude Haiku 5.5) в шлюзе —
0,1 USD за миллион входных токенов и 0,5 USD за миллион выходных; размышление модели оплачивается как выход. Это в 20 раз
дешевле Claude Sonnet (2 и 10 USD), которым сделаны сохранённые разборы засева (ниже), и в 7,5 раза — прежней Gemini Flash
(0,75 и 3,75 USD).

**Расход по замерам (2026-10-08).** Счётчика токенов у стенда нет (шлюз их считает, стенд — нет). Живые вызовы Claude Haiku
через весь путь адаптера (`docs/models.md`, «Замеры внешней модели»): три коротких потребности — 2 924–3 068 входных и 327–1 070
выходных токенов, 0,0005–0,0008 USD за разбор. Схема ответа идёт в системном промпте (`docs/models.md`, «Три режима») и
прибавляет к каждому запросу ≈ 1 тыс. входных токенов. Цена вызова «не больше» — оценка сверху по размерам запроса и по самым
длинным ответам прежнего замера (`docs/models.md`, «Замеры внешней модели») по тарифу Haiku; резюме на Haiku не мерились:

| Вызов | Что его делает | Вход | Выход, максимум | Цена вызова, не больше |
|---|---|---|---|---|
| разбор потребности | текст «Опишите, кого ищете», вставленная вакансия | промпт и схема ≈ 3 тыс. токенов, текст — ≈ 3 тыс. | 2 274 | ≈ 0,002 USD |
| разбор резюме | своё резюме на `/demo/resume`, засев | промпт и схема ≈ 4 тыс. токенов плюс текст до нескольких страниц — до ≈ 10 тыс. (не измерено) | 4 127 | ≈ 0,003 USD |

- **Засев модель не вызывает.** Тексты героев и потребностей сценария от засева к засеву не меняются, поэтому засев
  (выкатка новой партии, ночной и ручной сброс) берёт ответ модели из `seeds/model-parses.json` и пишет его как разбор
  моделью (`processing_mode = model`, в конверте `model.origin = stored`), фон читают правила (`demo_seed_background`).
  Текст без сохранённого ответа (резюме героя или потребность изменили, вышла новая версия схемы или таксономии) засев
  читает правилами — «Без модели», причина `demo_seed_not_stored` — и пишет его ключ в строку журнала воркера
  `demo seed: no stored model parse`. До этого засев каждой ночи разбирал моделью резюме и потребности сценария: в ночь на
  2026-10-08 — 20 резюме и 2 потребности (на Claude Haiku — до ≈ 0,07 USD за ночь). Сохранённые разборы героев и
  потребностей сценария сделаны Claude Sonnet (`claude-sonnet:latest`; в каждой записи файла — модель, которую назвал ответ,
  `anthropic/claude-sonnet-5-5`): засев
  показывает их одинаковыми от ночи к ночи и не зависит от того, доступен ли шлюз.
- **Вызов модели при засеве — только явно:** `DEMO_SEED_MODEL=live` в `.env.prod` (по умолчанию `stored`). Тогда текст
  без сохранённого ответа разбирает модель, сохранённые ответы по-прежнему берутся из файла. Переменная партию не меняет:
  засеянный стенд от неё не пересевается — нужен ручной сброс (раздел «Демо-данные», «Вручную»).
- **Действия жюри — основной расход.** Судья за визит разбирает несколько потребностей, одну-две вставленные вакансии и, может быть,
  своё резюме: 5 потребностей, 1 вакансия и 1 резюме — ≈ 0,015 USD; десять судей по три визита — ≈ 0,5 USD.
- **Нагрузочный прогон** (`docs/submission/06-validation.md`, «Нагрузка и чистый запуск») — не больше 60 разборов
  потребности, ≈ 0,12 USD.
- **Прогон оценки разбора моделью** (`tools/eval`, 1 025 резюме) на Claude Haiku — не больше ≈ 3 USD.

Фактический расход месяца показывает шлюз (`/admin/usage`, за admin-токеном шлюза); стенд его не видит.

**Файл сохранённых разборов.** `seeds/model-parses.json` — ответы модели по ключу: схема операции (`schemaVersion`),
метка версии таксономии (`taxonomy`) и `inputSha256` — тот же, что `ml_results.input_sha256` разбора (у резюме — хэш блоков
документа после docparse, у потребности — хэш текста). В записи — модель, давшая ответ, и сам ответ с цитатами
(`ml_results.output`, `docs/domain.md`, 16.1). Файл — часть `seeds/`: его правка меняет партию и пересевает стенд при выкатке.
Ответ в файл попадает только с базы стенда, где модель уже разобрала текст, — командой `scripts/demo-model-parses.ts`
(вызовов модели она не делает):

```sh
# какие ключи засеянных героев и потребностей сценария файл не хранит (то же, что строка-предупреждение засева)
ssh ensi-new 'docker exec fsp-career-app node scripts/demo-model-parses.ts missing'
# ответы модели из базы стенда, добавленные к файлу образа, — в файл репозитория; затем коммит и выкатка
ssh ensi-new 'docker exec fsp-career-app node scripts/demo-model-parses.ts export -' > seeds/model-parses.json
```

Локально с базой из `.env` — `node --env-file=.env scripts/demo-model-parses.ts export` (дописывает
`seeds/model-parses.json` на месте) и `… missing`. Порядок, когда ответа нет: засев называет ключи → один засев с
`DEMO_SEED_MODEL=live` (сброс вручную) → `export` → коммит файла → `DEMO_SEED_MODEL=stored`. Ответ берётся только из
`ml_results.output`, а его пишет продукт начиная с миграции `0039_ml_results_output`: разборы, сделанные раньше, ответа
не хранят, и выгрузить их нельзя.

**Защита от перерасхода разборами текста.** Разбор потребности и вставленной вакансии — единственные разборы, которые
запускает посетитель, поэтому у них три ограничения стенда, кроме капа шлюза:

- **Сначала допуск.** Компания, которой оператор приостановил или отклонил действия, получает `403` до вызова модели:
  статус компании читается перед разбором, а не только при записи потребности или черновика.
- **Лимит на учётную запись** — 30 разборов в час (`RATE_LIMIT_RULES.textParse`, `src/lib/server/http/rate-limit.ts`):
  `POST /api/v1/needs`, `POST /api/v1/vacancies/drafts/from-text` и формы «Новая потребность» и «Вакансия из текста»
  делят один счётчик, ключ API считается отдельно. Сверх лимита API отвечает `429 rate_limited` с `Retry-After` и
  подписью «Лимит разборов текста — 30 в час на учётную запись…», форма показывает ту же подпись над полем текста. Один
  скрипт за час тратит не больше 30 × 0,011 ≈ 0,33 USD.
- **Повтор текста — без модели.** Ответ модели хранится в Valkey сутки по хешу текста (`ml_results.input_sha256`), версии
  таксономии и компании (`src/lib/server/vacancies/text-extract.ts`): тот же текст той же компании разбирается из
  хранимого ответа, запрос в шлюз не уходит; в `ml_results` пишется своя строка с режимом `model`. Отказ модели не
  хранится — следующий разбор зовёт её снова. Повтор считается в лимит на учётную запись: лимит — на запросы, не на вызовы
  модели.

**Кап исчерпан.** Шлюз отвечает `429`, адаптер модели считает его недоступностью рантайма (`rate_limited` в
`src/lib/server/ml/http.ts`, `RUNTIME_DOWN` в `src/lib/server/ml/adapter.ts`): после трёх отказов подряд автомат
отключения 30 секунд не зовёт модель, разбор идёт правилами без ожидания, у результата — метка «Без модели»; раз в 30 секунд
один запрос проверяет шлюз и при `429` автомат открывается снова. Это проверено на локальном стенде с подставным шлюзом:
`429` на три разбора подряд, четвёртый и пятый ушли в правила за 19–23 мс без запроса к шлюзу, после возврата шлюза
первый разбор моделью — через 30 секунд от последнего отказа. Ничего чинить на стенде не нужно, но до конца месяца:

1. На странице моделей выключить `extract`: экраны говорят «модель выключена настройкой» вместо недоступности, проверочные
   запросы к шлюзу прекращаются.
2. Если показ ждёт разбора моделью — поднять кап проекта в шлюзе (`project set-budget fsp-career <usd>` в контейнере шлюза)
   и включить `extract` обратно; стенд перезапускать не нужно.

Неверный или отозванный ключ (`401`) и выключенный в шлюзе проект (`403`) автомат не открывают: это не недоступность, а отказ
(`request_rejected`), — каждый разбор уходит в шлюз, получает отказ за десятки миллисекунд и идёт правилами с меткой
«Без модели». Проверка ключа — `scripts/deploy/deploy.sh models`.

### Песочница

Работает с теми же правами, что и локально (`docs/contracts.md`, раздел 6.3): `SYS_ADMIN`, `SETUID`, `SETGID`,
`SETFCAP`, свой seccomp, `apparmor=unconfined`, `cgroup: private`. Ядро сервера — cgroup v2 с делегированием `cpu`,
`memory`, `pids`. Остаточный риск из раздела 6.3 (уязвимость ядра или go-judge даёт выход на хост) на общем сервере
касается и соседних проектов; принят для демо-стенда. На стенде песочница исполняет **одну программу за раз**
(`-parallelism=1`, `SANDBOX_MAX_CONCURRENT_RUNS=1`) — второй одновременный прогон получает `busy`.
Поэтому воркер стенда берёт задания `test.run` по одному (`--concurrency=test.run=1` в команде `worker`, против 2 по
умолчанию у обработчика): иначе второй прогон получал бы `busy`, а после повтора оставался в `awaiting_sandbox` до
оператора. Совпадение сверяет `src/worker/deployment.test.ts`. Разбор резюме —
тоже по одному (`DOCPARSE_MAX_CONCURRENT=1`): одно значение (`x-docparse-slots` в `docker-compose.prod.yml`) задаёт
слоты сервиса `docparse` и число разборов, которые клиент одного процесса шлёт разом, остальные ждут слота в клиенте.
Ограничение в клиенте, а не `--concurrency` воркера: во время засева задания `resume.parse` засева разбирает его собственный
воркер внутри того же процесса (`demo-seed:*` в журнале, линия очереди `demo_seed`), — флаг воркера стенда его не держит. Отдельный процесс
(`main.js reset` через `docker exec`) — свой клиент со своим слотом: его разборы и разборы воркера могут встретиться, и
тогда второй получает `busy` и повторяется (три попытки с паузой 10 с).

## Бюджет памяти

У каждого сервиса лимит без свопа (`mem_limit` = `memswap_limit`):

| Сервис | Лимит, МБ | Замер без нагрузки, МБ |
|---|---:|---:|
| sandbox | 1024 | 23 |
| embedder | 896 | ≈ 670² |
| docparse | 768 | 113 |
| app | 640 | 101 |
| postgres | 640 | 90 |
| worker | 512 | 61 |
| fsp-mock | 256 | 163 |
| storage | 256 | ≈ 90¹ |
| redis | 128 | 52 |
| mailpit | 64 | 10 |
| docparse-gateway, sandbox-gateway | 32 + 32 | 5 |
| gpu-tunnel | 32 | ≈ 3³ |
| **Итого** | **5280** | **≈ 1435** |

Замер — сразу после первого запуска. ¹ Хранилище SeaweedFS заменило MinIO после замера; число — локальный
замер без нагрузки, под загрузкой 10-мегабайтных файлов подряд — до ≈ 100 МБ при `GOMEMLIMIT=192MiB`. ² Эмбеддер добавлен
после замера; число — локальный замер: модель (≈ 635 МБ) держится в памяти процесса всё время, пик на пачке входов по
512 токенов — 644 МиБ (`memory.peak` контейнера), лимит — с запасом ≈ 40 %. ³ Туннель добавлен после замера; число —
локальный замер с одной сессией. Вход длиннее 512 токенов рантайм не принимает: память внимания растёт с квадратом длины
(7000 токенов — 8,9 ГБ), поэтому тексты режутся до 800 символов.

Сумма лимитов (5,3 ГБ) почти равна всей памяти сервера (5,7 ГБ) и больше свободной (≈ 2,9 ГБ до выкатки; 2,4 ГБ
после неё, когда стек занимал ≈ 1,5 ГБ из 3,4 ГБ занятых на сервере): лимиты — потолки, а не резерв. Без
нагрузки засеянный стенд занимает ≈ 1,4 ГБ вместе с моделью эмбеддера (1392 МиБ в 13 контейнерах после пересева
2026-10-09: эмбеддер 350, воркер 337, PostgreSQL 289, приложение 92; чистый запуск без демо-данных локально 2026-10-08 —
0,74 ГБ); пик одного прогона кода (до 512 МБ программа или компилятор) и одного разбора резюме (до 640 МБ) — ещё ≈ 1,2 ГБ, итого ≈ 2,6 ГБ, что помещается впритык к ≈ 2,9 ГБ. Поэтому на стенде
песочница и `docparse` работают по одному заданию, а не по два, как локально. Засев демо-данных добавляет до ≈ 0,3 ГБ
PostgreSQL (подраздел «PostgreSQL»): засев вместе с прогоном кода и разбором резюме в свободные 2,4 ГБ уже не
помещается — засев идёт при выкатке новой партии и ночью, не во время показа (не проверено под такой общей нагрузкой).
Проверить:

```sh
ssh ensi-new 'free -m; docker stats --no-stream $(docker ps -q --filter name=fsp-career)'
```

### PostgreSQL

Настройки заданы явно (`command` сервиса `postgres` в `docker-compose.prod.yml`): `shared_buffers=128MB`, `work_mem=4MB`,
`maintenance_work_mem=64MB`, `autovacuum_work_mem=32MB`, `max_connections=40`, `shm_size: 128m`, лимит 640 МБ без свопа.

- **Почему 384 МБ не хватало.** Без свопа в лимит идут разделяемая память (`shared_buffers` и `/dev/shm`) и частная память
  бэкендов; кэш файлов ядро отдаёт само. демо-засев на стенде дважды упёрся в 384 МБ (анонимная память 162 МБ +
  разделяемая 147 МБ + кэш), ядро убило бэкенд, сервер перезапустил все бэкенды с восстановлением — и засев, и воркер
  упали (раздел «Обрыв соединения с базой»).
- **Соединения.** Пулы `app` и `worker` — по 10 (`src/lib/server/db/index.ts`), ручной `main.js reset` — ещё 10, ночной
  `pg_dump`, `psql` оператора и 3 слота суперпользователя: 40 с запасом вместо стоковых 100. Частная память бэкенда — единицы
  МБ плюс `work_mem` на каждую сортировку и хэш запроса; `autovacuum_work_mem` ограничивает три процесса автоочистки,
  которые во время засева работают почти постоянно.
- **`shm_size: 128m`** — параллельные планы держат данные в `/dev/shm`; стоковых 64 МБ Docker могло не хватить
  (`could not resize shared memory segment`), а выше лимита контейнера `/dev/shm` всё равно не вырастет.
- **Замер** (локально): тот же сервис из `docker-compose.prod.yml` с этими настройками и лимитом, засев
  3000 кандидатов × 1500 вакансий (`main.js seed`, пул 10 соединений, как у воркера стенда) — дошёл до конца за 14 мин
  06 с, без OOM (`memory.events`: `oom_kill 0`). Пик анонимной и разделяемой памяти — ≈ 405 МиБ (анонимная до 266,
  разделяемая до 139; выборка раз в 10 с), остальное до лимита занимает кэш файлов, который ядро вытесняет
  (`memory.peak` = лимит, `memory.events max 3458` — это давление на кэш, а не убийства). Запас над пиком — ≈ 235 МиБ.

### Воркер

Лимит 512 МБ без свопа. V8 в контейнере с таким лимитом сам ставит потолок кучи ≈ 259 МБ
(`v8.getHeapStatistics().heap_size_limit`), остальное — код, буферы драйвера PostgreSQL и сборки. Куча растёт к потолку
лениво, поэтому `docker stats` воркера после засева или массового пересчёта показывает 340–360 МБ и в простое: это занятый
V8 запас, а не удержанные данные; риск — упереться в потолок кучи (`JavaScript heap out of memory`), а не в лимит
контейнера.

- **Что ест память.** Самое тяжёлое задание — `match.refresh` вакансии: весь каталог (3000 кандидатов) в снимках
  соответствия, `matchScore` каждой пары дважды (до и после окна реранкера), факты видимости всех кандидатов; `concurrency`
  у типа — 2. Снимок кандидата берёт у выводов навыков только id фактов: вклад целиком (правило, утверждение, все
  множители) — ≈ 2,6 КБ на вывод, у демо-каталога ≈ 20 000 выводов, ≈ 52 МБ JSON на каждое задание вакансии.
- **Замер** (локально): образ приложения в контейнере с лимитом и `cpus` воркера стенда, только
  `match.refresh`, 1417 заданий вакансий после переиндексации векторов на демо-засеве 3000 × 1417. Со вкладами целиком —
  22 мин, `memory.peak` 378 МиБ, анонимная память до 309 МиБ; с id фактов — 15,5 мин, `memory.peak` 221 МиБ, анонимная
  до 205 МиБ; `oom_kill 0` в обоих. Результат пересчёта тот же: снимки всех 3000 кандидатов совпадают. Запас до лимита —
  ≈ 290 МиБ. Засев демо-данных внутри воркера (`demo.reset`, 1000 × 300, шесть банков) на стенде 2026-10-09 — пик
`memory.peak` 413 МиБ из 512, OOM нет (раздел «Демо-данные», «Объём и время»).

## Обрыв соединения с базой

Когда `fsp-career-postgres` перезапускается (бэкенд убит по лимиту памяти и сервер перезапускает все бэкенды с
восстановлением, рестарт контейнера, выкатка), соединения пулов `app` и `worker` рвутся. Пулы postgres.js открывают новые
соединения на следующем запросе; запрос, шедший в момент обрыва, получает `CONNECTION_CLOSED`, задание — неудачную попытку
и повтор по расписанию повторов, а пока база восстанавливается (секунды), захват заданий пишет в журнал
`job capture failed` и повторяет.

**Дефект postgres.js 3.4.9** (последняя версия на момент замеров): если обрыв застал транзакцию, библиотека пишет её
`ROLLBACK` в уже закрытый сокет из таймера — `TypeError: Cannot read properties of null (reading 'write')` в
`connection.js:255`. Это исключение вне любого обработчика кода, по умолчанию оно убивает процесс; так воркер стенда
падал во время демо-засева. Воркер ловит его на уровне процесса (`src/worker/main.ts`): пишет
`uncaught error, stopping the worker` с причиной, останавливается как по сигналу — перестаёт брать задания, даёт идущим
период ожидания (20 с), отдаёт оставшиеся аренды — и выходит с кодом 1; Docker поднимает его заново
(`restart: unless-stopped`). Задание, чья транзакция оборвалась, получает неудачную попытку и повтор сразу, а не ждёт
истечения аренды (у `demo.reset` — 30 минут). Сценарий проверяет `tests/integration/db-disconnect.test.ts`: настоящий
процесс воркера, `pg_terminate_backend` посреди транзакции записи результата.

Что остаётся:

- задание, чей исход не удалось записать, потому что база ещё восстанавливалась, остаётся под арендой до её истечения, и
  его возвращает восстановление аренд;
- процесс `app` падает на том же дефекте, если обрыв застанет транзакцию запроса, и Docker перезапускает его
  (при замерах так не случилось ни разу: у `app` 0 перезапусков);
- исправление самой библиотеки (не писать в закрытое соединение) — отдельная правка зависимости.

**Штатная остановка** (выкатка, `docker compose stop`): по SIGTERM воркер перестаёт брать задания, ждёт идущие 20 с, отдаёт
оставшиеся аренды без списания попытки и выходит — укладывается в `stop_grace_period: 30s`. На стенде: сигнал
в 11:56:49, аренда `demo.reset` отдана (`job lease given back on shutdown`, `outcome: queued`) в 11:57:09, воркер
остановлен в 11:57:14.

## Эмбеддер

Сервис `fsp-career-embedder` (`docker-compose.prod.yml`, как в `compose.yaml` — `docs/development.md`, «Эмбеддер»): образ
`ghcr.io/ggml-org/llama.cpp:server-b11176`, два потока на двух CPU, сеть `internal`, порт не публикуется.

**Доставка модели — первым стартом сервиса, а не шагом `deploy.sh`.** Файл bge-m3 Q8_0 (635 МБ) лежит в томе
`fsp-career_embedder-models`; сервис при старте проверяет его SHA-256, а если файла нет или хэш не тот — скачивает с
Hugging Face по закреплённому коммиту и проверяет снова (недокачанный файл лежит как `.part` и не загружается). Так одинаково
локально и на стенде, модель не едет через машину разработчика (`docker save` образа с моделью весил бы +0,6 ГБ на каждую
смену модели), нет одноразового init-контейнера, на котором падает `docker compose up --wait`, а `start_period` проверки
здоровья (10 минут) покрывает скачивание. Цена: сервису нужен выход в интернет — кроме `internal` он в сети `egress`, а не
только в изолированной, как `docparse` и песочница; в эмбеддер уходят только тексты уровня карточки каталога (навыки, роли,
годы, обобщённые результаты ФСП), без ФИО, компаний и текста резюме. Образ рантайма (0,8 ГБ) `deploy.sh` скачивает до
`up --wait` (`compose pull --policy missing embedder`), чтобы его загрузка не входила в ожидание.

Если Hugging Face с сервера недоступен (не проверено), файл кладётся в том руками — сервис примет его после сверки хэша:

```sh
scp bge-m3-q8_0.gguf ensi-new:/tmp/
ssh ensi-new 'docker run --rm -v fsp-career_embedder-models:/models -v /tmp/bge-m3-q8_0.gguf:/src:ro --entrypoint cp \
  ghcr.io/ggml-org/llama.cpp:server-b11176 /src /models/bge-m3-q8_0.gguf && rm /tmp/bge-m3-q8_0.gguf'
```

**Переключение поиска.** При старте `app` регистрирует пространство `EMBED_SPACE_ID` и ставит `embedding.reindex`; воркер
считает векторы всех профилей и вакансий и переключает поиск, до этого каталог ищет по словам (явный режим FTS). Оценка
для демо-объёма (3000 кандидатов, ≈ 6300 текстов секций, 1500 вакансий) на двух потоках — ≈ 30 минут (по замеру ≈ 5
текстов в секунду; на стенде не проверено). Ход — в логе воркера:

```sh
ssh ensi-new 'docker logs fsp-career-worker 2>&1 | grep "embedding reindex progress" | tail -1'
```

Ночной сброс демо-стенда оставляет пространство активным, но удаляет векторы кандидатов и вакансий; засев ставит
`profile.embed` только кандидатам с резюме и тестами, остальных досчитывает `embedding.reindex` при следующем старте `app`.

## Выкатка

С машины разработчика, из репозитория, на закоммиченный HEAD:

```sh
scripts/deploy/deploy.sh
```

Скрипт:

1. выгружает HEAD через `git archive` во временный каталог (незакоммиченные правки на стенд не попадают) и собирает пять
   образов с тегом — коротким хэшем коммита: `fsp-career-app` (он же воркер), `fsp-career-docparse`, `fsp-career-sandbox`,
   `fsp-career-fsp-mock`, `fsp-career-gpu-tunnel`;
2. доставляет образы `docker save | gzip | ssh docker load`; образ, который уже есть на сервере под другим тегом того же
   репозитория, только перетегируется — тяжёлые `sandbox` (≈ 1,3 ГБ) и `docparse` едут, только когда меняются. Образ
   узнаётся по sha256 от списка слоёв и конфигурации (`{{json .RootFS.Layers}}{{json .Config}}` у `docker image inspect`),
   не по id: сервер хранит образы в хранилище containerd, где id — дайджест манифеста, записанного `docker load`, а у
   машины с классическим хранилищем id — дайджест конфигурации, и по id совпадения не бывает никогда. Сборка на сервере не идёт:
   сборка приложения и образа песочницы съела бы память соседей, а git-доступ сервера к репозиторию не нужен;
3. кладёт файлы выкатки из HEAD — `docker-compose.prod.yml` и всё, что он монтирует (конфиги шлюзов, профиль seccomp), —
   в `/root/fsp-career/releases/<выкатка>/`, а `scripts/deploy/` и `.env.prod.example` — в `/root/fsp-career`; создаёт
   `.env.prod`, если его нет, или дописывает в него новые ключи шаблона; готовит ключи туннеля и останавливает выкатку, если
   нет публичного ключа машины с GPU (`init-env.sh`); проверяет, что на сервере есть файлы прошлой выкатки — той, что
   поднимет откат (нет — доставляет их из её коммита в локальном репозитории; коммита нет — останавливается до рестарта);
4. копирует файлы выкатки из `releases/<выкатка>/` в `/root/fsp-career`, записывает номер выкатки в `release.env` (прошлый —
   в `release.env.prev`), выполняет `docker compose up -d --wait` и проверяет `https://fsp-career.volkv.com/api/health`:
   ответ 200 с хэшем нового коммита;
5. при провале — сохраняет состояние сервисов и логи `app` и `worker` в `releases/<выкатка>-failed-<время UTC>.log`, до
   того как откат пересоздаст контейнеры, показывает конец файла и поднимает прошлую выкатку; при успехе — удаляет образы
   и файлы выкаток стенда, кроме текущей и той, что поднимет откат (раздел «Диск»), и сообщает, отвечают ли модели через
   туннель (`deploy.sh models`; на успех выкатки не влияет).

Выкатка, которая пересоздаёт туннель (`gpu-tunnel`), запускает `deploy.sh models` тут же после `docker compose up -d --wait`:
туннель ещё не успевает переподключиться, и первый запрос отвечает `ECONNREFUSED` — переподключение занимает ≈ 1 мин. Ложный
провал этого шага не влияет на успех выкатки (п. 5); повторить `deploy.sh models` через минуту либо оговорить это в скрипте.

**Панель качества стенда.** Запись строки `eval_runs`, которую показывает `/admin/quality`, не входит в `deploy.sh`: после
выкатки прогон повторяют той же командой с `--record` на `.env.prod` стенда (`tools/eval/REPORT.md`, «Панель качества»).
Локально уже записаны прогоны `01a0dba6…` (R, правила) и `01a0dbb4…` (M, модель); на стенде панель актуальна только после
их повтора там.

В `/root/fsp-career` всегда лежат `docker-compose.prod.yml` и конфиги той выкатки, что записана в `release.env`, поэтому
команды ниже работают и после отката. Ключи туннеля (`gpu-tunnel/`), `.env.prod` и тома общие для всех выкаток.

Миграции, таксономия, правовые документы и политики применяются при старте контейнера `app` (CMD образа), до запуска
сервера; упавшая миграция не даёт приложению стать healthy, и скрипт откатывает выкатку. Стартовую команду образа до
выкатки проверяет гейт: `pnpm check:image` запускает образ на пустой базе (`docs/development.md`, «Полный гейт»). Демо-данные засевает воркер
после старта (раздел «Демо-данные»).

**Банк заданий при старте.** `scripts/release-bank.ts` выпускает каждую специализацию отдельно (`docs/domain.md`, 10.5) и стартом
не управляет: отказ одной специализации не роняет `app`, выкатка проходит, специализация закрыта. В логе `app` на каждую специализацию
строка `Bank release <специализация>: released | unchanged | refused | unchecked`, ниже — дефекты и ожидаемые оценки; отказ из-за
исключения генератора — дефект `the check of the bank failed: …` или `the bank tree does not load: …`, провал ворот —
`family <ключ>: no passed gate run…` / `…is not for the current source…`. Если отказ снял выпуск в силе, следом строка
`release <id> withdrawn: …` — специализация закрыта до выкатки с исправным банком. Перед стартом сервера попытки, идущие на выпуске
с ушедшим кодом, аннулируются: в логе `[bank] release <id> is not the code of the bank tree (…): N attempts in progress annulled for
version_defect`. Проверить заранее, на машине разработчика, — `pnpm bank:check` (строка на специализацию в конце, код 1 при отказе).

Переменные скрипта: `DEPLOY_HOST` (по умолчанию `ensi-new`), `DEPLOY_DIR` (`/root/fsp-career`), `DEPLOY_ORIGIN`
(`https://fsp-career.volkv.com`).

Руками на сервере (то же, что делает скрипт):

```sh
cd /root/fsp-career
docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env ps
docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env logs --tail 100 app worker
```

`down -v` и удаление томов `fsp-career_*` уничтожают базу и файлы — ни скрипт, ни эта инструкция их не используют.

**Переход с Redis 8 на Valkey.** Valkey 9.1 не читает снимок Redis 8 (`Can't handle RDB format version 15`, `Fatal
error loading the DB`) — контейнер `fsp-career-redis` не стартует, и выкатка падает на ожидании здоровья. В томе — сессии
входа, счётчики лимитов, незавершённые входы через ФСП ID и кэши; задания и данные живут в PostgreSQL. Поэтому при
первой выкатке с Valkey том удаляется (все вошедшие выходят):

```sh
cd /root/fsp-career
C="docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env"
$C stop app worker redis && $C rm -f redis
docker volume rm fsp-career_redis-data
```

затем `scripts/deploy/deploy.sh` — compose создаст том заново. Откат на выкатку с Redis 8 поднимет Redis на томе, куда
уже писал Valkey; прочитает ли Redis 8 снимок Valkey — не проверено, при отказе старта том удаляется так же.

**Смена настроек сети** (например, `internal: true` у `internal` при первой выкатке с ней): compose пересоздаёт сеть сам —
останавливает подключённые контейнеры, удаляет сеть, создаёт заново и поднимает их (проверено локально на Docker Compose
5.5.1; версия compose на сервере не сверялась). Если compose вместо этого отказывает с сообщением о расхождении сети —
`docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env down` (без `-v`, тома остаются),
затем выкатка заново. Стенд на время пересоздания недоступен.

### Диск

Диск сервера общий с другими проектами и почти занят (при замере: 97 %, свободно 2,4 ГБ). Что держит стенд:

- **Образы выкаток.** На сервере остаются образы текущей выкатки и той, которую поднимет откат (`release.env.prev`); после
  успешной выкатки `deploy.sh` удаляет остальные теги репозиториев `fsp-career-app`, `fsp-career-docparse`,
  `fsp-career-sandbox`, `fsp-career-fsp-mock`, `fsp-career-gpu-tunnel` — только их. Образы других проектов и сторонние
  образы, от которых стенд зависит (`pgvector`, `redis`, `nginx`, `seaweedfs`, `mailpit`, `llama.cpp`), скрипт не трогает.
  Повторная выкатка того же коммита держит тот же образ отката, а не удаляет его. Размер одной выкатки: песочница 2,6 ГБ,
  `docparse` 1,2 ГБ, приложение 0,7 ГБ, имитатор 0,5 ГБ; неизменившийся образ только перетегируется и места не
  добавляет. Новые образы загружаются до удаления старых, поэтому выкатка со сменой песочницы или `docparse` требует
  свободного места под их новые слои.
- **Файлы выкаток** (`releases/<выкатка>/`, десятки килобайт) удаляются вместе с образами выкатки; логи провалившихся
  выкаток (`releases/*-failed-*.log`) остаются — удалять руками.
- **Кэш сборки** на сервере не копится: образы собираются на машине разработчика и приезжают через `docker load`
  (`docker system df`: Build Cache 0 B), поэтому `docker builder prune` скрипт не вызывает.
- **Том базы** — раздел «Демо-данные», объём.

Проверить перед выкаткой:

```sh
ssh ensi-new 'df -h /; docker system df; docker images | grep fsp-career'
```

## Откат

```sh
scripts/deploy/deploy.sh rollback
```

Поднимает выкатку из `release.env.prev`, а откатываемую записывает туда же — повторный `rollback` вернёт её. На сервере
хранятся образы и файлы текущей и прошлой выкатки.

Откат запускает прошлую выкатку с **её собственным** `docker-compose.prod.yml` и конфигами из `releases/<выкатка>/`: они
копируются в `/root/fsp-career` перед стартом. Переменные сервисов, список `--types` воркера, сервисы и сети — те, с которыми
выкатка вышла; сервис, которого у неё не было (например, туннель у выкатки до него), откат останавливает
(`--remove-orphans`). Выкатке, выпущенной до того, как файлы стали храниться на сервере, скрипт доставляет их из её коммита
в локальном репозитории (коммита нет — `git fetch`). Общие для выкаток `.env.prod`, ключи туннеля и строка ключа в
`authorized_keys` откатом не трогаются: у старой выкатки лишние ключи `.env.prod` просто не читаются.

Упавший откат сохраняет состояние и логи так же, как упавшая выкатка (`releases/<выкатка>-failed-<время>.log`), и
завершается с ошибкой; `release.env` при этом называет выкатку, которую не удалось поднять.

**Миграции не откатываются.** Прошлый образ запускается на схеме новой выкатки. Это работает, только пока новая выкатка
добавляла таблицы и необязательные столбцы. Замена уникального ограничения частичными уникальными индексами (миграции
`0019_external_identity_demo_session`, `0020_company_inn_demo_session`: уникальность вне демо-сессий и отдельно внутри каждой)
ломает старый код без всякой ошибки старта: его `ON CONFLICT (issuer, subject)` и `ON CONFLICT (inn) WHERE status <> 'rejected'` не
находят уникального индекса, условие которого покрывает их условие, и PostgreSQL отказывает каждому такому запросу (`there
is no unique or exclusion constraint matching the ON CONFLICT specification`) — привязка учётки ФСП ID и регистрация
компании падают. Удалённый или переименованный столбец,
новый `NOT NULL` без значения по умолчанию ломают старый код так же. Поэтому:

- откат на выкатку **до** такой миграции невозможен — схема не совпадёт с кодом, а «откатить» миграцию скрипт не умеет и не
  должен: `drizzle` хранит только прямые миграции;
- откат образа годится, пока между выкатками нет миграций, меняющих существующее (сверить: `git diff <прошлая>..<новая> --
  src/lib/server/db/migrations`);
- во всех остальных случаях путь — **починка вперёд**: исправление коммитом и новая выкатка. Восстановление базы из бэкапа
  (ниже) возвращает и схему, и данные на момент копии — это потеря данных, а не откат, и только по решению команды.

## Секреты

`/root/fsp-career/.env.prod`, режим 600, только на сервере. Создаёт его `scripts/deploy/init-env.sh` из
[`.env.prod.example`](../.env.prod.example): ключи шифрования полей, HMAC-секрет, ключ подписи квитанций, пароли
PostgreSQL, Valkey (`REDIS_PASSWORD`) и хранилища (`S3_SECRET_ACCESS_KEY`), секреты клиента ФСП ID, вебхуков, assertion,
управляющий токен имитатора и пароль начального администратора — `openssl rand`. Имеющиеся
строки существующего файла скрипт не меняет никогда: ключи шифрования, HMAC-секрет и ключ подписи привязаны к уже
записанным данным, их смена делает данные нечитаемыми, а квитанции — непроверяемыми. Ключи, которых в файле нет, а в
шаблоне появились, дописываются: секрет — сгенерированным, настройка — значением шаблона. В репозитории — только шаблон без
значений секретов.

Ключи туннеля к моделям — файлы в `/root/fsp-career/gpu-tunnel/` (каталог 700, файлы 600, владелец — uid 10022 учётки
контейнера): `ssh_host_ed25519_key` — ключ хоста sshd контейнера, `init-env.sh` создаёт его один раз и не меняет (машина с GPU
его закрепила; смена — заново закрепить на машине), `client_ed25519.pub` — публичный ключ машины, кладётся руками до
выкатки. Ключ шлюза внешней модели — в `LLM_API_KEY` `.env.prod`; со своей моделью вместо него — ключ vLLM машины, в
`LLM_API_KEY` и `RERANK_API_KEY`.

## Демо-данные

Стенд работает в демо-режиме (`DEMO_MODE=true` в `.env.prod`; устройство засева и сброса — `docs/development.md`,
«Демо-данные»; учётки — README, «Демо-учётки»):

- **Первый засев и новая партия.** Контейнер `app` при старте (CMD образа) проверяет, засеяна ли текущая партия
  демо-данных; если нет — ставит задание `demo.reset`, и воркер очищает стенд и засевает его заново. Сброс с засевом идёт на стенде ≈ 31 минуту
  (ниже), пулы вакансий досчитываются заданиями `match.refresh` меньше минуты после — дольше, чем выкатка ждёт готовности
  сервера, поэтому сервер стартует сразу, а данные появляются по ходу засева. Партия
  меняется вместе с файлами `seeds/`, кодом засева, выпущенными банками заданий, `DEMO_CANDIDATES`, `DEMO_VACANCIES` и
  `FSP_MOCK_*`: такая выкатка пересевает стенд и удаляет все демо-сессии. Партию меняет и новая версия правового документа с
  `requires_reconsent` (`legal/documents.json`, сейчас — показ в каталоге): она прекращает согласия засеянных кандидатов на
  прежнюю, и без пересева каталог и подборки остались бы пустыми.
- **Каждую ночь в 00:00 UTC** (03:00 МСК) воркер сбрасывает стенд и засевает заново (модель засев не вызывает —
  ответы на резюме героев и потребности сценария берутся из `seeds/model-parses.json`, раздел «Бюджет шлюза модели»):
  всё, что сделали на стенде за день, включая регистрации жюри, уходит; справочники, правовые тексты, политики и
  прогоны оценки качества остаются.
- **Выключить ночной сброс** — `DEMO_NIGHTLY_RESET=false` в `.env.prod` (по умолчанию `true`; применяется при следующей
  выкатке или `docker compose up -d` с новым `.env.prod`). Тогда воркер сброс не планирует, а ночь, поставленная в
  очередь заранее, при запуске перепроверяет флаг и ничего не сбрасывает — в журнале событие `demo.reset_skipped`.
  Демо-сессия не обрезается ночью: она живёт до своего срока или до простоя (`retention_policy`) — часовое задание
  `demo.purge` удаляет сессии, чей срок вышел, как и прежде. Данные вне демо-сессий копятся, пока стенд не очистят
  руками: командой из пункта «Вручную» — она возвращает стенд в засеянное состояние и сбрасывает все сессии входа.
  `/demo` при выключенном сбросе о нём не пишет. Засев новой партии при выкатке (первый пункт) от переменной не
  зависит. В журнале сброс помечен, что его запустило: `trigger` — `nightly`, `startup` (новая партия) или `manual`.
- **Экспертиза** (12–18.10 и до 24.10: жюри само регистрирует кандидатов и работодателей, проходит тесты и возвращается
  на следующий день) — `DEMO_REVIEW_MODE=true` и `DEMO_NIGHTLY_RESET=false` в `.env.prod`, затем
  `docker compose up -d`; без выключенного сброса приложение не стартует (`ConfigError`). Режим не меняет партию —
  стенд не пересевается. Сроки — из `retention_policy` (версия 4):

  | | обычный режим | экспертиза |
  |---|---|---|
  | простой, после которого сессия удаляется | `demo_idle_minutes` 480 (8 ч) | `demo_review_idle_hours` 168 (7 суток) |
  | предельный срок от открытия | `demo_session_hours` 24 | `demo_review_session_hours` 720 (30 суток) |
  | место заполненного стенда отдаёт сессия, молчащая | `demo_evictable_minutes` 20 | `demo_review_evictable_hours` 24 |
  | своё резюме | обрезает сессию до `demo_own_resume_hours` 24 от загрузки | живёт, пока живёт сессия |

  `/demo` показывает действующие сроки до входа и предупреждает, что после них сессия удаляется целиком. Во время
  экспертизы не выкатывайте изменения `seeds/`, засева и банков заданий и не запускайте ручной сброс: оба удаляют все
  сессии жюри. После экспертизы — `DEMO_REVIEW_MODE=false` и, если нужно, `DEMO_NIGHTLY_RESET=true`; живые сессии
  дальше удаляются по обычному простою, предельный срок им остаётся тот, что дан при открытии.
- **Вручную** (перед показом, репетицией, записью, а при выключенном ночном сбросе — для регулярной чистки):

  ```sh
  ssh ensi-new 'docker exec fsp-career-worker node build/demo/main.js reset'
  ```

  Команда ждёт конца засева и пишет в конце число записей партии; журнал воркера — `logs worker`.
- **Переменные** — `DEMO_MODE`, `DEMO_CANDIDATES`, `DEMO_VACANCIES`, `DEMO_NIGHTLY_RESET`, `DEMO_REVIEW_MODE`,
  `DEMO_SEED_MODEL` (раздел «Бюджет шлюза модели»), `FSP_MOCK_SEED`, `FSP_MOCK_ATHLETES`. `init-env.sh`
  дописывает недостающие ключи шаблона в существующий `.env.prod` при каждой выкатке, не трогая имеющиеся строки: стенд,
  созданный до демо-режима, получает его значения из шаблона. Строки, которых в шаблоне больше нет, скрипт не удаляет:
  оставшийся `DEMO_ACCOUNT_PASSWORD` ни на что не влияет, его можно стереть руками. Стенд, созданный до засева r3, держит
  `DEMO_CANDIDATES=3000` и `DEMO_VACANCIES=1500` явно: куча воркера (256 МБ) рассчитана на засев 1000 × 300, поэтому эти
  строки приводятся к значениям шаблона.
- **Пароля у учёток засева нет**: посетитель входит только через `/demo` в копию героя (README, «Демо-учётки»).

**Объём и время.** На стенде (воркер — 1 CPU и 512 МБ на сервере с 4 CPU) пересев r3.1 (2026-10-09, ревизия `94c99dc9`,
1000 кандидатов × 300 вакансий, выпущены шесть банков) шёл 30 мин 44 с (02:03:31–02:34:15 UTC): выборка достижимых исходов
тестов (`reach_ms`, ниже) — 15 мин 55 с на одном ядре, кандидаты ≈ 1,5 мин, опросы и тесты ≈ 6 мин, вакансии ≈ 4 мин,
потребности, подборки и предложения ≈ 3 мин; после конца засева воркер догоняет `match.refresh` вакансий меньше минуты.
Память после засева без нагрузки — весь стек ≈ 1392 МиБ в 13 контейнерах (эмбеддер 350, воркер 337, PostgreSQL 289,
приложение 92); пик воркера за засев — 413 МиБ из 512 (`memory.peak`), приложения — 329 МиБ (на старте); OOM нет. Прежние
замеры: засев 3000 кандидатов × ≈ 1500 вакансий — ≈ 48 мин и ещё ≈ 15 мин догона `match.refresh`; партия
`demo-fe0e9e2977c6` (3000 кандидатов, 1406 вакансий) — 27 мин 58 с без догона. Локально (отдельный PostgreSQL с настройками и
лимитом стенда, `main.js seed`, 3000 кандидатов × 1500 вакансий: 1544 с данными ФСП, ≈ 1450 с текстовым резюме, 1412–1417
вакансий, 24 компании) засев шёл 13 мин 01 с на HEAD `48765ca` (резюме героев — текст) и 11 мин 14 с — 11 мин 32 с с
резюме героев в PDF и DOCX (второе — с разбором героев моделью `extract`, 11–18 с на резюме, параллельно фоновым
кандидатам); прибавки нет, разница — в пределах разброса машины, которую делят другие процессы. Соответствий —

с резюме героев в PDF и DOCX не перемерялась; замеры — до сохранённых разборов, когда резюме героев разбирала модель).

прибавляется сброс, а по его окончании — векторы для семантического поиска (раздел «Эмбеддер»).

**Засев r3** (опрос, заявленный грейд и синтетические тесты, потребности, подборки, предложения, вызов, отклик и запрос
подтверждения; вызов — «Северного кода», К-1 отвечает на него на сцене, отклик — К-2). Локально, `main.js seed` с `DEMO_CANDIDATES=1000`, `DEMO_VACANCIES=300` (значения по умолчанию),
выпущены банки Backend и QA, процесс в cgroup с `MemoryMax=512M` без свопа и с `--max-old-space-size=256`, как воркер

### Что видно на стенде во время засева

Засев после выкатки новой партии, ночной и ручной начинается со сброса, поэтому ≈ 31 минуту стенд неполный, а пулы вакансий
досчитываются заданиями `match.refresh` меньше минуты после конца засева. Сервер отвечает всё это время (`/api/health` —
200), воркер здоров. По шагам журнала воркера (`demo seed: …`; время — по замеру на стенде):

1. **Сброс** (секунды): таблицы очищены, Valkey очищен — все сессии входа закрыты, вошедшие выходят на страницу входа.
2. **Учётки и компании** (≈ 16 мин после сброса: перед строкой журнала засев выбирает достижимые исходы тестов, `reach_ms`):
   учётки персонала и компании сценария есть, кандидатов и вакансий нет.
3. **Кандидаты** (≈ 1,5 мин): первыми создаются герои сценария — с этого момента `/demo` открывает демо-сессии; до этого
   она пишет «Демо-данные стенда ещё засеваются. Обновите страницу через несколько минут». Затем фоновые кандидаты —
   каталог растёт по ходу, факты ФСП, разбор резюме и категории у кандидатов появляются позже их учёток. Вакансий ещё
   нет: пулы и рекомендации пустые.
4. **Опросы и тесты** (≈ 6 мин): опросы, заявленные грейды, попытки тестов с решениями и категории по ним.
5. **Вакансии** (≈ 4 мин): вакансии компаний появляются по ходу, их соответствия — следом; пулы
   вакансий заканчивают считаться только после конца засева (выше), не к концу этого шага.
6. **Потребности, подборки и предложения** (≈ 3 мин): состояния сценария — приглашения, ответы, этапы найма, возражение,
   представитель несовершеннолетнего, партнёрские пулы, воронка оператора, рынок.

Демо-сессия, открытая до конца шага 6, копирует героя таким, каким он засеян к этому моменту: без приглашений, найма и
возражения сценария (по коду: `/demo` считает стенд готовым, как только есть учётки героев; на стенде не проверено) —
такую сессию открывают заново после засева. Конец засева — событие `demo.seeded` с числами партии в журнале действий и
строка `job finished` задания `demo.reset` в журнале воркера (строку `demo data seeded` пишет только ручная команда
`main.js`, воркер её не пишет):

```sh
ssh ensi-new 'docker logs fsp-career-worker 2>&1 | grep -E "demo seed:|\"job_type\":\"demo.reset\"" | tail -3'
ssh ensi-new "docker exec fsp-career-postgres psql -U fsp -d fsp -Atc \"select occurred_at, details from audit_events
  where action = 'demo.seeded' order by occurred_at desc limit 1\""
```

После засева каталог ищет по словам, пока воркер не досчитает векторы профилей и вакансий (раздел «Эмбеддер»).

## Начальный администратор

Настоящий администратор стенда — не демо-учётка: вход паролем на `/login`, следит за моделями и справочниками и назначает
персонал (устройство — `docs/development.md`, «Начальный администратор»). В `/root/fsp-career/.env.prod`:
`BOOTSTRAP_ADMIN_EMAIL` (шаблон — `admin@fsp-career.volkv.com`) и `BOOTSTRAP_ADMIN_PASSWORD` (генерирует
`scripts/deploy/init-env.sh`). Переменные получает только контейнер `app`. При каждом старте `node build/admin/main.js
ensure` создаёт учётку или подтверждает роль; пароль существующей не меняется. Пароль нужен только для создания учётки и
сброса, поэтому **после первого старта его убирают из окружения**: переносят в менеджер паролей, в `.env.prod` оставляют
`BOOTSTRAP_ADMIN_PASSWORD=` пустым и пересоздают `app` (`restart` окружение контейнера не меняет):

```sh
cd /root/fsp-career
docker logs fsp-career-app 2>&1 | grep 'bootstrap administrator ensured'   # учётка создана
sed -i 's/^BOOTSTRAP_ADMIN_PASSWORD=.*/BOOTSTRAP_ADMIN_PASSWORD=/' .env.prod
docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env up -d app
docker exec fsp-career-app printenv BOOTSTRAP_ADMIN_PASSWORD                # пусто
```

Дальше старты подтверждают роль по одному адресу. Задать пароль заново — передать его только в эту команду (ввод без эха,
не в историю шелла):

```sh
cd /root/fsp-career
read -rs BOOTSTRAP_ADMIN_PASSWORD
docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env exec \
  -e BOOTSTRAP_ADMIN_PASSWORD="$BOOTSTRAP_ADMIN_PASSWORD" app node build/admin/main.js ensure --reset-password
unset BOOTSTRAP_ADMIN_PASSWORD
```

Адрес занят учёткой засева или неподтверждённой регистрацией, пароль слабый, или учётки нет, а пароля в окружении нет
(база восстановлена без неё — вернуть пароль в `.env.prod` на один старт) — старт останавливается с именем переменной в
логе. Проверка: `docker logs fsp-career-app 2>&1 | grep 'bootstrap administrator'`, вход, «Администрирование →
Справочники» открывается. Ночной сброс учётку сохраняет, сессии и канал почты сбрасывает (канал возвращает
следующий старт).

## Бэкап и восстановление

Бэкап — общий механизм сервера `fleet-backup` (ежесуточно), задания в `/etc/fleet-backup/jobs.conf`:

- `pg fsp-career` — `pg_dump -Fc` базы `fsp` из `fsp-career-postgres` с проверкой оглавления, локально в
  `/var/backups/fleet/fsp-career/` (14 дней) и оффсайт;
- `rsync fsp-career-files` — зеркало тома хранилища (`/var/lib/docker/volumes/fsp-career_storage-data/_data`, файлы
  резюме и документы) оффсайт. До переноса с MinIO (ниже) задание смотрело на `fsp-career_minio-data` — путь в
  `/etc/fleet-backup/jobs.conf` меняется вместе с переносом.

Прогнать вне расписания: `ssh ensi-new fleet-backup --only fsp-career`. При первой выкатке строк `fsp-career` в
`jobs.conf` не оказалось и команда ничего не делала; вернулись ли они — не проверено: перед опорой на бэкап сверить
`grep fsp-career /etc/fleet-backup/jobs.conf`.

Восстановление (заменяет текущие данные — только осознанно). Дамп возвращает и учётки, удалённые после его снятия, а
реестр удалений `erasure_ledger` лежит в той же базе и откатывается вместе с ними (`docs/domain.md`, 19.2, случай 39).
Поэтому реестр **выгружается из живой базы до восстановления** и применяется к восстановленной до старта приложения:

```sh
cd /root/fsp-career
C="docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env"
umask 077
# 1. Реестр из живой базы — до всего остального (строки: user_id и моменты запроса и очистки, без данных людей).
$C exec -T worker node build/erasure/main.js export > erasure-ledger-$(date +%F-%H%M).jsonl
# 2. База и файлы из копии.
$C stop app worker
docker exec -i fsp-career-postgres pg_restore -U fsp -d fsp --clean --if-exists --no-owner \
  < /var/backups/fleet/fsp-career/latest.dump
#    файлы: $C stop storage, вернуть содержимое тома из оффсайт-зеркала, $C up -d --wait storage
# 3. Схема текущей выкатки, затем реестр — до того, как приложение начнёт отдавать восстановленные данные.
$C run --rm --no-deps -T worker node scripts/migrate.ts
$C run --rm --no-deps -T worker node build/erasure/main.js replay < erasure-ledger-<время>.jsonl
# 4. Старт.
$C up -d --wait
```

`replay` проходит каждую запись так, как шло удаление в первый раз, штатным кодом: учётка, которую вернул дамп, заново
начинает удаление от имени системы (причина `ledger_replay`: согласие на обработку истекает от системы, членства и
приглашения закрываются, пулы пересчитываются) и сразу очищается кодом `account.purge` — объекты хранилища, затем строки;
удаление в ожидании — очищается; клон демо-сессии уходит со всей сессией, как при `demo.purge`; надгробие и отсутствующая
учётка — ничего. В реестре остаётся момент запроса человека, не повтора. Учётку, которую удалить нельзя (действующая роль
персонала или последний владелец компании — в дампе они ещё были), команда не трогает: называет её в журнале (`erasure
ledger entry refused`, `user_id`, причина) и завершается с кодом 1 — решение за оператором (снять роль, передать владение),
затем тот же `replay` ещё раз: повтор того же файла ничего не меняет в уже применённом. Код —
`src/lib/server/erasure/replay/`, проверка — `tests/integration/erasure-replay.test.ts`.

Остаточный риск: если живой базы нет (потерян диск), реестр выгружать неоткуда — копии реестра новее дампа нигде нет, и
удаления после снятия дампа вернутся. На стенде команды восстановления с повтором реестра не прогонялись; `replay` проверен
тестом на копии базы, `export` — локально.

Восстановление дампа проверено в отдельную базу того же контейнера (все 108 таблиц). Дамп восстанавливается
только с тем `.env.prod`, с которым снят: зашифрованные поля и HMAC-поиск требуют тех же ключей.

## Перенос файлов с MinIO на SeaweedFS

Образы MinIO больше не публикуются, поэтому хранилище стенда — SeaweedFS (`storage`, том `fsp-career_storage-data`).
Стенд, выкатанный до этой смены, держит файлы в томе `fsp-career_minio-data` сервиса `minio`; объекты копируются по S3
из временного контейнера старого MinIO (его образ остался в локальном кэше сервера) в новое хранилище. Порядок:

1. **До выкатки** — переименовать ключи хранилища в `.env.prod` (значения те же; иначе compose не найдёт
   `S3_ACCESS_KEY_ID` и выкатка, и откат упадут):

   ```sh
   cd /root/fsp-career
   cp .env.prod .env.prod.bak-$(date +%F)
   sed -i 's/^MINIO_ROOT_USER=/S3_ACCESS_KEY_ID=/; s/^MINIO_ROOT_PASSWORD=/S3_SECRET_ACCESS_KEY=/' .env.prod
   ```

2. **Выкатка** — `scripts/deploy/deploy.sh`. `--remove-orphans` удаляет контейнер `fsp-career-minio`; том
   `fsp-career_minio-data` остаётся. Новый `storage` стартует с пустым бакетом: до шага 3 старые файлы не отдаются.
3. **Копирование** — на сервере, с остановленными `app` и `worker`:

   ```sh
   cd /root/fsp-career
   C="docker compose -f docker-compose.prod.yml --env-file .env.prod --env-file release.env"
   env_value() { sed -n "s/^$1=//p" .env.prod; }
   S3_ACCESS_KEY_ID=$(env_value S3_ACCESS_KEY_ID) S3_SECRET_ACCESS_KEY=$(env_value S3_SECRET_ACCESS_KEY)
   S3_BUCKET=$(env_value S3_BUCKET)
   docker image inspect quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z >/dev/null && docker pull rclone/rclone:1.75.1
   $C stop app worker
   docker run -d --name fsp-career-minio-old --network fsp-career_storage -v fsp-career_minio-data:/data \
     -e MINIO_ROOT_USER="$S3_ACCESS_KEY_ID" -e MINIO_ROOT_PASSWORD="$S3_SECRET_ACCESS_KEY" \
     quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z server /data
   sleep 5
   docker run --rm --network fsp-career_storage --entrypoint sh \
     -e RCLONE_CONFIG_OLD_TYPE=s3 -e RCLONE_CONFIG_OLD_PROVIDER=Minio \
     -e RCLONE_CONFIG_OLD_ENDPOINT=http://fsp-career-minio-old:9000 \
     -e RCLONE_CONFIG_OLD_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" -e RCLONE_CONFIG_OLD_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" \
     -e RCLONE_CONFIG_NEW_TYPE=s3 -e RCLONE_CONFIG_NEW_PROVIDER=SeaweedFS \
     -e RCLONE_CONFIG_NEW_ENDPOINT=http://fsp-career-storage:8333 \
     -e RCLONE_CONFIG_NEW_ACCESS_KEY_ID="$S3_ACCESS_KEY_ID" -e RCLONE_CONFIG_NEW_SECRET_ACCESS_KEY="$S3_SECRET_ACCESS_KEY" \
     rclone/rclone:1.75.1 -c "rclone copy --checksum --s3-no-check-bucket old:$S3_BUCKET new:$S3_BUCKET \
       && rclone check old:$S3_BUCKET new:$S3_BUCKET && rclone size old:$S3_BUCKET && rclone size new:$S3_BUCKET"
   docker rm -f fsp-career-minio-old
   $C up -d --wait
   ```

   `rclone check` сверяет каждый объект по размеру и хэшу и пишет `0 differences found`; число объектов двух `size`
   совпадает с `select count(*) from files where status <> 'deleted'`. Сеть `fsp-career_storage` внутренняя: выхода
   наружу у контейнеров нет, поэтому образ `rclone/rclone` скачивается заранее. Первая команда после `env_value`
   падает, если образа MinIO в кэше сервера нет (что он там есть — не проверено); тогда источник — зеркало тома из
   бэкапа, и перенос нужно продумать заново.
4. **Бэкап** — в `/etc/fleet-backup/jobs.conf` путь задания `fsp-career-files` сменить на
   `/var/lib/docker/volumes/fsp-career_storage-data/_data` и прогнать `fleet-backup --only fsp-career`.
5. Том `fsp-career_minio-data` удалить (`docker volume rm`), когда стенд проверен на скачивании старых файлов и свежий
   бэкап нового тома лёг оффсайт.

Команды шагов 1 и 3 проверены локально на копии: S3-источник с MinIO-совместимым API вместо кэшированного
образа MinIO (его на машине разработчика нет), SeaweedFS `4.47`, rclone `1.75.1` — пять объектов разных префиксов
скопированы, `0 differences found`, `Content-Type` сохранён.
