# Разработка

## Окружение

| Что | Версия | Где закреплено |
|---|---|---|
| Node | 24 (LTS) | `.nvmrc`, `engines` в `package.json` (`engine-strict` в `.npmrc`) |
| pnpm | 12.5.1 | `packageManager` в `package.json`; нужную версию подставляет corepack (`corepack enable`) |
| Docker | Compose v2 | `compose.yaml` |
| Имитатор ФСП `fsp-mock` | Node 24, свой lock | `services/fsp-mock/package.json` и `pnpm-lock.yaml`; зависимости ставит `pnpm install` корня (скрипт `prepare`) |
| Python (сервис `docparse`) | 3.13 | образ `services/docparse/Dockerfile`; зависимости — `services/docparse/uv.lock` (uv); на хосте Python не нужен |
| Python (стенд оценки качества `tools/eval`) | 3.13 | образ `tools/eval/Dockerfile` (с Node той же версии для моста); зависимости — `tools/eval/uv.lock` (uv) |
| Песочница `sandbox` | go-judge 1.12.3; Python 3.13, Node 24 (JavaScript, TypeScript), Go 1.27, g++ 14 (C++17), Java 21 | образ `services/sandbox/Dockerfile`; хосту нужен cgroup v2 |

Первый запуск для разработки:

```sh
corepack enable          # один раз: pnpm нужной версии по packageManager
pnpm install
make infra               # создаёт .env из .env.example и поднимает инфраструктуру
make db-migrate
make db-seed-taxonomy    # справочники: роли, навыки, грейды, правила проекции ФСП
pnpm db:seed-legal       # правовые документы из legal/ (без них регистрация недоступна)
pnpm db:seed-policies    # продуктовые политики из policies/ и источники вакансий (без политик приглашения недоступны)
pnpm db:release-bank     # выпуски банка заданий теста на грейд из assessments/families/
make dev                 # http://localhost:57173
```

`.env` не коммитится; шаблон со всеми переменными и комментариями — `.env.example`. Новые переменные шаблона в существующий
`.env` сами не попадают: после обновления сверить с шаблоном (приложение при первом чтении настроек, а `docker compose` сразу
падают с именем недостающей переменной, не печатая значений).

**Весь стенд с приложением** — `make up`: собирает образ приложения (коммит — из `git rev-parse`) и образы сервисов, поднимает
всё и ждёт, пока каждый сервис станет healthy (`--wait`); приложение — http://localhost:57300, состояние —
http://localhost:57300/api/health. Контейнер приложения при каждом старте применяет миграции (`scripts/migrate.ts`) и публикует
версию таксономии из `taxonomy/` (`scripts/seed-taxonomy.ts`), правовые документы из `legal/` (`scripts/seed-legal.ts`),
продуктовые политики из `policies/` и источники вакансий (`scripts/seed-policies.ts`), выпуски банка заданий теста на грейд
из `assessments/families/` (`scripts/release-bank.ts`), и только после успеха всех пяти шагов запускает сервер: шаги идемпотентны,
изменённые файлы таксономии под уже опубликованной меткой — отказ старта (метку нужно поднять), изменённый текст документа —
его новая версия, изменённые параметры опубликованной версии политики — отказ старта (изменение — новая версия в файле), новый
источник вакансий — выключенным, изменённое содержимое опубликованной версии задания — отказ старта (изменение — новая версия
в файлах), задание, пропавшее из банка, снимается с публикации. Итог шагов —
в `docker compose logs app`. Адреса сервисов у контейнера свои, внутренние (`compose.yaml`, сервис `app`), секреты — из `.env`;
пустой секрет останавливает `docker compose` с именем переменной. Воркер фоновых заданий (сервис `worker`, тот же образ)
стартует после того, как приложение стало healthy, то есть после миграций; его журнал — `docker compose logs worker`.
Остановить — `make down` (тома сохраняются).

**Полный гейт** перед коммитом в `main` — `make check-all` (`pnpm check:all`). Нужны Docker, `.env` и свободные порты
57432 и 57379: e2e поднимает PostgreSQL и Valkey из `compose.yaml` и оставляет их работать (`make down` — погасить).
Integration-тесты песочницы собирают её образ; первая сборка — несколько минут, дальше — из кэша. Шаги идут
последовательно и останавливаются на первом красном; упавший шаг перезапускается отдельно командой из таблицы.
Весь стенд (`make up`) гейт не поднимает, но образ приложения запускает (`pnpm check:image`): `docker build` доказывает
только сборку, а стартовая команда образа исполняет `scripts/*.ts` обычным Node из скопированных исходников — модуль, которого
нет в образе, или упавшая публикация видны лишь при старте. Сервисы, до которых старт не ходит (хранилище, почта, парсер,
песочница, ФСП), в этой проверке недоступны; их проверяет `make up` и `/api/health` вручную.

**Своя база e2e.** Тесты e2e не трогают базу из `.env`: `playwright.config.ts` берёт сервер из её `DATABASE_URL` и базу с
именем `E2E_DATABASE` (по умолчанию `fsp_e2e`; имя базы из `.env` — отказ) и отдаёт её как `DATABASE_URL` всем процессам
прогона — серверу, воркерам Playwright и тому, что они запускают. Первый шаг сервера e2e (`scripts/e2e-database.ts`)
пересоздаёт её пустой, дальше — миграции и публикации, как у контейнера приложения. Поэтому прогон не встречает строк и
выпусков таксономии, оставленных разработкой или другим прогоном; после прогона база остаётся для разбора и
пересоздаётся следующим. `demo.spec.ts` заводит рядом ещё и свою временную базу `e2e_demo_*` и удаляет её в конце. Valkey
тот же сервер из `.env`, но своя база на слот (`REDIS_URL` с `/1` или `/2`, `tests/e2e/helpers/ports.ts`): сессии, лимиты
частоты и переключатели моделей прогона не смешиваются с разработкой (база 0) и со вторым прогоном.

**Второй прогон рядом** (копия дерева, приёмка): свои `build/` и `.svelte-kit/` у копии и так свои; в её `.env` — своё
`E2E_DATABASE` и `E2E_PORT=57185`. Порты прогона — слот из трёх (`tests/e2e/helpers/ports.ts`, одна точка для
`playwright.config.ts` и спеков): сервер, подмена API Codeforces и GitHub, демо-стенд `demo.spec.ts` — 57175–57177 по
умолчанию, 57185–57187 во втором слоте. Других слотов нет: имитатор `fsp-mock` из `compose.yaml` общий для копий и
возвращает вход через ФСП ID только на колбэки обоих слотов (`FSP_MOCK_REDIRECT_URIS` — список, а не переменная: иначе
каждый `compose up` из другой копии пересоздавал бы общий имитатор под себя); другой `E2E_PORT` — отказ конфига. Общими
остаются серверы `make infra` (PostgreSQL, Valkey, хранилище, Mailpit, `fsp-mock`). Имя compose-проекта
(`name: fsp-career`) перекрывается `COMPOSE_PROJECT_NAME` из окружения или `.env`, но порты хоста в `compose.yaml` те же
57xxx: отдельный стек копии рядом с основным без смены портов не поднять.

## Соглашения

**Конфигурация и подключения.** `config()`, `db()` и `redis()` из `src/lib/server` — ленивые: окружение читается и
валидируется (Zod) при первом обращении, подключения создаются тогда же. Поэтому `vite build` не требует окружения и не
подключается к сервисам. Модульного кода с побочными эффектами (подключение, чтение `env` на верхнем уровне) нет.
Окружение читается только через `$env/dynamic/private` в `src/lib/server/config.ts`; у секретов нет значений по умолчанию,
сообщение об ошибке называет переменные, но не печатает значения. Новая переменная — в схему `config.ts` и в `.env.example`.

**База данных.** Таблицы Drizzle — в `src/lib/server/db/schema/` (реэкспорт из `index.ts`), миграции — в
`src/lib/server/db/migrations/`. Имена в базе — `snake_case` (`casing: 'snake_case'` у Drizzle и drizzle-kit), поля в
TypeScript — `camelCase`. Миграции генерирует `pnpm db:generate`, применяет `scripts/migrate.ts` (из `make db-migrate`
и при старте контейнера). Таксономию публикует `scripts/seed-taxonomy.ts` (из `make db-seed-taxonomy` и при старте
контейнера), правовые документы — `scripts/seed-legal.ts` (из `pnpm db:seed-legal`, при старте контейнера и сервера e2e);
опубликованная версия документа неизменяема, правка текста в `legal/` — новая версия. Продуктовые политики
(`policies/<kind>.json`: версии, `effective_from`, параметры и основание каждого — раздел модели или `product_default`) и строки
источников вакансий публикует `scripts/seed-policies.ts` (из `pnpm db:seed-policies`, при старте контейнера и сервера e2e),
выпуски банка заданий теста (`assessments/families/<специализация>/<семейство>/`: `descriptor.json` и `generator.ts`) —
`scripts/release-bank.ts` (из `pnpm db:release-bank`, при старте контейнера и сервера e2e). Отдельного `drizzle.config.ts`
нет: параметры drizzle-kit — в скрипте `db:generate`.

**Состояние сервиса.** `GET /api/health` отвечает `200` и `{"status":"ok", ...}` или `503` и `"degraded"`, с версией,
коммитом сборки и статусами `up`/`down` PostgreSQL и Valkey. Причины отказа пишутся только в лог сервера.

**Тесты.**
- unit — рядом с кодом, `*.test.ts`; зависимости подменяются `vi.mock`, в том числе `$env/dynamic/private`;
- integration — `tests/integration`; `global-setup.ts` поднимает PostgreSQL (pgvector) и Valkey в Testcontainers и
  передаёт адреса через `inject`, тест подменяет ими `$env/dynamic/private`;
- e2e — `tests/e2e`, Playwright против production-сборки;
- образы контейнеров для тестов — `tests/helpers/images.ts`, держать в соответствии с `compose.yaml`;
- у каждого теста есть проверка (`expect.requireAssertions`).

**Зависимости.** Скрипты сборки зависимостей отключены (`allowBuilds` в `pnpm-workspace.yaml`): новая зависимость
со скриптом установки остановит `pnpm install`, её нужно явно разрешить или запретить там же. pnpm не ставит версии,
опубликованные меньше суток назад (политика `minimumReleaseAge`).

## Сервис разбора файлов `docparse`

Контракт — [`contracts.md`](contracts.md), раздел 4; схема ответа — `contracts/docparse/v1.schema.json`, единственный
источник: тесты сервиса проверяют по ней каждый ответ, приложение валидирует ответы по ней же. Код — `services/docparse/`
(Python 3.13, Starlette и uvicorn).

**Как устроен.** `POST /v1/parse` запускает отдельный процесс разбора на каждый запрос. Процесс ограничивает себе
адресное пространство (`memory_exceeded` вместо падения контейнера), работает во временном каталоге запроса (удаляется
после ответа) и возглавляет свою группу процессов: LibreOffice и Tesseract живут в ней же, по таймауту группа убивается
целиком. Одновременно идут не больше двух разборов, третий получает `503 busy`.
`make infra` собирает образ `docparse` только если его нет; после правок в `services/docparse` —
`docker compose up -d --build --wait docparse docparse-gateway`. Лимиты по умолчанию — из контракта; каждый переопределяется переменной `DOCPARSE_<ИМЯ>` (список —
`services/docparse/src/docparse/limits.py`), тесты так проверяют лимиты на маленьких входах.

| Формат | Чем читается | `tables[]` |
|---|---|---|
| PDF | pdfplumber (слова с координатами) и XY-cut: колонки, блоки и порядок чтения восстанавливаются по геометрии, а не по порядку в потоке PDF | да — линованные и выровненные таблицы страницы |
| PDF-скан, PNG, JPEG | pdftoppm в PGM, затем Tesseract `rus+eng`; страница без текстового слоя уходит в OCR, и срок разбора растёт с 30 до 90 с | нет |
| DOCX | python-docx: тело по порядку, таблицы по ячейкам, текстовые рамки, колонтитулы | да — по ячейкам |
| RTF, DOC, ODT | LibreOffice headless → DOCX → как DOCX | да — как DOCX |
| TXT | UTF-8 и UTF-16 с BOM, UTF-8, cp1251, KOI8-R, cp866 | нет |

**Защиты.** Проверки архива и DTD, блокировку ссылок LibreOffice, лимит памяти и смещения держат тесты, которые краснеют без них.
- DOCX и ODT до разбора проверяются как архив: число записей, заявленный и фактический распакованный объём
  (zip-бомба → `unpacked_too_large`, ложный заголовок → `corrupt`). XML-части с `<!DOCTYPE`/`<!ENTITY` отвергаются
  (`corrupt`): так приходят XXE и «миллиард смешков», а python-docx молча обрезал бы текст;
- LibreOffice запускается с профилем `BlockUntrustedRefererLinks`: без него он загружает связанные картинки документа;
- у контейнера нет выхода наружу: сеть `docparse` в compose — `internal: true`, и в ней нет никого, кроме шлюза
  `docparse-gateway` (nginx). Приложение и хост ходят к сервису только через шлюз, сам `docparse` не видит ни базу,
  ни хранилище, ни приложение;
- контейнер: непривилегированный пользователь, файловая система только для чтения, `/tmp` — tmpfs, capabilities сброшены,
  `no-new-privileges`, память 768 МБ без свопа.

**Смещения.** `start`/`end` блоков — кодовые точки Unicode в тексте NFC. В TypeScript строки индексируются единицами
UTF-16, и символы вне BMP (эмодзи) сдвигают индексы: прямой `text.slice(start, end)` по смещениям `docparse` запрещён,
перевод — через общий хелпер «кодовые точки → UTF-16».

**Версия экстрактора** — `<версия из pyproject.toml>+<хэш>`; хэш считается при сборке образа по коду, `uv.lock` и версиям
LibreOffice, Tesseract и poppler. Любое изменение, способное поменять результат, меняет версию.

**Зависимости.** Python-пакеты закреплены в `uv.lock` с хэшами; после правки `pyproject.toml` — `make docparse-lock`.
Системные пакеты ставятся из снимка snapshot.debian.org на дату `DEBIAN_SNAPSHOT` в `Dockerfile`: сборка воспроизводима,
обновление пакетов (в том числе исправления безопасности LibreOffice) — сдвиг этой даты.

**Тесты** — `services/docparse/tests`, фикстуры `tests/fixtures` синтетические (вымышленные люди, телефоны
`+7 (900) 000-00-0x`, почта `@example.com`); враждебные документы (XXE, бомбы, внешние ссылки) собираются в тестах.
Гоняются в тестовом образе сервиса, собранном на тех же системных инструментах, что и боевой, с `--network none`.

## Оценка качества ML

Стенд — `tools/eval/` (Python 3.13 в своём образе), подробно — `tools/eval/README.md`. Он генерирует синтетические резюме
(PDF и DOCX пяти семейств шаблонов) с разметкой из исходного профиля, прогоняет по ним продукт, считает метрики разбора
резюме, нормализации навыков и ранжирования против разметки и базового варианта, сверяет с порогами
`tools/eval/thresholds.json`, зафиксированными до прогона, и пишет отчёт и, с `--record`, строку `eval_runs`, которую
показывает `/admin/quality`.

**Продукт измеряется его же кодом.** Python вызывает мост `src/eval/` (SSR-бандл Vite `.eval-build/main.js`, сборка —
`src/eval/bundle.config.ts`, как у воркера): один JSON-запрос в stdin, один ответ в stdout; команды `info`, `extract`
(`docparse` через клиент приложения → извлечение правилами или моделью → строки доказательств → снимок профиля),
`normalize`, `evidence` (опыт, выводы и уровни ФСП профиля), `rank` (ранжирование продукта — кандидаты под каждую вакансию — во временной базе рядом с базой
из `.env`: мигрируется из этого checkout, получает его таксономию и банк заданий, удаляется в конце команды при любом
исходе), `record` (строка проверяется схемами панели качества до вставки и после). Мост читает `.env`
(`node --env-file`), таксономию — из `taxonomy/` того же checkout. Образ стенда запускается с сетью хоста: `docparse` и
база — по адресам из `.env`.

**Выборка** — манифест `tools/eval/datasets/<id>/manifest.json` (сид, размер, дата отсчёта, хеш разметки); документы не
коммитятся, а рендерятся при каждом прогоне в `tools/eval/out/` (в `.gitignore`) байт в байт одинаково. Разбиение dev/holdout —
по профилям и по семействам шаблонов. Генератор, который не воспроизводит хеш манифеста, — отказ прогона: изменение
генератора — новый id выборки.

**Режимы.** `--mode rules_only` — извлечение правилами; `--mode model` — через адаптер моделей (`LLM_*`), документ без
ответа модели читается правилами, прогон пишет `processing_mode` (`model`, `rules_only`, `partial`). Режим `model` на живой
модели ещё не проверен.

**Грабли.** Мост собирается в `.eval-build/` — вне `build/`, чтобы `pnpm build` его не стирал. `tools/eval/out/` создаётся до
`docker run`, иначе каталог достаётся root. Мост, собранный из дерева с незакоммиченными правками, сообщает ревизию
`<коммит>-dirty`; прогон на holdout с ней отклоняется, `APP_COMMIT` для моста принимается только на чистом дереве или с
пометкой `-dirty`.

## Эмбеддер

Векторы профилей, вакансий и поисковых запросов (`docs/contracts.md`, раздел 3.3; `docs/domain.md`, раздел 16) считает
сервис `embedder` — llama.cpp server на CPU (официальный образ `ghcr.io/ggml-org/llama.cpp:server-b11176`) с моделью
bge-m3 в GGUF Q8_0: 1024 измерения, CLS-пулинг, без префиксов, векторы единичной длины. Поиск от GPU не зависит. В
`compose.yaml` приложение и воркер ходят к нему по `http://embedder:8080`, с хоста — `http://localhost:57820`.

**Модель** лежит в томе `embedder-models`. Первый старт скачивает файл с Hugging Face по закреплённому коммиту репозитория
`ggml-org/bge-m3-Q8_0-GGUF` (635 МБ, локально ≈ 15 с вместе с загрузкой модели), каждый старт сверяет SHA-256 файла
(`MODEL_SHA256` сервиса): недокачанный или изменённый файл не загружается, а скачивается заново. Одноразового
init-контейнера нет — `docker compose up --wait` на нём падает; healthcheck (`/health` отвечает 200 после загрузки
модели) ждёт до 10 минут. Повторный старт — ≈ 6 с.

**Лимиты.** Вход — не больше 512 токенов (`--ubatch-size 512`): длиннее рантайм отвечает ошибкой сервера, а память
внимания растёт с квадратом длины (замер: вход 1650 токенов — 2,7 ГБ, 3300 — 4,8 ГБ, 7000 — 8,9 ГБ). Поэтому тексты
режутся до 800 символов (`MAX_INPUT_CHARS`, `src/lib/server/embeddings/text.ts`): список коротких технических названий —
≈ 1,7 символа на токен, список навыков — 2,5, русская проза — 3,8. Пик памяти на пачке входов по 512 токенов — 644 МиБ
вместе с моделью; лимит сервиса — 896 МБ. Один слот (`--parallel 1`), четыре потока локально, два на стенде.

**Пространство** описано в коде: `src/lib/server/embeddings/definitions.ts` (`BGE_M3_Q8`), идентификатор собирается из
модели, SHA-256 файла, префиксов, пулинга, нормализации, размерности, лимита входа и версии текстов секций:
`bge-m3@aa473d51f451/q:none/d:none/cls/l2/1024/t512/sections-v1`. `compose.yaml` задаёт `EMBED_BASE_URL`, `EMBED_MODEL`,
`EMBED_SPACE_ID` приложению и воркеру сам; `src/worker/deployment.test.ts` сверяет образ, SHA-256, пулинг и лимит входа
сервиса и `EMBED_*` обоих compose-файлов с определением. Другая модель, другой файл, другой способ резать тексты — новое
определение с новым идентификатором, не правка старого.

**Засев и переключение.** При каждом старте контейнер приложения выполняет `node build/embeddings/main.js ensure`
(`src/lib/server/embeddings/space.ts`): регистрирует строку `embedding_spaces` по определению `EMBED_SPACE_ID` (статус
`building`) и ставит `embedding.reindex`, если его ещё нет в очереди. Неизвестный идентификатор, `EMBED_MODEL` не той модели
или зарегистрированная строка, отличная от определения, — отказ старта. Задание `embedding.reindex`
(`src/lib/server/embeddings/reindex.ts`) считает векторы всех профилей и открытых вакансий страницами по
`4 × EMBED_BATCH_SIZE`, каждая страница — своей транзакцией с проверкой ревизии; прогресс — строки лога
`embedding reindex progress`. Когда всё посчитано, одной транзакцией: пространство `active`,
`search_settings.active_embedding_space_id` указывает на него, прежнее активное — `retired`, его векторы удаляются, каждой
вакансии с вектором ставится `match.refresh`. До этого поиск работает в явном режиме FTS (`semanticReason`
`no_active_space`). Прерванный пересчёт продолжается с места: посчитанное и не изменившееся пропускается без вызова
модели. Для уже активного пространства задание только досчитывает недостающее (после сброса демо-стенда, восстановления).

**Векторы профиля** — задание `profile.embed` (`src/lib/server/candidates/embed-job.ts`), его ставит каждая смена
доказательств резюме и тестов (`recordEvidenceChange`) с новой `profile_revision`. Три секции (`skills`, `experience`,
`summary`) из того, что показывает карточка каталога: навыки по числу упоминаний, группы опыта (роль, годы, применённые
навыки), желаемые роли, результаты ФСП в обобщённом виде (дисциплина, уровень соревнования, у совершеннолетних — группа
результата и формат). Названий компаний, должностей как написаны, заголовка и текста резюме в тексте нет. Секция с тем же
текстом не считается заново — её вектор переходит на новую ревизию. Пишется в настроенное пространство, пока оно
`building` или `active`; результат условный — ревизия сдвинулась, пока модель считала, — `discarded_stale`.

**Разработка на хосте.** `pnpm dev` и `make worker` ходят к эмбеддеру по адресам из `.env`: `EMBED_BASE_URL=http://localhost:57820`,
`EMBED_MODEL=bge-m3`, `EMBED_SPACE_ID` — идентификатор выше, затем `pnpm db:seed-embedding-space` и воркер с типами
`embedding.reindex,profile.embed,vacancy.embed`. Пустой `EMBED_BASE_URL` — поиск только по словам.

**Замеры** (локально, 4 потока): 300 демо-кандидатов (630 текстов секций) и 99 вакансий — 95 с, ≈ 8 текстов в
секунду; на двух потоках — ≈ 5 текстов в секунду, запрос, который ждёт за пачкой из 8 текстов, — ≈ 1,2 с (за пачкой из
32 — 5,5 с, дольше `EMBED_INTERACTIVE_TIMEOUT_MS`, поэтому `EMBED_BATCH_SIZE=8`). Точный поиск по 3000 кандидатам
(6000 векторов по 1024) — 20–22 мс в PostgreSQL; поиск каталога в режиме `hybrid` целиком на демо-засеве 3000 кандидатов
(эмбеддер ограничен 2 CPU, без реранкера) — p50 0,49–0,58 с по словам (из них документы и ранг FTS ≈ 0,4 с, эмбеддинг
запроса ≈ 20 мс, векторы ≈ 30 мс), 0,32–0,34 с по вакансии, 0,08 с без запроса; p95 до 0,84 с.
Индекс HNSW не нужен на этом объёме (`docs/domain.md`, 16.3). Оценка пула черновика вакансии до сохранения
(`estimateVacancyPool`) по тем же 3000 кандидатам — 0,20–0,24 с.

**Тесты** — `tests/integration/profile-embed.test.ts` (что попадает в тексты, условная запись, перенос секций без модели,
режимы отказа) и `tests/integration/embedding-reindex.test.ts` (регистрация, пересчёт со сбоем и продолжением,
переключение, досчёт активного, и живой прогон против сервиса `embedder` из `compose.yaml`: тот же скрипт старта, та же
модель; файл модели кэшируется в `node_modules/.cache/embedder-models`, первый прогон качает 635 МБ).

## Демо-данные

Демо-стенд и показ жюри идут на засеянных данных (`docs/domain.md`, разделы 7.1, 12.5, 19.2, 21): учётки всех ролей,
компании сценария и фона, синтетические кандидаты на реальных соревнованиях ФСП из мира имитатора, собственные и внешние
вакансии, приглашения, найм, возражение, представители несовершеннолетних. Код — `src/lib/server/demo/`, данные —
`seeds/` (учётки и герои `demo.json`, компании и организации `companies.json`, профили ролей и зарплатные коридоры
`roles.json`, коды регионов `regions.json`, резюме героев `resumes/` — PDF и DOCX; генерирует `pnpm demo:resumes` скриптом
`scripts/demo-resumes.py` внутри образа `docparse`, выход побайтово воспроизводим). Команда — `node build/demo/main.js <seed|reset|ensure>`,
SSR-бандл Vite, как у воркера (`src/lib/server/demo/bundle.config.ts`): засеву нужны модули с `$lib`, поэтому это не
`scripts/*.ts`.

**Только в демо-режиме.** Засев и сброс переписывают всю базу и без `DEMO_MODE=true` отказывают до первого запроса. Демо-режим
требует имитатор (`FSP_ACHIEVEMENTS_ADAPTER=mock`), его управляющий токен `FSP_MOCK_CONTROL_TOKEN` и набор данных имитатора
`FSP_MOCK_SEED` и `FSP_MOCK_ATHLETES` — засев генерирует тот же набор, чтобы
выбрать спортсменов, и сверяет его с запущенным имитатором (другой набор — отказ с именами переменных). Объём —
`DEMO_CANDIDATES` и `DEMO_VACANCIES` (по умолчанию 3000 и 1500). Локально:

```sh
make infra && make db-migrate && make db-seed-taxonomy && pnpm db:seed-legal && pnpm db:seed-policies && pnpm db:release-bank
DEMO_MODE=true pnpm db:seed-demo     # или DEMO_MODE=true в .env
```

**Путь данных — через продукт.** Учётки, анкеты и регистрационные строки пишутся как при регистрации; дальше засев действует
от имени людей функциями модулей: согласие на обработку, условия работы, согласие на каталог, подтверждение импорта ФСП,
загрузка резюме, квиз платформы, черновик и публикация вакансии, проверка компании оператором, приглашение, ответ, этапы и
исходы найма, возражение, представитель. Факты, утверждения, категории, соответствия, пулы, рынок — результаты заданий
(`fsp.sync` к запущенному имитатору, `resume.parse` → `resume.extract`, `evidence.compute`, `match.refresh`,
`vacancy.normalize`, `market.refresh`), которые засев выполняет встроенным воркером до пустой очереди этих типов; упавшее
задание — отказ засева. Внешние вакансии приходят заданием `vacancies.import` из двух синтетических источников
(`demo_board`, `demo_portal`, подпись «Демо-данные»), которые засев включает только на время своего импорта. Резюме героев
разбирает штатный адаптер модели: при недоступной или выключенной модели — правила, с причиной в результате. Фоновые резюме
засев читает правилами (причина `demo_seed_background`). Соответствия считаются без семантики и реранкера. Прямыми
строками пишутся только входы без экрана в продукте: ФИО кандидата, GitHub-профиль, принятие условий работы с
несовершеннолетними, подпись представителя и согласие на пул партнёра.

Засев недетерминирован: между прогонами на тех же входах расходятся числа фактов и соответствий (замер: факты 8101 и 8228,
соответствия 190 650 и 209 943). На стенде воркер параллельно с засевом разбирает моделью фоновые `resume.extract` — это
входит во время засева.

**Партия.** `seed_batch_id` — хэш входов засева (файлы `seeds/`, набор имитатора, объём, версия засева) — несут учётки,
кандидаты, компании, вакансии и публикации вакансий; по ним витрина подписывает синтетику. Законченная партия — событие
журнала `demo.seeded`: повторный засев ничего не делает. Прерванный засев продолжается с места остановки: каждый шаг находит
сделанное по естественным ключам (адрес, ИНН, порядок вакансий компании, тройка приглашения). Данные другой партии —
отказ с просьбой сбросить стенд.

**Сброс** (`docs/domain.md`, 19.2, контрпример 46) очищает все таблицы схемы, кроме справочников: таксономии, правовых
текстов, политик, наборов правил, банка заданий, источников вакансий, пространств векторов и прогонов оценки качества, — и
настоящего персонала стенда (учётки вне засева и демо-сессий с ролью персонала, их пароли и роли; см. «Начальный
администратор»).
Решение о каждой таблице — в `DEMO_RESET_PLAN` (`src/lib/server/demo/reset.ts`); таблица без решения останавливает сброс, а
тест `tests/integration/demo-reset.test.ts` сверяет план со списком таблиц схемы после миграций — новая таблица без решения
его роняет. Сброс идёт одной транзакцией (`TRUNCATE` и построчное удаление там, где справочник ссылается на очищаемую таблицу;
триггеры append-only на время транзакции выключены), затем удаляет объекты файлов из хранилища, очищает Valkey (`FLUSHDB`:
сессии, счётчики, кеши) и сбрасывает имитатор (`POST /mock/reset`). Остаются строки заданий `demo.reset` и векторы навыков.

**Задание `demo.reset`** — сброс и засев в воркере: ночью в 00:00 UTC (планировщик ставит задание наступающей ночи только в
демо-режиме) и при старте контейнера приложения, если засеянная партия не текущая (`main.js ensure` в CMD образа: засев
идёт минуты, дольше, чем выкатка ждёт готовности сервера).

**Время засева.** Люди стенда «присоединились» за 45 минут до засева, но не раньше публикации принятых ими юридических
текстов (`SeedContext.joinedAt`): от этого момента датируются учётки, принятие соглашения и согласие на обработку, а квиз —
позже согласия и до засева (на свежей базе тестов паузы ужимаются в оставшееся время).

**Демо-сессии и учётки засева** (`docs/domain.md`, 19.3). Посетитель входит только через `/demo`: в учётки засева (оригиналы,
фон, оператор и администратор засева) не войти ни паролем, ни через ФСП ID — пароля засев им не ставит.
Имитатор стенда не показывает героев сценария в списке демо-учёток (`FSP_MOCK_UNLISTED_HEROES` в `docker-compose.prod.yml` —
ключи героев `seeds/demo.json`; неизвестный ключ останавливает старт имитатора). Новые сессии — 60 в сутки с адреса (правило
`demoSession`; объём держит лимит живых сессий), запросы `POST /demo` — 200 за 10 минут (правило `demo`); живых сессий не больше
60, при нехватке место отдаёт сессия, молчащая дольше всех (не меньше 20 минут); сессию без запросов 8 часов завершает
`demo.purge`. Время использования сессий — в Valkey (`demo:activity`); заход на `/demo` с живой сессией отмечает использование
тоже. Клон оператора и администратора достаёт только строки своей сессии, общие действия
(пакет ФСП, роли персонала, режим моделей) закрыты — `src/lib/server/access/demo-actor.ts`,
`tests/integration/demo-actor.test.ts`.

**Векторы после сброса.** Сброс удаляет векторы профилей и вакансий (векторы навыков остаются). Свежий засев — и заданием
`demo.reset`, и командой `main.js seed`/`reset` (`make db-seed-demo`, `make demo-reset`) — ставит `embedding.reindex`
активного пространства и пространств в сборке (`enqueueDemoReindex`, `src/lib/server/demo/job.ts`); считает его воркер, до
конца пересчёта каталог ищет по словам. Уже засеянная партия пересчёт не ставит.

**Замеры** (локально): см. `docs/deploy.md`, «Демо-данные».

## Начальный администратор

Первый администратор стенда приходит из окружения (`docs/domain.md`, 4.1), остальных назначает администратор в кабинете. Это
обычная настоящая учётка, не демо: адрес шифруется с ключевым поиском, пароль — Argon2id, вход паролем штатный (и в
`DEMO_MODE` — отказ `demo_account` касается только учёток засева). Код — `src/lib/server/admin/bootstrap/` (`ensure.ts`),
команда — `node build/admin/main.js ensure [--reset-password]`, SSR-бандл Vite, как у демо-команды
(`src/lib/server/admin/bootstrap/bundle.config.ts`): ей нужны шифрование полей и журнал с `$lib`. CMD образа запускает её
при каждом старте приложения; без `BOOTSTRAP_ADMIN_EMAIL` она ничего не делает.

- `BOOTSTRAP_ADMIN_EMAIL` включает шаг; `BOOTSTRAP_ADMIN_PASSWORD` нужен только для создания учётки и `--reset-password`,
  без адреса — ошибка конфигурации. Пароль — по правилам всех учёток (не короче 10 символов, 4 разных, не совпадает с
  адресом), в журнал и лог не попадает; заданный пароль проверяется всегда, даже если не понадобится. Переменные получает
  только сервис `app`.
- Нет учётки с этим адресом — создаётся активная, с подтверждённым адресом, паролем, каналом почты и ролью `admin`
  (`granted_by` пусто); журнал — `auth.registered` и `staff.role_granted` от `system` с `via: environment`. Без пароля в
  окружении — отказ, старт останавливается.
- Есть настоящая активная учётка — роль выдаётся, если её нет; пароль не трогается (администратор мог его сменить), и
  окружению он больше не нужен: после первого старта пароль из окружения убирают, чтобы секрет не жил в контейнере
  постоянно, — следующие старты подтверждают роль по одному адресу. `--reset-password` ставит пароль из окружения заново
  (без него — отказ), снимает блокировку и завершает все сессии учётки (`auth.password_reset`, `via: environment`).
- Адрес учётки засева или демо-сессии, неактивная учётка (в том числе с неподтверждённым адресом), слабый пароль —
  отказ с именем переменной, старт приложения останавливается.

Локально (инфраструктура поднята, миграции применены):

```sh
# в .env: BOOTSTRAP_ADMIN_EMAIL=admin@example.org, BOOTSTRAP_ADMIN_PASSWORD=<свой пароль>
pnpm admin:ensure                                                                       # собрать, создать или подтвердить
node --env-file=.env --enable-source-maps build/admin/main.js ensure --reset-password   # задать пароль заново
```

После создания `BOOTSTRAP_ADMIN_PASSWORD` в `.env` можно оставить пустым: `pnpm admin:ensure` подтвердит роль по адресу.

В `make up` это делает старт контейнера `app` с переменными из `.env`. Письма при создании не уходят: адрес считается
подтверждённым тем, кто задаёт окружение.

**Сброс демо** (`DEMO_RESET_PLAN`) сохраняет настоящий персонал: учётки без `seed_batch_id` и `demo_session_id`, у которых
есть строка `staff_roles`, их пароли и роли; сессии уходят вместе с Valkey. Каналы уведомлений не сохраняются — они ссылаются
на события согласий (append-only, сброс их очищает `TRUNCATE`), — канал почты администратора снова открывает следующий
старт приложения. Проверки — `tests/integration/bootstrap-admin.test.ts`, `tests/integration/demo-reset.test.ts`.

## Письма законному представителю

У представителя кандидата 14–17 лет нет учётки: согласия подростка и раскрытие контактов по его приглашению он подписывает по
одноразовым ссылкам из писем (`docs/domain.md`, 6.3, 6.4, 13.6; код — `src/lib/server/consent/representative.ts`,
`src/lib/server/invitations/disclosure.ts`). Письмо с согласиями уходит, когда оператор подтвердил полномочия
(`/operator/representatives/<id>`), письмо о раскрытии — когда подросток принял приглашение на стажировку; оба кандидат может
запросить снова не чаще раза в 5 минут.

**Локально** письма уходят в Mailpit (`make infra`): веб-интерфейс — http://127.0.0.1:57825, ссылка в письме ведёт на
`APP_ORIGIN` (`/representative/consent?token=…`, `/representative/disclosure?token=…`) и открывается без входа. e2e читает
письма через API Mailpit (`tests/e2e/representative.spec.ts`).

**На демо-стенде** почтовый ящик стенда посетителю не виден, поэтому письма демо-сессии показывает страница «Письма сессии»
`/demo/mail` (ссылка в шапке рядом с таймером сессии; только клону и только своей сессии, остальным — 404). Письма
представителю подростка сессии хранятся с сессией в `demo_letters` (текст зашифрован: в нём ссылка с токеном) и уходят вместе
с ней — при удалении сессии и при сбросе стенда; письма вне демо-сессий туда не пишутся. Уведомления участников сессии
страница показывает письмами, которые ушли бы: у клонов нет каналов доставки, письмо собирается из уведомления так же, как
его собрала бы доставка; уведомления, скопированные с героями, старше сессии и не показываются. Код —
`src/lib/server/demo/letters.ts`, тест — `tests/integration/demo-letters.test.ts`.

## Воркер фоновых заданий

Задания — строки таблицы `jobs` (`docs/domain.md`, раздел 17): постановка в транзакции изменения, реестр типов —
`src/lib/server/jobs/registry.ts`, очередь — `jobs/queue.ts`. Воркер — отдельный процесс из того же образа:
`node build/worker/main.js --types=<тип>[,<тип>…]`. Его код — `src/lib/server/jobs/` (цикл `worker.ts`, планировщик
`scheduler.ts`, обработчики), точка входа и сборка — `src/worker/` (`bundle.config.ts`: SSR-бандл Vite с `$lib`,
зависимости из `node_modules`). Голым Node, как `scripts/*.ts`, воркер не запускается: ему нужны `$lib` и настройки
`config()`; `$env/dynamic/private` в его сборке — окружение процесса (`src/worker/env.ts`).

**Включённые типы — всегда явным списком** (`--types`; в compose — `command` сервиса `worker`). Тип вне реестра или тип
без обработчика — отказ старта с перечнем всех проблем, а не молчаливый пропуск. Новый обработчик: модуль пишет
`defineHandler({ type, concurrency, run })`, добавляет его в `src/lib/server/jobs/handlers.ts` и тип — в `--types`
сервиса `worker`; unit-тест `src/worker/deployment.test.ts` сверяет `--types` сервиса с зарегистрированными обработчиками. Сервис
`worker` запускает все зарегистрированные типы: разбор резюме и извлечение фактов, импорт и проверку вакансий, нормализацию и векторы
вакансий, векторы профилей и пересчёт пространства эмбеддингов, соответствие, расчёт доказательств профиля, синхронизацию ФСП, сроки и напоминания приглашений, запросы исхода найма, доставку
уведомлений, проверку компании по реестру, сверку производных `derivations.reconcile`, сроки ответа на возражения `objection.deadline_watch` (напоминание персоналу
за 5 дней и при просрочке, `docs/domain.md` 12.5), `retention.sweep` и `demo.reset` (вне демо-режима его
задание отказывает). `src/worker/deployment.test.ts` краснеет, если у типа из реестра нет обработчика, у периодического задания
или расписания нет обработчика или тип не включён ни в одном `--types` compose-файлов.

| Флаг | По умолчанию | Смысл |
|---|---|---|
| `--types` | — (обязателен) | включённые типы через запятую |
| `--concurrency <тип>=<n>` | `concurrency` обработчика | сколько заданий типа воркер выполняет одновременно; флаг повторяется по типам |
| `--health-port <port>` / `--no-health` | 57310 | порт `GET /health` на `127.0.0.1` |
| `--shutdown-grace-ms <ms>` | 20000 | сколько ждать выполняющиеся задания при остановке |

**Цикл.** Захват — `claimJob` среди типов, у которых есть свободный слот, по `priority` (`FOR UPDATE SKIP LOCKED`,
не больше одного `running` на `dedup_key`). Обработчик получает задание, `AbortSignal`, `request_id` вида `job:<id>`
(для журнала) и логгер; возвращает `{ isCurrent, write }`, и воркер пишет результат условно (`completeJob`: аренда ещё
наша и вход не устарел, иначе `discarded_stale`). Аренда продлевается пульсом каждую треть срока типа; потерянная
аренда прерывает обработчик через `signal`. Ошибка: `JobFailure` с `retryable` — назад в очередь с паузой 5 · 2^(n−1) с
(не больше 10 минут) или по `retryAfterSeconds`, до `max_attempts` типа, затем `failed`; `retryable: false` — сразу
`failed`; любая другая ошибка — повторяемая, в `last_error` остаётся только класс ошибки (сообщение может содержать
данные), полный текст — в логе. Задания упавших воркеров (истёкшая аренда) раз в 15 с возвращает любой живой воркер.

**Остановка.** SIGTERM или SIGINT: захват прекращается, выполняющиеся задания дорабатывают в пределах
`--shutdown-grace-ms`; оставшимся аренда возвращается (`releaseJob`: снова `queued`, попытка не засчитывается),
обработчик получает `abort`. `stop_grace_period` сервиса — 30 с, больше льготного срока и ожидания прерванных
обработчиков (5 с).

**Периодические задания.** Планировщик — внутри воркера, без cron-контейнера: каждые 30 с каждый воркер ставит
задание текущего периода для своих включённых периодических типов (`PERIODIC_JOBS` в `scheduler.ts`):
`retention.sweep` и `market.refresh` — раз в сутки (UTC), `derivations.reconcile` — раз в час, `demo.reset` — в демо-режиме, задание наступающей ночи ждёт 00:00 UTC.
Проверка «задание периода уже есть» и постановка идут в одной транзакции под `pg_try_advisory_xact_lock` типа: два
воркера не ставят задание периода дважды, а воркер, не взявший блокировку, пропускает такт. Расписания со своими
сроками (`SCHEDULE_TICKS` в `handlers.ts`) идут на том же такте у воркера, включившего их тип: `vacancies.import` —
`scheduleVacancyImports` по `schedule` каждого включённого источника; `vacancies.text_recheck` — с запуска воркера, пока вакансии
несут проверку текста другой версии валидатора (`domain.md` 13.1) — под той же блокировкой типа. У периода одно задание
любого исхода: упавшее видно администратору и планировщиком не перезапускается. Задания `vacancies.text_recheck` ни на одной
странице кабинета не показаны — только лог воркера и `jobs.last_error`.

**`derivations.reconcile`** (`src/lib/server/derivations/reconcile.ts`, `docs/domain.md` 17.3) — страховка от потерянных
пересчётов. Страницами по 500 кандидатов (статусы `onboarding`, `active`, `ineligible_age`, `profile_revision > 0`) сверяет
для расчёта доказательств профиля, векторов профиля и соответствия (`match.refresh` по кандидату) требуемую ревизию — `profile_revision` — с
обработанной: наибольшей из `input_version` успешных заданий этого вида по кандидату и ревизии сохранённого результата
(опубликованный расчёт, векторы кандидата в пространстве `building`/`active`, строки `match_scores`). Отстающий вид без
ожидающего или выполняющегося задания ставится на текущую ревизию с `created_by = {kind: system, id: derivations.reconcile}`;
одну ревизию сверка ставит не больше раза — упавшее задание остаётся видно администратору и не повторяется каждый час, следующая
правка профиля делает вид снова должным. За прогон — не больше 2000 заданий; прогон, упёршийся в этот предел, ставит своё
продолжение под тем же ключом `reconcile:{period}` того же часа — пока есть отставание, оно не ждёт следующего часового тика.
Публикация нового набора правил (`taxonomy/publish.ts`) ставит сверку текущего часа в своей же транзакции, не дожидаясь
расписания. Итог (по видам, `joined`, `capped`) — в строке завершения лога. Тест — `tests/integration/derivations-reconcile.test.ts`.

**`retention.sweep`** держит партиции журнала `audit_events` на 24 месяца вперёд (`audit_events_ensure_partitions`) и
удаляет месяцы старше `audit_retention_months` действующей `retention_policy` — по событию журнала
`audit.partition_dropped` на месяц, в одной транзакции с проверкой аренды. Без опубликованной политики ничего не
удаляется (срок хранения — продуктовое решение). Партиция с чужим именем — отказ без повторов: её границам задание не
доверяет. В той же транзакции под ролью `fsp_retention` обнуляются `content` и `file_id` артефактов попыток тестирования,
чей `retention_until` (из `assessment_policy`) раньше текущей даты UTC; строка, хэш и оценка остаются. Число очищенных —
`artifacts_cleared` в строке завершения задания.

**Наблюдаемость.** Логи — JSON по строке (`docker compose logs worker`): `job_id`, `job_type`, `attempt`, `request_id`,
исход и длительность; без ПДн. `GET /health` на `127.0.0.1:57310` — `200 ok`, пока воркер работает и база отвечала
недавно, иначе `503 degraded`; в теле — счётчики по типам (`claimed`, `succeeded`, `discardedStale`, `retried`, `failed`,
`leaseLost`, `released`, `inFlight`), возвращённые аренды и поставленные периодические задания. Healthcheck сервиса
`worker` ходит туда же.

Тесты — `tests/integration/worker.test.ts` (захват по приоритету, повторы с backoff до `failed`, возврат истёкшей аренды,
остановка без потери задания, два воркера без двойного выполнения, периодическое задание однажды, отказ старта) и
`tests/integration/jobs-retention.test.ts`. Защиты держат тесты, которые краснеют без них: без `SKIP LOCKED` при захвате
два воркера выполняют задания дважды, без backoff повтор идёт сразу, без возврата аренды задание при остановке зависает
в `running`, без advisory lock планировщик ставит задание, пока другой воркер решает.

## Песочница `sandbox`

Контракт — [`contracts.md`](contracts.md), раздел 6; артефакты попыток — [`domain.md`](domain.md), раздел 10.4.
Движок — [go-judge](https://github.com/criyle/go-judge) (`services/sandbox/`), адаптер приложения —
`src/lib/server/sandbox/` (`GoJudgeRunner` реализует `SandboxRunner`).

**Как устроен прогон.** Адаптер валидирует запрос (лимиты — в границах `LIMIT_BOUNDS` из `request.ts`, иначе
`invalid_request`), компилирует код одним вызовом go-judge и прогоняет тесты по очереди, каждый — в свежем окружении
со своими лимитами. Скомпилированная программа между шагами лежит в хранилище go-judge и удаляется после ответа
(забытая истекает сама через 5 минут). Вывод сравнивает адаптер (`checker.ts`): `exact` — строки без учёта `\r\n`,
пробелов в конце строк и пустых строк в конце; `tokens` — последовательность токенов; `float_eps` — числа с абсолютной
или относительной погрешностью `eps`, остальные токены точно. Эталон в песочницу не передаётся. Статусы go-judge
переводятся в вердикты по таблице контракта; переполнение вывода (`CollectSizeExceeded`) — всегда `output_limit`,
даже если программа после него упала. Тест, чей лимит по часам уже не помещается в 60 с запроса, не запускается и
получает `time_limit` с `skipped: true`. Больше `maxConcurrentRuns` одновременных прогонов в процессе — `busy`.
`artifacts.ts` строит строки `assessment_artifacts`: `code_submission` до вызова, `run_result` компиляции и каждого
теста после; `sha256` — хэш канонического JSON содержимого (`src/lib/server/json/canonical.ts`, общий с хэшем версии
таксономии). Адрес шлюза и число одновременных прогонов процесса — `SANDBOX_URL` и `SANDBOX_MAX_CONCURRENT_RUNS`
(по умолчанию 2, как `-parallelism` движка).

**Языки** задаёт образ: `services/sandbox/languages.json` — команды компиляции и запуска, окружение, сколько
процессов и потоков нужно самому рантайму (`tasks`, cgroup pids считает и потоки); версии тулчейнов вписываются при
сборке образа. Адаптер читает этот файл изнутри песочницы (`/etc/sandbox/languages.json`), поэтому набор языков и версии
всегда те, что реально исполняют код. Лимит процессов задачи (`processes`) — сколько процессов программа может иметь
сама, включая себя; потоки рантайма добавляются сверху. Особенности:
- `typescript` — снятие типов Node (`ts-strip.js`), без трансформаций: `enum`, `namespace`, параметры-свойства — ошибка
  компиляции;
- `go` — стандартная библиотека собрана при сборке образа в кэш только для чтения; без него сборка каждого решения
  стоила бы ~10 с CPU. Окружение прогрева в `Dockerfile` должно совпадать с окружением компиляции в `languages.json`;
- `java21` — `javac` и `jar` в один шаг компиляции, куча JVM равна лимиту памяти (`-Xmx{memory_mb}m`), так что
  переполнение — `memory_limit`, а не `OutOfMemoryError` в `runtime_error`.
- `kotlin` — компилятор JetBrains (релиз из GitHub, контрольная сумма закреплена в `Dockerfile`) запускается на JDK образа
  напрямую через `kotlin-preloader.jar`, без скрипта `kotlinc`; в образе только нужные jar: компилятор, stdlib, reflect,
  `kotlinx-coroutines-core-jvm`. Исходник `Main.kt` с `fun main()` на верхнем уровне, класс запуска `MainKt`; stdlib и
  корутины идут в classpath при компиляции и запуске, в `main.jar` их нет. Куча компилятора ограничена 384 МБ (лимит
  `compileMemoryMb` — до 512), «hello world» компилируется ≈ 2 с CPU, решение на 100 строк ≈ 3 с (один CPU, как на
  стенде) — укладывается в `compileCpuTimeMs` по умолчанию (10 с). Запуск как у `java21`: куча равна лимиту памяти.

**Изоляция программы.** Каждый запуск go-judge делает в собственных пространствах имён: user (программа — uid 1536
внутри, снаружи — отдельный непривилегированный uid на окружение, без дополнительных групп), network (только `lo`, и тот
выключен), mount (корень — tmpfs; тулчейны `/usr`, `/bin`, `/lib` только для чтения; писать можно в `/w` и `/tmp`, это
свежие tmpfs на каждый запуск, их объём входит в лимит памяти), PID, IPC, UTS. Лимиты — cgroup v2 (CPU-время, память,
pids), время по часам — таймер go-judge. Запуск без cgroup go-judge не допускает (`-no-fallback`).

**Фильтр системных вызовов программы** — `services/sandbox/seccomp.yaml`, его ставит go-judge перед `execve` каждой
программы (компиляторы и решения; флаг `-seccomp-conf` добавляет `entrypoint.sh` перед флагами команды, поэтому он
остаётся и при команде из compose; без файла контейнер не стартует). Профиль контейнера (`seccomp.json`) обязан
разрешать namespaces и mount самому go-judge и потому разрешал их и программе: `unshare(CLONE_NEWUSER)` с mount внутри,
`clone` с флагами namespace, сокет `AF_NETLINK`, `ptrace` проходили. Фильтр — список разрешённых: вызовы, которые
Docker по умолчанию разрешает любому контейнеру, плюс `arch_prctl`; без `unshare`, `setns`, `mount`/`umount2`,
`pivot_root`, нового API монтирования (`fsopen`, `open_tree`, …), `keyctl`/`add_key`/`request_key`, `bpf`,
`userfaultfd`, `io_uring_*`, `perf_event_open`, `ptrace`, `process_vm_*`, `kcmp`, `modify_ldt`. Остальное — `EPERM`;
`clone` — только без флагов namespace; `clone3` — `ENOSYS` (флаги у него в памяти, фильтр их не видит; glibc тогда
откатывается на `clone`); `socket` — только `AF_UNIX`, `AF_INET`, `AF_INET6`; `personality` — значения Docker. Вызовы
через 32-битный вход (`int 0x80`) — `EPERM` целиком: номера там другие и прошли бы мимо фильтра 64-битных. Формат —
политика `elastic/go-seccomp-bpf`; её читает только go-judge, собранный с тегом `seccomp`, а выпущенный бинарник и образ
`criyle/go-judge` собраны без него и флаг молча игнорируют, поэтому `Dockerfile` собирает go-judge из модуля
(`go install …@GO_JUDGE_VERSION`, сверка с базой контрольных сумм Go). Имена вызовов — из таблицы x86_64 этой
библиотеки: неизвестное имя останавливает go-judge на старте; образ — только для x86_64.

**Права контейнера.** go-judge строит окружения из пространств имён и монтирований, поэтому контейнеру нужен
`CAP_SYS_ADMIN`. Минимальный набор проверен перебором (Docker 29.8, ядро 7.0):
- `cap_add`: `SYS_ADMIN` (namespaces, mount, pivot_root, запись в cgroup), `SETUID`/`SETGID` (карты uid/gid окружений),
  `SETFCAP` (карта uid 0 в user namespace, ядро ≥ 5.12); без любого из четырёх окружение не создаётся, остальные
  capabilities сброшены;
- `seccomp`: профиль Docker по умолчанию (moby/profiles `seccomp/v0.2.3`) плюс `pivot_root` — `services/sandbox/seccomp.json`;
  без `pivot_root` окружение не входит в свой корень;
- `apparmor=unconfined`: профиль `docker-default` запрещает любые `mount`; свой профиль потребовал бы загрузки на хосте;
- cgroup: у контейнера свой cgroup namespace, смонтированный только для чтения; `entrypoint.sh` перемонтирует его на
  запись и переносит процесс в дочернюю группу. Писать можно только в поддерево контейнера — лимиты самого контейнера
  (1.5 ГБ, 2 CPU, 512 pids) заданы уровнем выше и недоступны;
- procfs: ядро разрешает смонтировать procfs в user namespace, только если где-то виден procfs без перекрытий, а Docker
  маскирует части `/proc`. Вместо снятия масок (`systempaths=unconfined`, что открыло бы запись в `/proc/sys`)
  `entrypoint.sh` монтирует отдельный экземпляр только для чтения в `/run/sandbox/proc`.

`--privileged` не нужен. Остальное ограничено: файловая система только для чтения (`/tmp`, `/run` — tmpfs),
`no-new-privileges`, память 1.5 ГБ без свопа (две программы по ≤ 512 МБ плюс go-judge и его хранилище), 2 CPU,
512 pids, ни томов, ни Docker-сокета. **Остаточный риск:** go-judge работает от root с `CAP_SYS_ADMIN` без AppArmor;
уязвимость в go-judge или в ядре за вызовами, которые фильтр программе оставил, даёт выход в контейнер с этими правами,
а через ядро — на хост.
Поэтому контейнер изолирован и по сети: сеть `sandbox` — `internal: true`, в ней только шлюз `sandbox-gateway` (nginx),
который пропускает `POST /run`, `DELETE /file/{id}` и `GET /version`, а загрузку файлов, чтение хранилища и WebSocket
закрывает. Приложение ходит к песочнице через шлюз (`SANDBOX_URL`); песочница не видит ни базу, ни хранилище, ни
приложение, а программа кандидата — даже шлюз.

`make infra` собирает образ песочницы, если его нет (≈1.3 ГБ, первая сборка тянет образы тулчейнов); после правок в
`services/sandbox` — `docker compose up -d --build --wait sandbox sandbox-gateway`. Версии: go-judge — `GO_JUDGE_VERSION`, тулчейны —
теги образов в `ARG` `Dockerfile`, g++ — из снимка snapshot.debian.org (`DEBIAN_SNAPSHOT`); обновление — сдвиг тега или даты.

**Тесты** — `tests/integration/sandbox.test.ts`: собирают образ (`docker build`, кэш общий с compose) и запускают
контейнер с правами из `compose.yaml`. Проверяют решения на всех языках, `wrong_answer`, `time_limit` по CPU и по часам,
`memory_limit` (C++ и JVM), `runtime_error` с кодом и сигналом, `compile_error`, `output_limit`, отказ сети, запись вне
`/w` и `/tmp`, упор fork-бомбы в pids, отказ программе в namespaces, mount, netlink, ptrace и прочем из фильтра (зонды
на C++ и Python), `busy`, `unavailable`, запись артефактов в `assessment_artifacts`. Сетевой тест
краснеет с `-net-share` go-judge, тест времени — без лимитов времени, fork-бомба — без лимита процессов, зонды — без
фильтра программы.

## Имитатор ФСП `fsp-mock`

Контракт — [`contracts.md`](contracts.md), разделы 1 (API достижений) и 2.6 (ФСП ID); схема ответов —
`contracts/fsp-achievements/v1.schema.json`, тесты имитатора проверяют по ней каждый ответ. Код — `services/fsp-mock/`:
Node 24 и TypeScript без сборки (Node снимает стираемые типы, как у `scripts/*.ts`), OIDC — библиотека `oidc-provider` 9.
Это отдельный пакет со своим `pnpm-lock.yaml`, не член workspace корня; зависимости ставит `pnpm install` корня (скрипт
`prepare`) или `pnpm fsp-mock:install`. После правок — `docker compose up -d --build --wait fsp-mock`.

**Один адрес для браузера и контейнеров.** `iss` ID-токена сверяется точным сравнением, поэтому браузер (редирект на
вход) и контейнер `app` (discovery, токены, API) должны видеть одинаковый issuer. Имитатор везде доступен как
`http://fsp-mock.localhost:57610`, issuer — `http://fsp-mock.localhost:57610/realms/fsp`. Браузеры и glibc хоста
разрешают `*.localhost` в loopback, где опубликован порт; контейнеры разрешают то же имя через сетевой алиас compose, а
процесс внутри слушает тот же порт 57610. Если на хосте имя не разрешается (`getent hosts fsp-mock.localhost` пусто) —
строка `127.0.0.1 fsp-mock.localhost` в `/etc/hosts`.

**Переменные.** Приложение читает `FSP_ID_*`, `FSP_ACHIEVEMENTS_*`, `FSP_WEBHOOK_SECRET`, `FSP_ASSERTION_SECRET` из `.env`
(контейнер `app` получает их в `compose.yaml`); имитатор получает те же значения под своими именами:

| Переменная имитатора | Откуда в compose | Смысл |
|---|---|---|
| `FSP_MOCK_ORIGIN`, `PORT` | `http://fsp-mock.localhost:57610`, `57610` | публичный адрес (issuer = адрес + `/realms/fsp`) и порт процесса |
| `FSP_MOCK_CLIENT_ID`, `FSP_MOCK_CLIENT_SECRET` | `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET` | единственный клиент — платформа |
| `FSP_MOCK_REDIRECT_URIS` | колбэки `pnpm dev`, e2e и контейнера | через запятую, точное совпадение |
| `FSP_MOCK_ASSERTION_SECRET` | `FSP_ASSERTION_SECRET` | HMAC утверждений о согласии (`service_with_assertion`) |
| `FSP_MOCK_WEBHOOK_URL`, `FSP_MOCK_WEBHOOK_SECRET` | `http://app:3000/...`, `FSP_WEBHOOK_SECRET` | подписка на вебхуки при старте |
| `FSP_MOCK_CONTROL_TOKEN` | `FSP_MOCK_CONTROL_TOKEN` | токен ручек управления; без него ручки выключены |
| `FSP_MOCK_SEED`, `FSP_MOCK_ATHLETES` | по умолчанию `fsp-career-2026-7`, `3000` | сид данных и число спортсменов (200–5000) |

Секреты — не короче 32 символов; без обязательной переменной процесс не стартует и называет её.

**ФСП ID.** Пути как у Keycloak: `{issuer}/.well-known/openid-configuration`, `/protocol/openid-connect/auth`, `/token`,
`/userinfo`, `/certs`, `/logout`, `/token/introspect`, `/revoke`. Authorization Code с обязательным PKCE S256,
`client_secret_basic`, `redirect_uri` — точное совпадение, `iss` в ответе авторизации, ID-токен RS256 с `nonce` и
`auth_time`, `prompt=login` и `max_age` требуют повторного входа. Claims: `sub`, `name`, `given_name`, `family_name`,
`preferred_username`, `email`; даты рождения и телефона нет. Scopes сверх стандартных: `fsp_achievements` —
делегированный доступ к достижениям (с `offline_access` выдаётся refresh-токен; Keycloak не требует для этого
`prompt=consent`, имитатор добавляет его сам), `fsp_achievements_service` — сервисный токен `client_credentials`.
Поля discovery из раздела 2.6 повторяют сохранённый discovery `sso.fsp-russia.ru` (фикстура тестов); обслуживается
подмножество, нужное клиенту платформы (code + PKCE S256, refresh, client credentials, RS256), остальные объявленные
значения запросами отвергаются. Страница входа помечена как имитатор: пароля нет, пользователь выбирается из демо-учёток
или поиском по сиду. Сессии, токены и ключ подписи живут в памяти процесса: после перезапуска — вход заново.

**API достижений** (`/v1`):

| Запрос | Доступ | Ответ (`$defs` схемы) |
|---|---|---|
| `GET /v1/disciplines` | открыт | `DisciplineList` |
| `GET /v1/competitions?discipline=&level=&season=&page=&pageSize=` | открыт | `CompetitionList` |
| `GET /v1/competitions/{id}` | открыт | `Competition` |
| `GET /v1/athletes/{fspId}` | допуск | `Athlete` |
| `GET /v1/athletes/{fspId}/achievements?page=&pageSize=` | допуск | `AchievementsPage` |
| `POST`, `GET /v1/webhooks`, `DELETE /v1/webhooks/{id}` | сервисный токен | `WebhookSubscription` |

- Допуск (`AccessGrant`, раздел 1.2). `delegated_user_token`: `Authorization: Bearer <токен ФСП ID со scope
  fsp_achievements>`, `sub` токена должен совпасть с `{fspId}`. `service_with_assertion`: `Authorization: Bearer
  <сервисный токен>` и `X-FSP-Consent-Assertion: base64url(JSON {sourceAthleteId, consentEventId, issuedAt, expiresAt,
  signature})`, где `signature` — hex HMAC-SHA-256 строк `sourceAthleteId`, `consentEventId`, `issuedAt`, `expiresAt`,
  соединённых `\n`, секретом `FSP_ASSERTION_SECRET`; срок — не больше 5 минут. Допуск проверяется до поиска спортсмена:
  чужой или несуществующий `fspId` — одинаково `grant_mismatch`.
- Ошибки — `{ "error": { "code", "message" } }`: `401 grant_invalid`, `403 grant_mismatch`, `404 not_found` (например,
  учётка ФСП ID без профиля спортсмена), `429 rate_limited` с `Retry-After`, `503 unavailable`, `400 invalid_request`.
- Полнота. Результаты идут страницами (новые первыми, `pageSize` до 100, по умолчанию 20); спортсмен и разряды повторяются
  на каждой странице, соревнования — те, на которые ссылаются результаты страницы. `sourceVersion` (и `ETag`) —
  `{datasetId}.{ревизия спортсмена}`: любое изменение данных спортсмена меняет версию. Снимок полон, если получены все
  страницы, версия одна и у каждой страницы `complete: true`.
- `Result.id` — собственный стабильный ID записи; неизвестные значения перечислений приходят как `unknown` с исходной
  строкой в `rawValues` (в сиде: роль в команде `оператор`, уровень «Кубок технологических видов спорта»).

**Вебхук** (раздел 1.5): `POST` на адрес подписки с заголовками `X-FSP-Event-Id`, `X-FSP-Timestamp` и
`X-FSP-Signature: sha256=<hex HMAC-SHA-256 от "{timestamp}.{rawBody}">`. Подписка из `FSP_MOCK_WEBHOOK_URL` создаётся
при старте, дополнительные — `POST /v1/webhooks`. Повторы — через 1 и 5 секунд при сетевой ошибке, `429` и `5xx`.
Приложение, запущенное `pnpm dev` на хосте, вебхуков из контейнера не получает (Vite слушает `127.0.0.1` хоста):
для него синхронизация запускается вручную, отправленное видно в `GET /mock/webhooks/deliveries`.

Изменения держатся до перезапуска или `POST /mock/reset`; по умолчанию каждое изменение отправляет вебхук
(`?notify=false` — без него).

| Запрос | Что делает |

## Svelte 5: runes

Режим runes включён принудительно для кода проекта (`compilerOptions.runes` в `vite.config.ts`, библиотеки из
`node_modules` компилируются в своём режиме). `export let` и `$:` — ошибки компиляции. `on:click` и `<slot>` компилятор
пропускает с предупреждением об устаревании, а `pnpm check` (`--fail-on-warnings`) — нет. `$app/stores` устарел: вместо
него `$app/state`.

| Задача | Svelte 5 |
|---|---|
| реактивное состояние | `let count = $state(0);` — объекты и массивы глубоко реактивны; `$state.raw` — без проксирования |
| вычисляемое значение | `const double = $derived(count * 2);`, сложное — `$derived.by(() => { ... })` |
| побочный эффект | `$effect(() => { ...; return () => cleanup(); });` — только для работы с внешним миром, не для вычислений |
| свойства компонента | `let { title, items = [], ...rest }: Props = $props();` |
| двусторонняя привязка | `let { value = $bindable() } = $props();` |
| события | атрибуты `onclick={handler}`; события компонента — свойства-колбэки (`onsave`) |
| слоты | `{#snippet row(item)}...{/snippet}` и `{@render row(item)}`; содержимое по умолчанию — `children` |
| свойства страницы и макета | `let { data }: PageProps = $props();`, `let { children }: LayoutProps = $props();` из `./$types` |
| состояние страницы | `import { page } from '$app/state';` → `page.url`, `page.params` (без `$`) |
| общее состояние | модуль `*.svelte.ts` с `$state` внутри класса или объекта |
| классы | `class={['card', active && 'card-active']}` |
| отладка | `$inspect(value)` |

## Tailwind CSS 4

- Подключение — `@import 'tailwindcss';` в `src/app.css`, плагин `@tailwindcss/vite`. Файла `tailwind.config.js` нет:
  тема настраивается в CSS.
- Токены темы: `@theme { --color-brand-600: oklch(...); --font-display: ...; }` → классы `bg-brand-600`, `font-display`.
- Свои утилиты — `@utility name { ... }`, свои варианты — `@custom-variant dark (&:where(.dark, .dark *));`.
- Дополнительные источники классов — `@source '../path';` (по умолчанию сканируется весь проект, кроме `.gitignore`).
- В `<style>` компонента утилиты доступны через `@reference '../app.css';` и `@apply`.
- Синтаксис: CSS-переменная как значение — `bg-(--brand)`; `!important` — суффикс `bg-red-500!`; варианты применяются
  слева направо; контейнерные запросы — `@container` и `@md:...` без плагина.
- Переименования относительно v3: `shadow-sm` → `shadow-xs`, `shadow` → `shadow-sm`, `rounded-sm` → `rounded-xs`,
  `outline-none` → `outline-hidden`, `ring` → `ring-3`; цвет рамки по умолчанию — `currentColor`.
- Порядок классов упорядочивает `prettier-plugin-tailwindcss`.

## Грабли окружения

- **Прокси.** Если в окружении заданы `HTTP_PROXY`/`HTTPS_PROXY`, запросы к локальным сервисам уходят в прокси и виснут
  или получают чужой ответ: `curl --noproxy '*'`, `NO_PROXY=localhost,127.0.0.1`. Поэтому Playwright ждёт готовности
  сервера по порту (`webServer.port`), а не по URL.
- **`docker compose up --wait` и одноразовые контейнеры.** Завершившийся init-контейнер `--wait` считает ошибкой
  (код 1), даже при выходе с нулём. Поэтому бакет создаёт само хранилище: `weed mini` при старте заводит бакет из
  `S3_BUCKET`, а healthcheck `storage` зеленеет, только когда бакет есть (S3 API отвечает раньше, чем бакет создан).
- **Хранилище.** SeaweedFS `weed mini`: мастер, том, filer и S3 API в одном процессе; единственная учётка — ключи
  `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` (переменные `AWS_*` контейнера), автосоздание бакетов при загрузке
  выключено. Интеграционные тесты поднимают тот же образ с той же командой (`tests/helpers/storage.ts`). Образы MinIO
  больше не публикуются — прежний сервис `minio` и его переменные `MINIO_ROOT_*` удалены; в старом `.env` они не мешают.
- **TypeScript закреплён на 6.0.** `svelte-check` и `typescript-eslint` пока не поддерживают TypeScript 7.
- **pnpm 11+.** Настройки pnpm читаются только из `pnpm-workspace.yaml`; поле `pnpm` в `package.json` игнорируется.
  Неразрешённый скрипт установки зависимости — ошибка `ERR_PNPM_IGNORED_BUILDS`.
- **Коммит сборки.** `vite build` берёт коммит из `APP_COMMIT` или из `git rev-parse`; в Docker-сборке `.git` нет, поэтому
  `APP_COMMIT` передаётся аргументом (`make up`, `pnpm docker:build`), без него сборка падает с понятной ошибкой.
- **Скрипты на TypeScript** (`scripts/*.ts`) запускаются обычным `node` (встроенное снятие типов): только стираемый
  синтаксис — без `enum`, `namespace`, параметров-свойств (`erasableSyntaxOnly` в `tsconfig.json`), без алиасов `$lib`.
  Стартовые скрипты образа импортируют модули `src/` по относительному пути, поэтому `Dockerfile` копирует в образ весь
  `src/` (тесты отсекает `.dockerignore`), а не выбранные файлы: новый импорт не требует правки `Dockerfile`. Зависимость
  из `devDependencies` в таком скрипте в образе не найдётся — её ловит `pnpm check:image`.
- **Общая машина.** Тесты ограничены по параллелизму: Vitest `--maxWorkers=3`, Playwright `--workers=2`, тесты
  `docparse` — в одном процессе и в контейнере с `--cpus 2`. Integration и e2e одновременно не запускать.
- **Порт у сервиса во `internal`-сети не публикуется.** Docker не пробрасывает порты контейнера, у которого нет других
  сетей, поэтому доступ к `docparse` и `sandbox` с хоста идёт через их шлюзы.
- **Песочнице нужен cgroup v2 на хосте** (`stat -fc %T /sys/fs/cgroup` → `cgroup2fs`) с контроллерами `cpu`, `memory`,
  `pids`. Без них контейнер `sandbox` не стартует и пишет причину в лог.
