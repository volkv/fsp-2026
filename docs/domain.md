# Модель предметной области

Словарь и модель данных ядра платформы: сущности, поля, связи, инварианты, жизненные циклы, владельцы записей и правила видимости.
Контракты внешних сервисов и адаптеров — в [`contracts.md`](contracts.md).

Документ описывает всё, что следует из карточки задачи и не зависит от технического задания. Продуктовые политики, которые ТЗ может
изменить (набор ролей, ключ категории, вилка, срок ответа, режим несовершеннолетних), вынесены в версионированные данные и справочники,
а не в структуру таблиц. Такие места помечены **«ТЗ-зависимо»**; сводный список — в разделе 20.

## 0. Соглашения

**Типы.**

| Обозначение | Тип PostgreSQL | Смысл |
|---|---|---|
| `id` | `uuid` (v7) | внутренний идентификатор, генерирует приложение |
| `ext_id` | `text` | внешний идентификатор (OIDC `sub`, ID спортсмена, ID соревнования) — непрозрачная строка, формат не проверяется, UUID не требуется |
| `ts` | `timestamptz` | момент времени, хранится в UTC |
| `date` | `date` | календарная дата без времени |
| `enum` | `text` + `CHECK` | перечисление; новые значения — миграцией |
| `money` | `integer` | целое число единиц валюты; валюта, период и налоговая база — в соседних полях (блок «вилка» ниже) |
| `hash` | `text` | SHA-256 в hex, если не сказано иное |
| `enc` | `bytea` | значение, зашифрованное на уровне приложения (AES-256-GCM, ключ из окружения, версия ключа в префиксе) |
| `hmac` | `text` | HMAC-SHA-256 нормализованного значения с секретом приложения — для поиска по зашифрованному полю |
| `jsonb` | `jsonb` | структура со схемой, описанной рядом; схема валидируется в приложении |

**Обязательность** в таблицах полей: **да** — `NOT NULL`; **нет** — допускает `NULL`; **усл.** — обязательно при условии, указанном в смысле поля.

**Блок «вилка»** (`salary`) — один набор колонок везде, где хранится зарплата (вакансия, публикация, условия приглашения, ожидания
кандидата, показатели рынка):

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `salary_min`, `salary_max` | `money` | нет | границы; `NULL` — граница неизвестна; обе `NULL` — зарплата не указана; при обеих `salary_min ≤ salary_max` |
| `salary_currency` | `text` | усл. | ISO 4217 (`RUB`, `USD`, …); обязательна, если есть хоть одна граница |
| `salary_period` | `enum` | усл. | `month` · `year` · `hour` · `project`; обязателен, если есть хоть одна граница |
| `salary_tax_base` | `enum` | усл. | `gross` (до НДФЛ) · `net` (на руки) · `unknown`; обязательна, если есть хоть одна граница |

Функция `compareSalary(a, b) → lower | equal | higher | overlap | not_comparable`: сравнение выполняется, только если у обеих вилок
совпадают `salary_currency`, `salary_period` и `salary_tax_base` и ни одна база не `unknown`; иначе `not_comparable`. Неизвестная
граница — открытый конец интервала («от 200 000» = [200 000, ∞)); вилка без обеих границ несравнима (`not_comparable`). Пересчёт между gross
и net, валютами или периодами в сравнениях не делается; где пересчёт показан (рынок, раздел 12.5), он помечен как оценка.

**Общие правила.**

- Имена таблиц и колонок — `snake_case`, таблицы — во множественном числе.
- У изменяемых записей есть `created_at ts` и `updated_at ts`; в таблицах полей они не повторяются.
- **Append-only** таблицы (события согласий, раскрытия, журнал, оценки тестов, входящие события интеграций) защищены триггером,
  запрещающим `UPDATE` и `DELETE`, и отдельной ролью БД без этих прав. Исключение — задание очистки по сроку хранения, оно работает под
  отдельной ролью и само пишет событие в журнал. **Реализация:** триггер пропускает только `DELETE` от роли `fsp_retention`
  (задание очистки переключается на неё `SET LOCAL ROLE`); отдельная роль приложения без прав `UPDATE`/`DELETE` на эти таблицы —
  настройка развёртывания, пока приложение подключается владельцем схемы.
- Удаление персональных данных — физическое, через задания очистки (раздел 19). «Мягкое удаление» флагом для ПДн не используется.
- **Версионированные справочники** (таксономия, правовые документы, политики продукта, правила вывода) неизменяемы после публикации.
  Изменение — новая версия. Записи, рассчитанные по справочнику, ссылаются на конкретную версию.
- Слово «оператор» в документе означает две разные вещи, поэтому идентификаторы разведены: `operator` — роль сотрудника ФСП в продукте
  (модерация, аудит); `pd_operator` — оператор персональных данных в смысле 152-ФЗ (юридическое лицо).

## 1. Словарь

| Термин | Идентификатор | Определение |
|---|---|---|
| Пользователь | `user` | Учётная запись платформы. Своя идентичность `user_id`, не совпадает ни с одним внешним идентификатором. |
| Внешняя идентичность | `external_identity` | Пара `(issuer, subject)` от внешнего провайдера входа (ФСП ID). Устойчивый идентификатор по OIDC Core §5.7. |
| Связь со спортсменом | `athlete_link` | Связь пользователя с ID спортсмена в конкретном источнике достижений. Отдельна от внешней идентичности. |
| Кандидат | `candidate` | Профиль соискателя, принадлежащий пользователю. |
| Работодатель | — | Пользователь, состоящий в компании (`company_member`) с ролью владельца или рекрутера. |
| Компания | `company` | Организация-работодатель, идентифицируется ИНН, проходит проверку. |
| Оператор ФСП | `operator` | Роль сотрудника ФСП: модерация компаний, возражений, полномочий представителей; чтение журнала. |
| Администратор | `admin` | Роль технического администратора: управление ролями персонала и справочниками. |
| Законный представитель | `legal_representative` | Родитель, усыновитель, опекун или попечитель несовершеннолетнего кандидата. **Не учётная запись**, а подтверждаемая связь с кандидатом. |
| Оператор ПДн | `pd_operator` | Юридическое лицо, которое обрабатывает персональные данные платформы. Хранится как данные, а не как константа. |
| Правовой документ | `legal_document` | Версия текста согласия или соглашения с хэшем и снимком оператора ПДн. |
| Событие согласия | `consent_event` | Факт выдачи или отзыва согласия по конкретной версии документа, append-only. |
| Раскрытие | `disclosure` | Факт передачи идентифицирующих данных кандидата конкретной компании по конкретному основанию, append-only. |
| Факт источника | `source_fact` | Слой 1 доказательств: запись, полученная из источника (ФСП, тест, Codeforces, GitHub, резюме), с уровнем доверия. |
| Утверждение | `claim` | Слой 2: утверждение о кандидате, извлечённое из факта (например, из блока резюме), с цитатой. |
| Вывод о навыке | `skill_inference` | Слой 3: вывод «у кандидата есть основания для навыка с силой s», рассчитанный правилом конкретной версии. Сила — вес оснований, **не вероятность**: калибровки нет, в интерфейсе — полоса («слабые / умеренные / сильные основания»), не проценты. |
| Группа зависимых доказательств | `evidence_group` | Вклады, описывающие одно событие реального мира (результат, разряд по этому результату, упоминание того же соревнования в резюме). Внутри группы вклады не складываются (раздел 9.3). |
| Уровень доверия | `trust_level` | `fsp_verified` · `platform_verified` · `public_verifiable` · `claimed` — кем и как проверены факт и его принадлежность кандидату. Свойство **факта**, а не вывода, и не общий приоритет источников: вклад в навык определяется релевантностью факта утверждению (правило проекции). |
| Квитанция проверки | `verification_receipt` | Подписанное платформой заявление о проверенном факте: источник, дата сверки, ссылка на запись источника, хэш снимка, что подтверждает и чего нет. Проверяется без раскрытия личности (раздел 9.6). |
| Группа опыта | `experience_entry` | Место работы из резюме: должность — организация — период — применённые навыки, с несколькими цитатами (раздел 9.5). |
| Уровень ФСП | `fsp_level` | Фасет L1–L5 по дисциплине из достижений ФСП. Не грейд и в грейд не пересчитывается (раздел 12.2). |
| Характер подтверждения | `attestation` | Свойство вывода: `direct` (факт прямо подтверждает навык), `derived` (навык выведен правилом из факта о другом), `claimed`. |
| Категория | `category_assignment` | Назначение кандидату роли, диапазона грейда и ядра стека по результату конкретного расчёта. Оси независимы: установленная ось сохраняется, когда другая — «недостаточно данных». |
| Желаемая роль | `desired_role` | Роль, которую кандидат ищет сам. Отличается от **выведенной** роли категории; на расчёт категории не влияет. |
| Расчёт категоризации | `categorization_run` | Детерминированный расчёт над снимком входа при фиксированных версиях таксономии и правил и заданном моменте `as_of`. |
| Возражение | `category_dispute` | Обращение кандидата против категории (ч. 3–4 ст. 16 152-ФЗ): срок 30 дней, ответственный, результат. |
| Вакансия | `vacancy` | Нормализованное предложение работы. `origin = own` — опубликована проверенной компанией на платформе, вилка полная; `origin = external` — собрана из публикаций внешних источников, вилка и грейд могут быть неизвестны. |
| Публикация | `vacancy_posting` | Запись о вакансии в конкретном внешнем источнике (`source`, `external_id`, URL, исходные условия, даты). У одной внешней вакансии может быть несколько публикаций — кластер дублей. |
| Заявка «это наша вакансия» | `vacancy_claim` | Обращение работодателя, связывающее внешнюю вакансию с компанией; ведёт в проверку компании. Прав на приглашения по внешней вакансии не даёт. |
| Соответствие | `match` | Оценка пары «вакансия ↔ кандидат» по версии правил с сохранённым разложением на компоненты и объяснением; одна и та же в обе стороны. |
| Приглашение | `invitation` | Выход работодателя на конкретного кандидата по собственной вакансии; условия — неизменяемые версии (`invitation_terms`) со сроком ответа. |
| Версия условий | `invitation_terms` | Неизменяемый набор условий приглашения. Пересмотр — новая версия с показом изменений и отдельным принятием. |
| Процесс найма | `hiring_process` | Этапы после принятия приглашения (собеседование, предложение, выход) и исход, о котором сообщает каждая сторона. |
| Уведомление | `notification` | Сообщение пользователю о событии с доставкой по каналам (почта, Telegram) и отметками доставки. |
| Партнёр соревнования | `competition_partnership` | Проверенная компания, которой оператор ФСП открыл пул финалистов конкретного соревнования; кандидаты видны ей по отдельному согласию. |
| Рынок категории | `market_indicator` | Три раздельных показателя: ожидания кандидатов, вилки вакансий, внешний ориентир; у каждого выборка, дата, география, налоговая база и метод. |
| Проекция карточки | `projection` | Набор полей кандидата, доступный конкретному зрителю в конкретном контексте: `self`, `catalog`, `recipient`, `public`, `operator`. |
| Пространство эмбеддингов | `embedding_space` | Неизменяемое описание способа построения векторов. Векторы сравнимы только внутри одного пространства. |
| Конверт ML-результата | `ml_result` | Запись о вызове модели или правил: версии входа, схемы, таксономии, модели, режим обработки, ссылки на доказательства. |
| Задание фона | `job` | Единица фоновой работы с версией входа, ключом дедупликации, арендой и условной записью результата. |
| Политика продукта | `product_policy` | Версионированный набор параметров (срок ответа, режим несовершеннолетних, пороги), на который ссылаются записи. |

## 2. Карта агрегатов

```
users ─┬─ password_credentials, email_tokens, sessions (Redis), api_keys
       ├─ external_identities (issuer, subject) ── athlete_links (source, source_athlete_id)
       ├─ staff_roles (operator | admin)
       ├─ notification_channels, notifications ── notification_deliveries
       ├─ company_members ── companies ─┬─ company_verifications
       │                                └─ competition_partnerships
       └─ candidates ─┬─ age (birth_date + источник + статус)
                      ├─ representations ── legal_representatives, authority_checks
                      ├─ consent_events ── legal_documents ── pd_operators
                      ├─ source_facts ─┬─ claims ── skill_inferences ── categorization_runs ─┬─ category_assignments
                      │                │     └─ experience_entries                          ├─ fsp_level_assignments
                      │                │                                                    └─ category_disputes
                      │                ├─ verification_receipts (публичный `handle` — колонка, отдельной таблицы нет)
                      │                ├─ assessment_attempts ─┬─ assessment_scores (источник «тест»)
                      │                │                       └─ assessment_artifacts
                      │                └─ resume_documents ── files, document_extractions
                      ├─ embeddings (embedding_spaces)
                      ├─ match_scores ── vacancies
                      ├─ invitations ─┬─ invitation_terms ── invitation_responses ── disclosures
                      │               └─ hiring_processes ── hiring_reports
                      └─ candidate_company_blocks
vacancies ─┬─ companies (origin = own; claimed_company_id у внешних)
           ├─ vacancy_postings ── vacancy_sources, vacancy_import_runs
           └─ vacancy_claims
jobs, ml_results, audit_events, inbound_events, erasure_ledger, eval_runs, product_policies, market_snapshots
taxonomy_versions ── roles, skills, skill_aliases, grades, work_formats, fsp_projection_rules, fsp_strength_params,
                     fsp_level_rules, categorization_rulesets, match_rulesets, salary_references
```

Владелец записи — модуль, который единственный пишет в таблицу. Остальные модули читают через его функции.

| Агрегат | Модуль-владелец | Кто видит (кроме владельца-модуля) |
|---|---|---|
| Пользователь, сессии, идентичности | `auth` | сам пользователь; администратор — статус и роли, без секретов |
| Роли персонала, права | `access` | администратор |
| Компании, членство | `companies` | члены компании; оператор ФСП |
| Документы, согласия, представители, раскрытия | `consent` | субъект; оператор ФСП — по делу; работодатель — только свои раскрытия |
| Кандидат, возраст | `candidates` | через проекции (раздел 14) |
| Факты, утверждения, выводы, группы опыта, квитанции | `evidence` | через проекции; квитанции — публичная проверка без личности (9.6) |
| Тесты | `assessments` | кандидат; оператор ФСП — по делу о пересмотре |
| Таксономия | `taxonomy` | все (справочник) |
| Категоризация, возражения | `categorization` | через проекции; оператор ФСП — дела по возражениям |
| Внешние вакансии, публикации, импорт, заявки «это наша вакансия» | `sourcing` | все пользователи — вакансии и публикации (без ПДн); заявки — заявитель и оператор ФСП |
| Соответствие вакансия ↔ кандидат | `matching` | компания — по своим вакансиям через проекции; кандидат — своё соответствие |
| Вакансии компаний, приглашения, условия, ответы, процессы найма | `hiring` | компания-отправитель и адресат-кандидат; оператор ФСП — агрегаты воронки |
| Уведомления и каналы | `notifications` | адресат |
| Рынок категории | `market` | члены проверенных компаний; кандидат — рынок своей категории |
| Партнёрства соревнований | `companies` | компания-партнёр; оператор ФСП |
| Файлы, резюме, извлечения | `documents` | владелец файла; получатель — по раскрытию |
| ML-результаты, векторы | `ml` | внутренний |
| Задания | `jobs` | администратор — очередь и ошибки |
| Журнал | `audit` | администратор по роли; оператор ФСП — по выданному праву `audit.read` |

## 3. Пользователь, вход и внешние идентичности

Вход двух видов: собственный (почта и пароль) и через ФСП ID (OIDC, контракт — `contracts.md`, раздел 2). Регистрация, согласия, дата
рождения и выбор роли проходят одним потоком в приложении (раздел 3.6).

### 3.1. `users`

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | `user_id`, первичный ключ |
| `status` | `enum` | да | `pending_email` · `active` · `suspended` · `deletion_pending` · `deleted` |
| `email_enc` | `enc` | усл. | адрес почты; `NULL` только у `deleted` |
| `email_hmac` | `hmac` | усл. | уникальный индекс для входа и проверки занятости адреса |
| `email_verified_at` | `ts` | нет | момент подтверждения адреса по ссылке из письма |
| `display_name` | `text` | нет | имя для интерфейса; ФИО кандидата хранится в `candidates` |
| `locked_until` | `ts` | нет | блокировка входа после серии неудачных попыток |
| `last_login_at` | `ts` | нет | для политики неактивности |
| `deletion_requested_at` | `ts` | нет | запрос удаления аккаунта |
| `deleted_at` | `ts` | нет | момент очистки; строка остаётся как надгробие без ПДн |
| `seed_batch_id` | `text` | нет | учётка создана сидом демо-данных (или клон демо-учётки); `NULL` — настоящая |
| `demo_session_id` | `ref demo_sessions` | нет | клон демо-учётки в демо-сессии (19.3): удаляется вместе с сессией |

**Инварианты.**
- Почта уникальна по `email_hmac` среди не удалённых пользователей.
- Почта, полученная от внешнего провайдера, не считается подтверждённой для нашей платформы: подтверждение — только по нашей ссылке.
- Надгробие `deleted` хранит только `id`, `status`, `deleted_at`: на него ссылаются журнал и раскрытия, связь с человеком разорвана.

**Переходы.**

```
pending_email ──(подтвердил адрес)──▶ active
active ──(администратор)──▶ suspended ──(администратор)──▶ active
active | pending_email | suspended ──(запрос удаления)──▶ deletion_pending ──(задание очистки)──▶ deleted
```

`deletion_pending` немедленно отзывает все сессии и ключи API и скрывает кандидата отовсюду (раздел 19).

### 3.2. `password_credentials`

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `user_id` | `id` | да | PK и FK на `users` |
| `hash` | `text` | да | строка Argon2id (PHC) с параметрами внутри; минимум `m=19456, t=2, p=1` |
| `changed_at` | `ts` | да | смена пароля отзывает остальные сессии |

Пользователь, вошедший только через ФСП ID, может не иметь пароля. При входе хэш с устаревшими параметрами пересчитывается.

### 3.3. `email_tokens`

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `purpose` | `enum` | да | `verify_email` · `reset_password` · `member_invite` · `representative_invite` · `representative_consent` · `representative_disclosure` |
| `token_hash` | `hash` | да | в письме — только исходный токен (32 байта случайных) |
| `user_id` | `id` | нет | для `verify_email`, `reset_password` |
| `target_ref` | `id` | нет | для приглашений: `company_members.id` или `representations.id`; для `representative_consent` — `representations.id` (одна ссылка и подписывает, и отзывает), для `representative_disclosure` — `invitation_terms.id` (версия, которую принял кандидат) |

ссылке (устаревшая редакция текста, закрытый запрос) откатывает и её использование — ссылка остаётся рабочей до срока.

### 3.4. Сессии и попытки входа (Redis)

| Ключ | Значение | TTL |
|---|---|---|
| `session:{sha256(session_id)}` | `user_id`, `created_at`, `auth_time`, `auth_method` (`password` / `fsp_id`), `ip`, `ua` | простой 7 дней, абсолютный 30 дней |
| `user_sessions:{user_id}` | множество хэшей сессий | для отзыва всех сессий |
| `login_fail:acct:{email_hmac}` / `login_fail:ip:{ip}` | счётчики | окно блокировки |

**Инварианты.** Идентификатор сессии ротируется при входе и смене привилегий. Для чувствительных операций (привязка и отвязка ФСП ID,
смена пароля, создание ключа API, удаление аккаунта) требуется свежая аутентификация: `auth_time` не старше 10 минут. Права не кешируются
в сессии: членство и статус компании проверяются на каждом запросе (раздел 4).

### 3.5. `external_identities` и `athlete_links`

**`external_identities`** — кто вошёл через внешнего провайдера.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `user_id` | `id` | да | владелец связи |
| `issuer` | `text` | да | точное значение `iss`, например `https://sso.fsp-russia.ru/realms/fsp` |
| `subject` | `ext_id` | да | `sub` из ID-токена |
| `linked_at` | `ts` | да | |
| `link_method` | `enum` | да | `signup_via_provider` · `linked_by_user` |
| `last_login_at` | `ts` | нет | |
| `profile_claims` | `jsonb` | нет | `name`, `given_name`, `family_name`, `preferred_username` на момент последнего входа — только для подстановки в форму |

**`athlete_links`** — чьи достижения импортируются.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `user_id` | `id` | да | |
| `source` | `enum` | да | `fsp` (расширяемо: другие федерации, платформы соревнований) |
| `source_athlete_id` | `ext_id` | да | ID спортсмена в API источника |
| `basis_identity_id` | `id` | усл. | внешняя идентичность, на основании которой установлена связь; обязательна у `active`. **Реализация:** `NULL` после отвязки — идентичность удаляется (`contracts.md` 2.5), связь остаётся `unlinked` |
| `resolution_method` | `enum` | да | `subject_equals_athlete_id` (мок) · `resolved_by_source_api` · `operator_confirmed` — **ТЗ-зависимо** |
| `status` | `enum` | да | `active` · `unlinked` |
| `linked_at`, `unlinked_at` | `ts` | да / нет | |
| `demo_session_id` | `ref demo_sessions` | нет | связь в демо-сессии (19.3) — клона участника сценария или учётки, заведённой в сессии: действует внутри сессии; вебхуки и пакеты результатов ФСП её не обновляют, клон не синхронизируется, учётка сессии синхронизируется по своему согласию |

**Инварианты.**
- `UNIQUE (issuer, subject)` — одна внешняя идентичность принадлежит одному пользователю. Одинаковый `sub` у двух разных `issuer` — это
  две разные идентичности.
- `UNIQUE (source, source_athlete_id) WHERE status = 'active' AND demo_session_id IS NULL` — один спортсмен связан максимум с одним
  пользователем. Внутри демо-сессии — свой такой же индекс по `(source, source_athlete_id, demo_session_id)`: клон героя-спортсмена
  связан со спортсменом только в своей сессии и правило вне сессий не ослабляет (19.3).
- **Автосвязка по email запрещена.** Совпадение почты внешнего аккаунта с почтой локального не создаёт связь и не даёт входа в локальный
  аккаунт. Связь создаётся только при входе через провайдера нового пользователя или по действию уже вошедшего пользователя
  с подтверждением обеих сторон (контракт — `contracts.md`, раздел 2.4).
- ID спортсмена не равен `subject` по определению: в моке они совпадают (`resolution_method = subject_equals_athlete_id`), в реальном API
  способ сопоставления станет известен из спецификации ФСП.
- Отвязка идентичности переводит зависящие от неё `athlete_links` в `unlinked`; импортированные по ним факты выводятся из профиля
  (раздел 19).

### 3.6. Поток регистрации

Один поток приложения, одинаковый для входа паролем и через ФСП ID:

1. Учётные данные: почта и пароль **или** возврат от ФСП ID (создаётся `external_identity`, `link_method = signup_via_provider`).
2. Подтверждение почты по ссылке (`pending_email → active`).
3. Выбор роли: кандидат или работодатель (роли персонала выдаёт администратор).
4. Кандидат: дата рождения (ФСП ID её не передаёт — в `claims_supported` реального discovery нет `birthdate`) → пользовательское
   соглашение → согласие на обработку профиля (отдельный экран) → при 14–17 годах приглашение представителя → при возрасте меньше 14 лет
   отказ в профиле соискателя с сохранением учётной записи и внешней идентичности (раздел 7.3).
5. Работодатель: пользовательское соглашение → ИНН компании → заявка на проверку (раздел 5). До проверки компании каталог недоступен.

раздел 8.

**`notification_channels`**

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `user_id` | `id` | да | |
| `kind` | `enum` | да | `email` · `telegram` |
| `telegram_chat_id_enc` | `enc` | усл. | для `telegram` в статусе `active`; адрес почты берётся из `users.email_enc`, отдельно не хранится |
| `telegram_chat_hmac` | `hmac` | усл. | `UNIQUE` среди `active`: один чат — один пользователь |
| `status` | `enum` | да | `active` · `unlinked` · `blocked_by_user` (бот заблокирован в Telegram) |

**`telegram_link_tokens`**: `token_hash hash`, `user_id id`, `expires_at ts` (10 минут), `used_at ts`. Привязка — только переходом по

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `user_id` | `id` | да | адресат |
| `type` | `text` | да | из реестра типов (`invitation.received`, `invitation.terms_revised`, `invitation.answered`, `invitation.representative_answered`, `invitation.expired`, `invitation.withdrawn`, `invitation.response_due_soon`, `hiring.outcome_requested`, `hiring.outcome_reminder`, `hiring.reports_diverged`, `company.verification_decided`, `vacancy.moderation_decided`, `dispute.decided`, `representation.decided`, `representation.consents_signed`, `representation.consents_revoked`, `candidate.age_verified`, `assessment.annulled`, …) |

| `read_at` | `ts` | нет | |

**`notification_deliveries`**: `id`, `notification_id`, `channel_id`, `status enum(queued|sent|failed|skipped)`, `skip_reason

**Инварианты.**
- Доставка — задание `notification.deliver` на каждую пару «уведомление × канал». Перед отправкой проверяются канал, настройка, для
  `telegram` — `effectiveConsent(telegram_notifications)`, и доступ адресата к объекту **на момент отправки**: отозванное приглашение,
  отозванное раскрытие или закрытая карточка дают `skipped (object_not_visible)`, а не письмо о несуществующем.
- Telegram — иностранный сервис: сообщение содержит только вид события и ссылку в продукт, без имён, названий компаний, вакансий и сумм.
  Письмо адресату может содержать его собственные данные (компания и вакансия приглашения — кандидату), но не ПДн другой стороны:
  работодателю кандидат называется псевдонимом.
- Напоминания — отдельные типы с `dedup_key` по этапу; их расписание — параметры `notification_policy` (срок до окончания ответа,
  интервалы запроса исхода найма, максимум повторов). **ТЗ-зависимо.**
- Отзыв `telegram_notifications`, команда боту «стоп» или ответ Bot API «бот заблокирован» → канал `unlinked` / `blocked_by_user`,
  `telegram_chat_id_enc` и `telegram_chat_hmac` стираются в той же транзакции; уведомления продолжают приходить в интерфейс и на почту.
- Уведомления о решении оператора (`company.verification_decided`, `vacancy.moderation_decided`, `dispute.decided`,
  `representation.decided`) называют только исход; причину адресат читает в продукте (профиль компании, страница вакансии). О решении
  модерации по вакансии узнают автор вакансии и владельцы компании — активные члены, по уведомлению на дело.
  У законного представителя нет учётной записи: при решении по его полномочиям уведомляется кандидат, а не представитель, и только тем,
  подтверждены ли полномочия, — без заметок оператора и деталей документа.
- **Письма законному представителю** — не уведомления: у него нет учётной записи и каналов. Письмо с одноразовой ссылкой
  (`email_tokens`, раздел 3.3) уходит сразу после фиксации транзакции, которая его вызвала, и пишет в журнал
  `representation.letter_sent` с исходом отправки. Неушедшее письмо не повторяется само: кандидат запрашивает его снова (раздел 6.4).
  Письмо называет подопечного, а о раскрытии — компанию, вакансию, вилку и раскрываемые поля: это данные самого подопечного,
  о которых представитель решает. Решение представителя кандидату — `representation.consents_signed`,
  `representation.consents_revoked` и `invitation.representative_answered`; компании — `invitation.answered` с признаком
  `by_representative`. Отзыв представителем согласия на обработку удаляет профиль (раздел 19.1): кандидату уходит письмо прямо
  через почту, как при удалении, — уведомление с отложенной доставкой не дожило бы до очистки.
- **Уведомления кандидату о решениях оператора по его профилю** — категория `account`, называют исход, `payload` — коды:
  `candidate.age_verified` (объект `candidate`, `{ regime: adult | minor, hidden }`) — дата рождения проверена по документу
  (раздел 7.2): письмо называет режим и то, что профиль подростка без подтверждённого представителя скрыт, — без даты и вида
  документа; ведёт на страницу согласий. `assessment.annulled` (объект `assessment_attempt`, `{ attempt_id, reason }`) — попытка
  аннулирована (раздел 10.2): письмо называет тест и засчитывается ли попытка в лимит (не засчитываются `technical_failure` и
  `version_defect`), без оснований оператора; ведёт на страницу попытки. `representation.consents_revoked` (объект
  `representation`, `{ representation_id, catalog_visibility, fsp_import }`) — какие согласия отозвал представитель и что это
  сразу значит; ведёт на страницу согласий.

## 4. Роли и объектные права

### 4.1. Роли

| Роль | Где хранится | Как получается | Что даёт |
|---|---|---|---|
| Кандидат | существование строки `candidates` со статусом `active` | путь регистрации | свой профиль, приглашения к себе, свои согласия |
| Владелец компании | `company_members.role = owner` | создатель заявки; полномочия проверяются при проверке компании | вакансии, приглашения, приглашение рекрутеров, ключи API компании |
| Рекрутер | `company_members.role = recruiter` | приглашение владельца, принятое по ссылке | каталог, вакансии, приглашения компании |
| Оператор ФСП | `staff_roles.role = operator` | выдаёт администратор | модерация компаний и собственных вакансий, возражений, полномочий представителей, конфликты даты рождения, пересмотр и аннулирование попыток тестов, импорт результатов ФСП (выгрузки и протоколы); `audit.read` — только если администратор выдал его отдельно |
| Администратор | `staff_roles.role = admin` | начальная учётка из окружения; далее — другой администратор | роли персонала, справочники, очередь заданий, журнал действий (`audit.read` по роли); **без** доступа к данным кандидатов по умолчанию |
| Законный представитель | не роль и не учётка | `representations` (раздел 6.4) | подписание согласий за подопечного по ссылке с токеном |
| Партнёр соревнования | не роль пользователя, а статус компании | `competition_partnerships` (раздел 5.5), открывает оператор ФСП | членам компании — пул финалистов этого соревнования по согласию кандидатов |

Роль «аудитор» отдельно не заводится: это право `audit.read` — у администратора оно по роли, оператору ФСП выдаётся отдельно. **ТЗ-зависимо:** набор ролей и возможность
совмещать роли кандидата и работодателя в одной учётке (в MVP запрещено политикой, не схемой).

**`staff_roles`**: `user_id id`, `role enum(operator|admin)`, `granted_by id`, `granted_at ts`, `revoked_at ts` — append-only по смыслу,
активна запись без `revoked_at`. **Реализация:** право `audit.read` хранится в `extra_permissions text[]` строки оператора
(у других ролей пусто), отзыв — `revoked_at` и `revoked_by`.

### 4.2. Права

Права — строки реестра (`resource.action`). Проверка — функция `can(actor, permission, object?)`, которая сочетает роль с объектным
правилом. Роль сама по себе доступа к объекту не даёт.

**Переходы.**

```
draft ──(заявка)──▶ submitted ──(оператор: подтвердил)──▶ verified ──(оператор)──▶ suspended ──(оператор)──▶ verified
                         ├──(оператор: отказал)──▶ rejected ──(повторная заявка)──▶ submitted
                         └──(оператор: запросил уточнение)──▶ draft ──(повторная заявка)──▶ submitted
```

`suspended` и `rejected` немедленно закрывают каталог, приглашения, пулы партнёра и ключи API компании; отправленные и не принятые
приглашения переходят в `withdrawn`. Идущие процессы найма (раздел 13.7) не закрываются: кандидат по-прежнему сообщает исход.

Компания может появиться из заявки «это наша вакансия» (раздел 13.3): заявка создаёт или находит компанию по ИНН в статусе `draft`
и ведёт заявителя в общий путь проверки. Импорт вакансии компанию не создаёт и статус ей не меняет.

**Производное состояние** `effectiveConsent(candidate, kind, scope, at)` — истина, если одновременно:
1. последнее событие по `(subject, kind, scope)` от субъекта — `grant` и после него нет `revoke`/`lapse`;
2. документ этого `grant` не вытеснен версией с `requires_reconsent`;
3. для кандидата 14–17 лет на момент `at` — дополнительно действует `grant` того же вида и области от представителя, у которого
   `representations.status = authority_verified` на момент `at`;
4. для кандидата 18+ — `grant` подписан самим субъектом **после** совершеннолетия (согласия времён несовершеннолетия утрачивают силу
   событием `lapse`).

**Инварианты.**
- Подписант и субъект — разные ссылки. `signer_user_id` может совпадать с пользователем кандидата, `representation_id` — никогда.
- Отзыв возможен в любой момент и субъектом, и действующим представителем несовершеннолетнего. Отзыв одним из них прекращает действие.
- Области независимы: отзыв `catalog_visibility` не трогает профиль и импорт; выдача `fsp_import` не показывает профиль работодателям;
  `contact_disclosure` по приглашению компании A не даёт ничего компании B.
- Обычная отметка на экране не считается письменным согласием по ст. 16: для вида с `form = electronic_signature` событие без
  подписи в `evidence` отвергается.

**Состав карточки каталога по выбору кандидата.** Базовый состав каталога — обобщённый (раздел 14). Кандидат 18+ может добавить к нему
значения `scope_fields` согласия `catalog_visibility`:

| Значение | Что добавляет в проекцию `catalog` |
|---|---|
| `fsp_achievements_exact` | точные достижения ФСП: соревнование, этап, место, команда, ссылка на протокол; квитанции — на уровне точного факта |
| `external_profiles` | ссылки на подтверждённые профили Codeforces и GitHub (только `ownership_status = verified`) |

Решение — `scope_fields`, а не отдельный вид согласия: цель, получатели (проверенные работодатели) и основание те же, меняется только
перечень данных, а перечень данных и есть содержание согласия (п. 4 ч. 4 ст. 9). Изменение состава — новое событие `grant` с новым
`scope_fields`: расширение и сужение журналируются так же, как выдача, а сужение действует немедленно. Для кандидата 14–17 лет событие
с непустым `scope_fields` отвергается валидацией — режим подростков не меняется. При совершеннолетии выбор заново делает сам кандидат
(событие `lapse`, раздел 7.3).

**Инварианты.**

- Согласие, подписанное представителем, учитывается только пока его связь в `authority_verified` (раздел 6.3, п. 3). Окончание связи

**Подписи представителя без кабинета.** Представитель действует только по одноразовым ссылкам из писем (разделы 3.3, 3.7);
ссылка работает, пока связь в `authority_verified`, кандидату 14–17 лет и его профиль `active`.

1. **Согласия профиля.** Сразу после `authority_verified` представителю уходит письмо `representative_consent` (7 суток). Страница
   ссылки показывает тексты `pd_processing` (обязательно, если ещё не подписано), `catalog_visibility` и `fsp_import` (по желанию)
   с раздельными отметками и тем, дал ли своё согласие кандидат. Подпись — `grant` связи на каждую отмеченную редакцию
   (`method = email_link`); устаревшая редакция отвергает всю подпись, ссылка остаётся рабочей. После подписи: изменение профиля
   (`profile_revision + 1`, пересчёт категории при `pd_processing`), при действующем с обеих сторон `fsp_import` — `fsp.sync` по
   активным связям со спортсменом, кандидату — `representation.consents_signed`. Кандидат видит по каждому виду свою сторону
   и сторону представителя («получено» / «ожидается», страница «Согласия») и запрашивает письмо снова — не чаще раза в 5 минут;
   новое письмо отзывает ссылку прежнего.
2. **Отзыв согласий.** Та же страница ссылки (`/representative/consent`) показывает у подписанных представителем согласий отметку
   «Отозвать»; отзыв идёт в два шага — страница называет последствия каждого вида, представитель подтверждает. Подтверждение —
   `revoke` связи на каждый вид, чья подпись представителя сейчас действует (`method = email_link`, `evidence` — адрес, браузер,
   `email_token_id`), `consent.revoked` с `representation_id`; согласие прекращается для обеих сторон (раздел 6.3) и снова
   действует, только когда его подпишут и кандидат, и представитель. Последствия — те же, что у отзыва кандидатом (раздел 19.1),
   в той же транзакции: `catalog_visibility` — `visibility = hidden` и изменение профиля (пересчёт соответствий и счётчиков);
   `fsp_import` — связи со спортсменом `unlinked`, факты `fsp` → `withdrawn`, `consent.revocation_cleanup`; `pd_processing` —
   удаление учётной записи подопечного (`account.deletion_requested`, причина `processing_revoked`, актор — аноним по ссылке):
   профиль → `deletion_pending`, связь → `ended (candidate_deleted)`, сессии кандидата отзываются, кандидату — письмо об удалении.
   Иначе кандидату — `representation.consents_revoked`. Ссылка срабатывает один раз; вид без действующей подписи пропускается,
   а если отзывать нечего — отказ `not_signed` без записей, ссылка остаётся рабочей (повтор ничего не пишет).
3. **Письмо после изменения.** После подписи и после отзыва (кроме удаления) представителю уходит письмо «Согласия законного
   представителя изменены»: что сейчас подписано с его стороны и новая ссылка `representative_consent` (7 суток), по которой
   подписывают недостающее и отзывают данное. Письмо — тот же путь, что остальные (`representation.letter_sent`, вид `consents`;
   для кандидата демо-сессии письмо сохраняется в «Письмах сессии», раздел 19.3).
4. **Письмо по запросу представителя.** Страница `/representative/letter` принимает адрес: каждой связи в `authority_verified`
   с этим адресом (`legal_representatives.email_hmac`) уходит новое письмо со ссылкой — не чаще раза в 5 минут на связь, ответ
   одинаков для любого адреса. Так отзыв доступен в любой момент, не дожидаясь кандидата.
5. **Раскрытие по приглашению** — раздел 13.6.

### 7.2. Возраст

Возраст хранится как дата рождения с источником и статусом проверки и **вычисляется на момент запроса**, а не хранится флагом:
переход через день рождения меняет режим без пересчёта данных.

`ageBand(candidate, at) → unknown | under_14 | 14 | 15 | 16 | 17 | adult`

- `birth_date_status ∈ {unknown, conflict}` → `unknown`.
- Точность `year` даёт диапазон возможных возрастов; если диапазон пересекает границу 14, 15, 16 или 18 лет → `unknown`.
- Иначе — полных лет на дату `at`.

`is_minor` для работодателя — `ageBand ∈ {14, 15, 16, 17}`. Дата рождения и возраст в годах работодателю не показываются никогда.

**Источники и конфликты.** Самостоятельно указанная дата принимается со статусом `unverified`. Если год рождения из ФСП не согласуется
с указанной датой, статус становится `conflict` (режим `unknown`, профиль закрыт) до решения оператора по документу. Оператор ставит
`verified` с `birth_date_source = operator_document`.

**Реализация** (`src/lib/server/operator/ages.ts`, кабинет `/operator/ages`, право `age.review`). Очередь — активные профили в
`conflict`, старые первыми (момент открытия — последнее `age.conflict` журнала); в списке нет ни дат, ни имён. Дело показывает ФИО и
почту (чтобы договориться о проверке и сверить документ), указанную дату с источником, ID спортсмена ФСП, чья запись дала расходящийся
год, и представителя подростка, если он есть; открытие дела — `operator.case_access` (`case_type = age`). Год рождения из ФСП платформа
не хранит — только признак расхождения. Решение: дата рождения из документа (точность `day`), способ проверки (`document_presented` —
документ на встрече или видеозвонке, `in_person` — личный визит) и вид документа (`passport` · `birth_certificate` ·
`international_passport` · `foreign_identity_document`) без номера и реквизитов; копия документа не хранится, решение без неё
действительно, как проверка полномочий представителя без копии (6.4). В одной транзакции: дата → `verified` с `birth_date_verified_by/at`,
`profile_revision + 1` с пересчётом соответствий (`match.refresh`), событие `age.verified` — способ, вид документа, совпала ли дата с
указанной, режим (`adult` · `minor`), без самой даты. Последствия следуют из режима сразу, потому что возраст вычисляется на момент
запроса (7.2, 7.3):
- `adult` — взрослый режим; согласия, подписанные, пока указанная дата делала человека несовершеннолетним, не действуют по правилу 4
  `effectiveConsent`, а их `lapse` и завершение связи с представителем записывает ежедневное задание совершеннолетия (7.3);
- `minor` (14–17) — защищённый режим: согласия нужны и от представителя с `authority_verified`; без такого представителя профиль
  снимается с показа в каталоге (`visibility = hidden`);
- возраст, в котором профиль вести нельзя (младше 14 лет, 14–17 при `minor_policy.enabled = false`), — отказ `409 ineligible_age`,
  ничего не меняется: действующий профиль не переходит в `ineligible_age` (переход есть только из `onboarding`), конфликт остаётся
  открытым, профиль — закрытым. Как закрывать такой профиль (удаление с сохранением учётной записи до 14 лет) — открытый вопрос.

Решённый конфликт повторно не решается (`409 not_in_conflict`). Уведомления кандидату о решении нет: для него нужен отдельный тип
уведомления.

| `ageBand` | Профиль соискателя | Видимость работодателям | Публичная страница | Согласия |
|---|---|---|---|---|
| `unknown` | закрыт | нет | нет | — |
| `under_14` | отказ: `ineligible_age`, учётная запись и внешние идентичности сохраняются, дата рождения заменяется на `eligible_from` | нет | нет | не собираются |
| 14–17 | создаётся, `visibility` принудительно `hidden` до подтверждения представителя | только в контексте конкретной активной вакансии с `min_age ≤ возраст`, компания приняла `minor_employment_terms` | недоступна | субъект **и** представитель с `authority_verified` |

**Совершеннолетие.** Задание `candidate.majority_transition` в день 18-летия: события `lapse` по согласиям, подписанным во время

Публичная страница автоматически не включается.

**Реализация.** Согласия времён несовершеннолетия перестают действовать по правилу 4 `effectiveConsent` и без задания.
Задание делает это видимым: ежедневное расписание воркера ставит его один раз в сутки каждому взрослому (с точностью «год» —
после 19-го года), у кого не завершена связь с представителем или последнее событие какого-либо согласия — `grant` времён
несовершеннолетия; задание пишет `lapse` (`signer_kind = system`, причина `majority`) по каждому такому согласию — и кандидата, и
представителя, — завершает связь (`majority`), скрывает профиль и уведомляет кандидата (`candidate.majority_reached`, ссылка — на
страницу «Согласия»). Согласие, подписанное взрослым после 18 лет, не трогается. Повторное
согласие — страница «Согласия» кабинета: кандидат с профилем `active`, чья собственная сторона `pd_processing` не действует
(подписана до 18 лет или вытеснена редакцией с `requires_reconsent`), подписывает текущую редакцию сам; профиль остаётся `active`,
его обработка возобновляется (`profile_revision + 1`, пересчёт категории). Показ в каталоге взрослый включает заново на странице
видимости (`catalog_visibility`). Отказы шагов, ждущих представителя, у подростка везде называются кодом
`representative_consent_required` и объясняют, чего не хватает: указать представителя, дождаться проверки оператора или подписи
по письму.

**ТЗ-зависимо:** если ТЗ исключит несовершеннолетних, политика `minor_policy.enabled = false` переводит 14–17 в тот же режим, что
`under_14`. Таблицы не меняются.

### 7.4. `canShow(candidate, viewer, context)`

Единственная функция, решающая, видит ли зритель кандидата и в какой проекции. Запросы каталога, карточки, API, выгрузки и счётчиков
вызывают её (или её SQL-предикат, сгенерированный из того же описания правил), а не повторяют условия.

**Входы.**

```ts
type Viewer =
  | { kind: 'anonymous' }
  | { kind: 'user'; userId: string }                       // кандидат смотрит себя
  | { kind: 'member'; userId: string; memberId: string; companyId: string; via: 'session' | 'api_key' }
  | { kind: 'staff'; userId: string; role: 'operator' | 'admin' };

type ViewContext =
  | { kind: 'self' }
  | { kind: 'catalog'; vacancyId?: string }                // поиск; для 14–17 лет vacancyId обязателен
  | { kind: 'invitation'; invitationId: string }           // карточка в рамках приглашения
  | { kind: 'partner_pool'; partnershipId: string }        // пул финалистов соревнования партнёра
  | { kind: 'public' }                                     // публичная страница
  | { kind: 'case'; caseType: 'dispute' | 'moderation' | 'authority' | 'assessment'; caseId: string };

type ShowDecision =
  | {
      allowed: true;
      projection: 'self' | 'catalog' | 'recipient' | 'public' | 'operator';
      extras: ('fsp_achievements_exact' | 'external_profiles' | 'partner_competition_result')[]; // сверх базового состава
      policyVersion: string;
    }
  | { allowed: false; reason: DenyReason };
```

Функция читает **текущее** состояние (момент `now`): статус кандидата, `ageBand`, `effectiveConsent`, `representations`, статус компании
и членства, вакансию, приглашение, блок-лист, версию `product_policy`.

**Правила** (первое сработавшее запрещающее правило даёт отказ с причиной):

1. `self`: зритель — пользователь кандидата → `self`. Иначе отказ.
2. `case`: зритель — персонал с правом на этот тип дела, дело существует и относится к кандидату → `operator`, событие
   `operator.case_access`. Иначе отказ.
3. Кандидат не `active` → `candidate_inactive`.
4. Нет `effectiveConsent(pd_processing)` → `no_processing_consent`.
5. `ageBand = unknown` → `age_unknown`; `under_14` → `age_ineligible`.
6. `public`: зритель любой; `ageBand = adult`, `public_distribution.available`, действует `effectiveConsent(public_distribution)` →
   `public` (поля — из `scope_fields`). Иначе отказ.
7. Зритель — член компании: членство `active`, компания `verified`, право `candidate.card.read`; компания не в блок-листе кандидата.
   Иначе отказ.
8. `invitation`: приглашение этой компании этому кандидату; если оно `accepted` и действует `contact_disclosure` с областью этого
   приглашения → `recipient`. Если приглашение не принято или согласие отозвано — переход к правилу 9 с `vacancyId` приглашения.
9. `catalog`:
   - `visibility = catalog`, `search_status ≠ not_looking`, действует `effectiveConsent(catalog_visibility)`;
   - 14–17 лет: `vacancyId` задан; вакансия принадлежит компании зрителя, `status = published`, `min_age` не `NULL`
     и `≤ ageBand`; компания приняла `minor_employment_terms`; представитель в `authority_verified`;
   → `catalog`; `extras` — из `scope_fields` действующего `catalog_visibility` (только `adult`).
10. `partner_pool`: партнёрство этой компании `active`; кандидат входит в пул по правилам раздела 5.5 → `catalog` с `extras` из
    `scope_fields` и `partner_competition_result` (точный результат именно этого соревнования). Настройка `visibility` на пул не влияет:
    согласие `partner_pool` — самостоятельное основание.
11. Иначе → `not_visible`.

`DenyReason`: `candidate_inactive`, `no_processing_consent`, `age_unknown`, `age_ineligible`, `not_member`, `company_not_verified`,
`blocked_by_candidate`, `no_catalog_consent`, `hidden_by_candidate`, `minor_requires_vacancy`, `vacancy_not_eligible`,
`representative_not_verified`, `no_disclosure_consent`, `not_partner`, `not_in_pool`, `no_case_access`, `not_visible`. Внешним
зрителям причина не раскрывается: API отвечает `404 not_found` (`contracts.md` 5.3), причина пишется в журнал.

**Счётчики и рынок категории** строятся только по кандидатам, для которых `canShow(…, catalog)` истинна для данного зрителя, и
показываются с порогом: значения меньше 5 выводятся как «< 5».

**Счётчик «в пуле N подтверждённых кандидатов»** у внешней вакансии (раздел 13.3) виден зрителю без компании, поэтому считается
предикатом `catalogVisibleToAnyVerifiedCompany(candidate)` — правило 9 без условий конкретной компании: `visibility = catalog`,
`search_status ≠ not_looking`, действует `catalog_visibility`, `ageBand = adult`. Подростки в этот счётчик не входят никогда. Блок-листы
кандидатов на обезличенное число не влияют. Порог «< 5» тот же.

## 8. Запрещённые поля

**Инвариант схемы.** В таблицах кандидата, фактов, утверждений, вакансий, в схемах API и в схеме извлечения резюме нет полей:
пол, гражданство, национальность, раса, язык как признак происхождения, религия, убеждения, политические взгляды, членство в общественных
объединениях, семейное положение, наличие детей, состояние здоровья и инвалидность, фотография, место рождения, место регистрации
(«прописка»), паспортные данные, СНИЛС, ИНН физического лица, возраст в годах в выдаче работодателю.

Основания: ч. 3 ст. 53 565-ФЗ, ст. 3 и 64 ТК (дискриминация), ст. 10–11 152-ФЗ (специальные категории и биометрия), ч. 5 ст. 5
(минимизация).

**Как соблюдается.**
- Тест схемы: список колонок перечисленных таблиц и свойств схем API и извлечения сверяется со словарём запрещённых имён и синонимов
  (`gender`, `sex`, `citizenship`, `nationality`, `marital_status`, `children`, `religion`, `photo`, `birth_place`, …).
- Разбор резюме такие сведения не извлекает: в схеме `extract` их нет. Исходный текст резюме остаётся у кандидата и получателя по
  раскрытию, в каталог не попадает.
- У работодателя нет фильтров по этим признакам и по возрасту. Единственный возрастной признак — `is_minor` (гл. 42 ТК — ограничение,
  предусмотренное федеральным законом).
- Текст вакансии проверяется валидатором дискриминационных формулировок (раздел 13.1).

Три слоя разделяют «источник сообщил», «из этого следует утверждение» и «мы делаем вывод о навыке». Доверие — свойство факта; вывод
его не наследует автоматически.

**Уровень доверия** определяется источником **и** способом привязки: результат ФСП по действующей связи со спортсменом —
`fsp_verified`; строка PDF-протокола, которую кандидат назвал своей (`protocol_self_claim`), — `claimed` («есть в протоколе,
принадлежность не подтверждена»), после подтверждения оператором ФСП (`operator_confirmed`) — `fsp_verified`; профиль Codeforces без
подтверждения владения — `claimed`, с подтверждением — `public_verifiable`.

**Три разных вида сведений ФСП**, которые не подменяют друг друга:

| Вид | Где | Что утверждает | Как показывается |
|---|---|---|---|
| Присвоенный разряд или звание | факт `qualification` (приказ о присвоении) | человек имеет разряд | «КМС, присвоен {дата}» |
| Результат соревнования | факт `competition_result` | место в конкретном соревновании | «2 место, Чемпионат России 2025» |
| Расчётный показатель | вклад вывода (`computed_indicator`), не факт | результат соответствует нормам разряда по версии ЕВСК | «результат соответствует нормам КМС (ЕВСК, ред. …)» — никогда «КМС» |

**Переходы.** `active → superseded` (источник прислал новую версию записи), `active → withdrawn` (отзыв согласия, отвязка, удаление
документа), `active → annulled` (источник аннулировал результат, попытка теста аннулирована). Любой переход увеличивает
`candidates.profile_revision` и ставит задание пересчёта.

**Инварианты.**
- Утверждение из документа без цитаты не сохраняется. Цитата должна дословно (после нормализации пробелов) находиться в блоке
  `block_id` извлечения `extraction_id` по смещениям `start..end` **и** поддерживать утверждение: для `skill_mention` — содержать алиас
  навыка, для `experience_period` — даты. Одного вхождения подстроки где-то в документе недостаточно.

### 9.3. `skill_inferences` (слой 3)

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `run_id` | `id` | да | расчёт категоризации, в котором получен вывод |
| `candidate_id` | `id` | да | |
| `skill_key` | `text` | да | в таксономии версии расчёта |
| `strength` | `numeric(4,3)` | да | 0…1, сила оснований по формуле ниже; не вероятность |
| `strength_band` | `enum` | да | `weak` · `moderate` · `strong` — пороги из правил расчёта; интерфейс и API показывают полосу |
| `attestation` | `enum` | да | `direct` · `derived` · `claimed` |
| `badge_trust` | `enum` | нет | уровень бейджа; задан **только** при `attestation = direct` и равен наивысшему доверию среди прямо подтверждающих фактов |
| `contributions` | `jsonb` | да | `[{fact_id, claim_id?, group_key, rule_id, rule_version, weight, value, format_factor?, team_factor?, recency_factor, computed_indicator?, contribution, trust_level, attestation}]` |

**Группы зависимых доказательств и формула силы.** Одно событие, пришедшее несколькими путями, не усиливает оценку многократно.
Каждый вклад получает `group_key`:

| Вклад | `group_key` |
|---|---|
| Результат ФСП; разряд, присвоенный по этому соревнованию (`basisCompetitionId`); упоминание того же соревнования в резюме, сопоставленное с фактом | `event_key` факта: `fsp:competition:{competitionId}` |
| Разряд без известного соревнования-основания | `fsp:qualification:{discipline}:{rank}` |
| Все попытки и пересдачи одного задания платформы | `test:assessment:{assessmentId}` |
| Рейтинг внешнего профиля (в том числе переданный ФСП как `platformAccounts`) | `profile:{platform}:{handle}` — один для факта ФСП и факта профиля |
| Упоминания навыка в одном резюме | `resume:{resumeDocumentId}` — одно резюме — одна самодекларация, сколько бы мест работы его ни называли |

```
strength(skill) = 1 − Π_g (1 − max_{i ∈ g} cᵢ)
```

Внутри группы берётся **наибольший** вклад, между группами — насыщающее объединение. Десять участий в разных соревнованиях — десять групп;
результат, разряд за него и строка резюме о нём — одна группа.

**Вклад факта ФСП:** `c = strength_of_result × skill_weight × format_factor × team_factor × recency_factor`.
- `strength_of_result` — по расчётному показателю ЕВСК (`computed_indicator`) или присвоенному разряду; таблица и версия нормы — в
  `fsp_strength_params` (раздел 11).
- `format_factor` — формат соревнования: очный финал весит больше онлайн-отбора; множители по `online` и `stage` соревнования — в
  `fsp_strength_params`. Неизвестный формат — множитель онлайн-отбора (консервативно).
- `team_factor` — командный результат: множитель неизвестной роли, если персональная специализация не передана; ×1 — только если
  специализация передана и совпадает с навыком правила.
- `recency_factor` — давность от `occurred_on` к `as_of` расчёта.

**Правило бейджа.** Бейдж «Подтверждено ФСП» у навыка ставится, только если правило проекции объявляет, что данный тип факта прямо
подтверждает этот навык (`direct`). Командное призовое место не подтверждает прямо ни язык, ни `teamwork`: факт устанавливает участие
в команде и её результат, а не качество взаимодействия. Разряд не подтверждает производственную самостоятельность. Примеры:

| Факт | Вывод | `attestation` |
|---|---|---|
| Присвоен КМС по алгоритмике | `algorithms` | `direct`, бейдж `fsp_verified` |
| 2 место на ЧР по алгоритмике, разряд не присвоен | `algorithms`, вклад с `computed_indicator = KMS` | `direct`, бейдж `fsp_verified`; показатель подписан как расчётный |
| Призёр командного продуктового соревнования, `specialization = backend` | `backend`-навыки из правила специализации | `derived` (правило со ссылкой на факт), бейджа нет |
| Призёр командного соревнования, специализация не передана | только общие навыки дисциплины (`teamwork`, `presentation`) с множителем неизвестной роли | `derived`, бейджа нет; `Go` не выводится вовсе |
| Роль `captain` | маркер `team_lead` с весом 0,5 | `derived` |
| Онлайн-отбор и очный финал одного сезона | две группы (разные соревнования), у отбора меньший `format_factor` | как у дисциплины |
| Резюме: «Go, 3 года» с цитатой | `go` | `claimed` |
| Резюме: «не работал с Go» | нет вывода | — |
| Тест по Go, оценка засчитана | `go` | `direct`, бейдж `platform_verified` («Подтверждено платформой») |
| Присвоен II разряд по алгоритмике у аналитика с опытом | `algorithms` | `direct`; роль и грейд — по опыту, `algo_engineer` не выводится |
| Участие в продуктовом соревновании без места по нормам, `specialization = backend` | уровень ФСП L1 | основание роли ниже порога, роль не выводится; желаемая роль показывается как не выведенная |

**Роль из достижений ФСП.** Основание роли в ФСП одно — персональная специализация участника команды, называющая роль (правила
`fsp_projection_rules` с обязательной специализацией: продуктовые соревнования, информационная безопасность, робототехника).
Алгоритмика, индивидуальные результаты любой дисциплины, БАС и командный результат без такой специализации подтверждают навыки и
уровень ФСП, а не род работы. Путь к роли через навыки засчитывает ключевые группы навыков роли только по основаниям вне ФСП
(`coreSkillGrounds = outside_fsp`); навыки из ФСП входят в сумму оснований и ранжируют роли. Специализация сама может установить роль,
о которой больше ничего не говорит, если её основание достигает порога роли, — но такая роль не бывает основной при роли, установленной
без ФСП (резюме, опыт, тест платформы; раздел 12.2).

Подтверждённый дочерний навык даёт родителю частичный вклад (множитель задаётся правилом таксономии), но не наоборот; такой вклад
всегда `derived`.

**Где живут правила.** Веса «дисциплина / специализация → навык или роль» и `attestation` каждой цели — `fsp_projection_rules`;
таблица ЕВСК-эквивалента с версией нормы, `format_factor`, множитель неизвестной роли, давность — `fsp_strength_params`; шкала уровня
ФСП — `fsp_level_rules`; группировка вкладов и пороги `strength_band` — `categorization_rulesets.params`. Все — в версии таксономии
(раздел 11); вывод ссылается на `rule_id` и `rule_version`.

### 9.4. Внешние профили

**`external_profiles`**: `id`, `candidate_id`, `platform enum(codeforces|github)`, `handle ext_id`, `external_id` (устойчивый
идентификатор аккаунта, у GitHub — числовой `id`: переименованный аккаунт остаётся тем же профилем), `ownership_status
enum(unverified|verified)`, `ownership_method enum(oauth|handle_challenge)`, `verified_at ts`; одноразовый код —
`challenge_code`, `challenge_expires_at`, `challenge_attempts`; сверка — `sync_status enum(pending|ok|source_unavailable|not_found)`,
`sync_error` (код причины: `timeout` · `network` · `rate_limited` · `server_error` · `protocol_error`), `sync_checked_at`,
`synced_at`. Один профиль на платформу у кандидата (`UNIQUE (candidate_id, platform)`). Факты из профиля без подтверждённого
владения получают `trust_level = claimed`.

**Подтверждение владения без OAuth-приложения (`handle_challenge`).** Кандидат называет хэндл (или ссылку на профиль) —
платформа выдаёт одноразовый код (`fsp` + 12 латинских букв) со сроком 60 минут и 10 проверками. Кандидат кладёт код туда,
куда может писать только владелец аккаунта: Codeforces — поле имени, фамилии или организации (`user.info` отдаёт `firstName`,
`lastName`, `organization` без ключа); GitHub — описание или имя файла публичного gist либо README репозитория
`<login>/<login>`. Сервер ищет код через публичный API; найден — профиль `verified`, код стёрт. Аккаунт, подтверждённый другим
кандидатом, не подтверждается повторно (учётки демо-сессий и демо-засева не в счёт); проверка и подтверждение идут под
блокировкой хэндла.

**Чтение и факты.** Подтверждённый профиль читается сразу и затем раз в сутки (задание `external_profile.refresh`,
расписание — по `sync_checked_at` старше суток). Один факт на профиль, `trust_level = public_verifiable`, `ownership_basis =
handle_challenge`, `ownership_ref = external_profiles.id`, `event_key = profile:{platform}:{handle}`:
- Codeforces — `platform_rating`: рейтинг, максимум, ранг, число решённых задач (разные задачи с вердиктом OK из
  `user.status`), число рейтинговых контестов, дата последнего; `occurred_on` — дата последнего изменения рейтинга;
- GitHub — `repo_languages`: доли языков по байтам пяти последних своих репозиториев (форки не считаются), число публичных и
  своих репозиториев, месяц последнего push, число обновлённых за год; `occurred_on` — месяц последнего push. Это языки
  репозиториев, а не подтверждение авторства каждой строки.

**Вклад в навыки** — правилами набора категоризации (`categorization_rulesets.params.evidence.publicProfiles`, с версии 6;
проверяются выпуском таксономии): Codeforces — навыки `competitive_programming` и `algorithms` с силой по порогам пикового
рейтинга (`maxRating`, без рейтинга — нижний порог), меньше `minSolved` решённых задач — вклада нет; GitHub — язык с долей
не меньше `minShare` даёт навык по таблице «язык linguist → навык», полная сила с `fullShare`, вес меньше веса теста
платформы. Основание вклада — `public_profile`, группа — `event_key` профиля, давность — от `occurred_on`. Доверие вклада —
доверие факта: `public_verifiable` у подтверждённого профиля (бейдж «Публичный профиль» при прямом подтверждении), у
неподтверждённого — `claimed`; родителям навыка, как и всегда, — только `derived`. Прямое подтверждение публичным профилем
покрывает требование вакансии, но подтверждённым для доверия к оценке и для пула не считается (13.4).

**Квитанции** — по шаблонам `receipt_templates` источников `codeforces` и `github`: обобщённая квитанция Codeforces называет
уровень пикового рейтинга (титул), точная — хэндл и рейтинг; квитанция GitHub — языки, а в «не подтверждает» — авторство
каждой строки кода. Снимок источника, к которому квитанция привязывает обязательство, — само чтение (`source_snapshot_sha256
= payload_sha256`).

Новое чтение с тем же содержанием обновляет `last_verified_at`; другое — `superseded` и новая версия; аккаунта больше нет —
`withdrawn` (`source_profile_not_found`); отвязка удаляет строку профиля и переводит факты в `withdrawn` (`profile_unlinked`).
Любой переход идёт общим путём изменения доказательств (`profile_revision`, пол доказательств при изъятии, пересчёт).

**Сеть.** Внешние API вызывает только сервер, у каждого запроса срок; Codeforces — не чаще раза в 2 с, GitHub без токена —
60 запросов в час с адреса, с `GITHUB_TOKEN` — 5000. Корни API — `CODEFORCES_API_URL`, `GITHUB_API_URL` (по умолчанию
настоящие). Источник не ответил — у профиля `sync_status = source_unavailable` с причиной, факты прежние,
задание повторяется в момент, который назвал источник; подстановок нет. Журнал: `external_profile.challenge_issued`,
`.verified`, `.verification_failed`, `.synced`, `.sync_failed`, `.unlinked` — платформа и коды, без хэндла.

### 9.5. `experience_entries` — группы опыта

Место работы из резюме — не набор плоских утверждений, а группа «должность — организация — период — применённые навыки». Группу
собирает разбор (`contracts.md` 3.2, поле `group`); утверждения группы ссылаются на неё через `claims.experience_entry_id`.

| `id` | `id` | да | |

| `position_title` | `text` | нет | должность как написано |
| `role_key` | `text` | нет | нормализованная роль; `NULL` — не сопоставлена |
| `organization_name` | `text` | нет | как написано; в каталог не попадает (раздел 14) |

**Расчёт стажа** — часть расчёта категоризации (`categorization_runs.experience_summary`), детерминированный при `as_of`:
- **общий стаж** — длина **объединения** интервалов всех действующих групп с `period_status = valid` (не `rejected`); пересекающиеся
  периоды (совместительство, две должности в одной компании) сливаются, а не складываются;
- **стаж по роли** — объединение интервалов групп с этой ролью (или с ролями семьи — по правилам расчёта); **стаж по навыку** — групп,
  где навык в `applied_skill_keys`;
- открытый конец при `is_current` — `as_of`; точность `year` даёт диапазон: стаж хранится как `{min_months, max_months}`, а не
  точное число;
- группы с `period_status ≠ valid` в стаж не входят и попадают в `missing` оси грейда («у места работы X нет дат»).

### 9.6. `verification_receipts` — квитанции проверки

Квитанция — подписанное платформой заявление о факте с уровнями доверия `fsp_verified`, `platform_verified` или `public_verifiable`.
Работодатель проверяет её по публичному идентификатору, не узнавая личности; кандидат видит свои квитанции в профиле.

Компания получает квитанции автоматически при просмотре карточки кандидата в каталоге — одну на показанный факт, на уровне показа:
`exact`, если факт показан точно, иначе `generalized`; карточка показывает у достижения квитанции только этого уровня. Кандидату 14–17
лет квитанции не выпускаются и не показываются (раздел 14).

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `handle` | `text` | да | `UNIQUE`; публичный идентификатор, 128 случайных бит в base32; не выводится из `id` и не связан между компаниями |
| `fact_id` | `id` | да | |
| `fact_payload_sha256` | `hash` | да | версия факта, о которой квитанция |
| `audience_company_id` | `id` | нет | компания, которой выдан идентификатор; `NULL` — квитанция кандидата о самом себе |
| `disclosure_level` | `enum` | да | `generalized` (как в базовом каталоге) · `exact` (кандидат 18+ выбрал точные достижения, или получатель после раскрытия) |
| `statement` | `jsonb` | да | канонический JSON, схема ниже |
| `statement_sha256` | `hash` | да | |
| `signature`, `signing_key_id` | `text` | да | Ed25519 над каноническим `statement`; открытые ключи публикуются (`contracts.md` 5.5) |
| `commitment_nonce` | `bytea` | да | соль обязательств; не раскрывается публично |
| `issued_at` | `ts` | да | |

`UNIQUE (fact_id, fact_payload_sha256, audience_company_id, disclosure_level)` — повторный показ той же карточки той же компании не
выпускает новую квитанцию.

**Состав `statement`.**

| Поле | Смысл |
|---|---|
| `receipt_version` | версия схемы заявления |
| `source` | `fsp` · `platform_test` · `codeforces` · `github` |
| `verified_at` | `source_facts.last_verified_at` — дата сверки с источником |
| `asserts` | что факт подтверждает на уровне `disclosure_level`: дисциплина, уровень соревнования, сезон, группа результата, формат (очный / онлайн); на уровне `exact` — соревнование, этап, место |
| `does_not_assert` | чего факт не подтверждает — тексты шаблона факта (`receipt_templates` версии таксономии) по виду результата: `all` — в каждой квитанции шаблона («владение конкретным языком», «коммерческий опыт», для теста — «самостоятельность выполнения», «навыки за пределами покрытия задания»); для результата соревнования ФСП ещё `team` или `individual` — командный он или личный («личный вклад в командное решение» — только у командного), и `byRole` — по роли участника команды (запасной, тренер; `unknown` — источник роль не передал). Выпуск таксономии отказывает шаблону другого факта с текстами по виду результата или роли |
| `record_commitment` | `generalized`: SHA-256(`source_record_ref` ‖ `commitment_nonce`); `exact`: сам `source_record_ref` |
| `snapshot_commitment` | `generalized`: SHA-256(`source_snapshot_sha256` ‖ `commitment_nonce`); `exact`: сам `source_snapshot_sha256` |
| `issuer` | платформа и `signing_key_id` |
| `source_simulator` | только в квитанциях демонстрационного стенда: `true`, если факт получен от демонстрационного имитатора ФСП (`FSP_ACHIEVEMENTS_ADAPTER=mock`), а не от самой федерации |

Обязательства вместо сырых ссылок нужны потому, что `source_record_ref` и хэш снимка одинаковы для всех компаний: две компании, сравнив
квитанции, связали бы псевдонимы одного кандидата. Оператор ФСП при разборе раскрывает обязательство, предъявив соль.

**Статус при проверке** вычисляется в момент запроса, не хранится: `valid` — факт `active` и его `payload_sha256` совпадает с
`fact_payload_sha256`; `superseded` — источник прислал новую версию записи; `annulled` — источник аннулировал результат или попытку;
`not_valid` — факт изъят (отзыв, отвязка, удаление) без указания причины. После очистки аккаунта квитанции удаляются, проверка отвечает
`404 not_found`. Персональных данных, псевдонима кандидата и `candidate_id` проверка не возвращает.

Пересмотр не меняет статус попытки: он добавляет оценку.

**Связь с доказательствами.** Действующая оценка (последняя в цепочке `supersedes`) неаннулированной попытки порождает `source_fact`
(`source = platform_test`, `trust_level = platform_verified`, `ownership_basis = own_attempt`). Новая оценка → старый факт
`superseded`, новый `active`. Аннулирование попытки или объявление версии `defective` → факты `annulled` → пересчёт. Автоматический
отказ кандидату по результату теста не производится (ст. 16).

**ТЗ-зависимо:** лимит попыток, интервал пересдачи и срок хранения артефактов — параметры `product_policy` вида `assessment_policy`.

**Реализация пересмотра и аннулирования** (`src/lib/server/assessments/review.ts`, `annul.ts`; кабинет `/operator/assessments`,
право `assessment.review`). **Откуда оператор узнаёт о попытке:** список «требуют внимания» — отправленные неаннулированные попытки,
в журнале сигналов которых есть вставки из буфера или уходы со страницы (повод посмотреть человеку, не вывод о заимствовании), и
отправки, которые песочница не проверила дольше 30 минут (после сбоя песочницы попытка остаётся `submitted`, 6.4); «все последние» —
до 100 отправленных попыток, аннулированные тоже. Счётчик «требуют внимания» на первом экране оператора считает всю очередь
(`attemptsForReviewCount`). Жалобы на попытку как отдельного канала нет: просьба кандидата приходит к оператору
вне платформы и записывается причиной `candidate_request`. **Дело попытки** показывает условие и версию (с хэшем содержимого), код и
прогоны по всем тестам версии с их данными — скрытым тоже (вывод программы на скрытом тесте хранится только хэшем), шаги квиза с
ключами и оценкой способности, цепочку оценок, факты профиля с их статусом и журнал сигналов; открытие — `operator.case_access`
(`case_type = assessment`) и `assessment.artifact_viewed`. **Аннулирование** — отправленной попытки (`submitted`, `scored`) с причиной,
в одной транзакции: попытка → `annulled` (`annulled_by`, `annulled_at`, `annul_reason`); ожидающий прогон отправки отменяется
(идущий не запишет результат: попытка уже не `submitted`); факты `platform_test` этой попытки → `annulled`
(`status_reason = attempt_annulled`), их утверждения и группы опыта → `invalidated`; квитанции таких фактов отвечают `annulled`
(статус квитанции следует за фактом, 9.6); при снятом факте — `profile_revision + 1` с подъёмом `evidence_floor_revision`,
снятием опубликованной категории и постановкой `categorization.compute` и `profile.embed` (17.3). Событие `assessment.annulled` —
причина, прежний статус, число снятых фактов. Повтор по аннулированной попытке ничего не меняет и событие не пишет;
неотправленная попытка — `409 attempt_not_sent`. Попытка, аннулированная из-за `technical_failure` или `version_defect`, не входит в
лимит попыток. Кандидату — уведомление `assessment.annulled`; страница попытки показывает дату, причину и засчитывается ли попытка
в лимит.

### 10.4. `assessment_artifacts` — артефакты попытки

Оценку можно пересмотреть только по исходному ответу, поэтому попытка хранит всё, из чего получена оценка.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `attempt_id` | `id` | да | |
| `seq` | `integer` | да | порядок в попытке; `UNIQUE (attempt_id, seq)` |
| `kind` | `enum` | да | `answer` (ответ на вопрос или открытый ответ) · `code_submission` (исходный код, язык) · `run_result` (результат прогона в песочнице) · `quiz_step` (шаг адаптивного квиза) |
| `content` | `jsonb` | усл. | небольшие артефакты: `quiz_step` — `{item_id, item_version, presented_at, answer, correct, ability_estimate_after}`; `run_result` — ответ песочницы по тесту (`contracts.md` 6.1) без вывода программы сверх лимита |
| `file_id` | `id` | усл. | крупные артефакты (код, вывод) — объект в хранилище, `files.purpose = assessment_artifact` |
| `sha256` | `hash` | да | хэш содержимого |

Append-only. **Реализация:** после `retention_until` задание `retention.sweep` сначала удаляет объект файла артефакта из
хранилища, затем роль очистки обнуляет `content` и `file_id` (только вместе) и удаляется строка `files`; при сбое хранилища всё
остаётся до следующего запуска, повтор удаляет тот же объект. Строка, `sha256` и оценка остаются. **Доступ:** кандидат — свои ответы и код, результаты прогонов по открытым тестам (скрытые тесты и ключи не раскрываются);
оператор ФСП — все артефакты в деле `assessment`; работодатель — никогда, ему видны уровень, дата, версия задания и покрытие.

**Подпись результата.** Факт теста показывается как «Подтверждено платформой: задание {название} v{версия}, {дата}, уровень {уровень}»
с покрытием задания. Успешная попытка подтверждает выполнение конкретного задания в конкретных условиях (изолированная песочница, лимиты,
журнал сигналов); она не выдаётся за доказательство самостоятельного выполнения или всесторонней квалификации. Перенос на широкий навык —
только через правило `assessments.skill_keys` с весом и полосой силы, как у любого вывода.

**Неизвестные навыки.** Очередь пополняют только теги внешних публикаций, которые нормализация не распознала, — из резюме навыки в

единицы каждому своему написанию. Написание длиннее 80 символов в очередь не идёт — это фраза требования, а не название навыка.
`last_seen_at`/`last_posting_id` называют публикацию, которая принесла написание последней; более ранняя публикация, обработанная
позже (повтор задания, новая версия таксономии), не отнимает это место у более поздней. Администратор видит очередь в
«Таксономия → Неизвестные навыки» и отмечает написание `added` или `rejected`; сама отметка на словарь не влияет — он меняется
только новой версией таксономии.

**Нормализация навыка.** Точный алиас → нечёткое сопоставление с порогом; если два канонических навыка ближе порога и неразличимы —
отказ (`alternatives` в утверждении) → неизвестный навык с исходным текстом. Полнотекстовый поиск (FTS `russian`) нормализацию не
заменяет.

**ТЗ-зависимо:** состав ролей, грейдов и навыков, веса правил проекции, множители формата, шкала уровня ФСП, веса соответствия — данные
справочников; ТЗ меняет версию справочника.

## 12. Категоризация и возражения

Категория — навигация и подсказка для работодателя. Она не скрывает кандидата и не отсекает его от вакансий: решение о приглашении
принимает человек. Поэтому продукт не требует письменного согласия по ч. 2 ст. 16, а ч. 3–4 ст. 16 выполняются объяснением
и возражением.

### 12.1. `categorization_runs`

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `candidate_id` | `id` | да | |
| `input_revision` | `bigint` | да | `profile_revision` на момент снятия снимка |
| `input_snapshot_sha256` | `hash` | да | хэш канонического JSON входа |
| `input_refs` | `jsonb` | да | идентификаторы фактов и утверждений, вошедших в снимок |
| `taxonomy_version_id` | `id` | да | |
| `ruleset_id` | `id` | да | версия правил |
| `as_of` | `ts` | да | момент, от которого считается давность; входит в детерминированность |
| `computed_at` | `ts` | да | |
| `job_id` | `id` | нет | задание, выполнившее расчёт |
| `origin` | `enum` | да | `automatic` · `manual_override` (решение оператора по возражению) |
| `override_by`, `override_reason` | `id`, `text` | усл. | для `manual_override` |
| `outcome` | `enum` | да | `complete` (у основной категории установлены все три оси) · `partial` (хотя бы одна ось установлена) · `insufficient_data` (ни одной) |
| `missing` | `jsonb` | да | по осям: чего не хватает и что добавить — `{role: [...], grade: [{code: 'no_dated_experience', hint: …}], stack: [...]}`; пусто у установленной оси |

| `status` | `enum` | да | `computed` · `published` · `superseded` · `blocked` · `discarded_stale` |

**Детерминированность.** Одинаковые снимок, `taxonomy_version_id`, `ruleset_id` и `as_of` дают одинаковый результат. Расчёт — чистая
функция без обращений к моделям; эмбеддинги в категорию не входят.

**Переходы.**

```
computed ──(input_revision = текущему profile_revision, input_revision ≥ evidence_floor_revision, все входы active)──▶ published   (предыдущий published → superseded)
computed ──(profile_revision ушёл вперёд)──▶ discarded_stale
published ──(вход отозван: факт withdrawn/annulled, согласие отозвано)──▶ blocked ──(пересчёт)──▶ superseded
```

`blocked` снимает категорию с карточки немедленно, до завершения пересчёта; кандидат остаётся в каталоге без категории.

### 12.2. `category_assignments` и `fsp_level_assignments`

Категория — три **независимые оси**: роль, грейд, ядро стека. Каждая устанавливается своими основаниями; неизвестная ось не отменяет
известные. Кандидат с подтверждёнными ролью и стеком, но без данных о производственном опыте, получает категорию «backend · Go · грейд:
недостаточно данных» и находится по роли и стеку.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `run_id` | `id` | да | |
| `rank` | `enum` | да | `primary` · `secondary` |
| `role_status` | `enum` | да | `established` · `insufficient_data` |
| `role_key` | `text` | усл. | выведенная роль; при `role_status = established` |
| `grade_status` | `enum` | да | `established` · `insufficient_data` |
| `grade_min`, `grade_max` | `text` | усл. | диапазон грейда; при `grade_status = established` |
| `grade_confidence` | `numeric(3,2)` | усл. | уверенность 0…1; при `grade_status = established` |
| `stack_status` | `enum` | да | `established` · `insufficient_data` |
| `stack_skill_keys` | `text[]` | да | ядро стека, 0–3 навыка; пусто при `insufficient_data` |
| `score` | `numeric` | нет | счёт роли; при `role_status = established` |
| `explanation` | `jsonb` | да | вклады: `[{source, fact_id, claim_id, group_key, skill_key, rule_id, contribution, trust_level, attestation, text}]`; грейд: какие сигналы сдвинули границы; расхождения источников («по резюме — senior, по тесту — middle»); желаемая роль против выведенной |

**Инварианты.**
- В строке назначения установлена хотя бы одна ось. При `outcome ∈ {complete, partial}` ровно одна `primary` и не больше двух
  `secondary`; при `insufficient_data` назначений нет, есть только `missing` и уровни ФСП.
- `role_status = insufficient_data` у `primary` допустим (известен только стек); у `secondary` роль установлена всегда — дополнительная
  категория без роли смысла не имеет.
- Грейд устанавливается только по производственным сигналам (стаж по роли, маркеры ответственности, тест уровня). Достижения ФСП
  ни устанавливают, ни сдвигают грейд; их сила идёт в навыки и в уровень ФСП. «Недостаточно данных» по грейду работодатель видит как
  неизвестность, а не как низкий грейд: в фильтре по грейду такой кандидат выводится отдельной группой «грейд не установлен».
- Основная роль выбирается среди ролей, установленных без ФСП, если такие есть (`primaryRole = grounds_outside_fsp_first`); среди
  ролей одного вида решает счёт. Признак в объяснении роли — `established_without_fsp` (раздел 9.3).
- Желаемая роль (`candidates.desired_role_keys`) на расчёт не влияет. Если она не совпадает с выведенной, объяснение показывает обе
  и чего не хватает для желаемой.
- Объяснение строится только из сохранённых вкладов; текстовый пересказ (если есть) не добавляет фактов.

**`fsp_level_assignments`** — фасет «уровень ФСП» по дисциплине, считается тем же расчётом.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `run_id` | `id` | да | |
| `discipline` | `text` | да | код дисциплины (`contracts.md` 1.3) |
| `level` | `enum` | да | `L1` · `L2` · `L3` · `L4` · `L5` по `fsp_level_rules` |
| `basis_fact_ids` | `id[]` | да | факты, давшие уровень (только `fsp_verified`) |
| `last_result_on` | `date` | нет | свежесть: дата последнего результата в дисциплине |

Уровень ФСП — отдельный фасет каталога, а не грейд: олимпиадник без коммерческого опыта находится как «алгоритмика L4, грейд не
установлен», а не как выдуманный middle. Для 14–17 лет в каталоге показывается только дисциплина и уровень (раздел 14).

**ТЗ-зависимо:** ключ категории (роль × грейд × стек), число дополнительных категорий, пороги осей, шкала уровня ФСП.

| `resolved_at`, `notified_at` | `ts` | нет | |

**Переходы.** `open → in_review` (назначен ответственный) → `resolved_upheld | resolved_changed`; `open | in_review → withdrawn`
(кандидатом). Задание `dispute.deadline_watch` за 5 дней до `due_at` уведомляет (`dispute.due_soon`) ответственного оператора — пока у
него действует роль, иначе всех операторов — и всех администраторов, и ставит себя на `due_at`, где сообщает о просрочке
(`dispute.overdue`). Получатели — только сотрудники, досягающие возражения (раздел 19.3): персонал демо-сессии кандидата или, если он
вне сессий, персонал вне сессий. Рассмотренное, отозванное или удалённое возражение не напоминает; каждый получатель получает каждый
этап один раз. В уведомлении — только срок, без данных кандидата и текста возражения. Ссылка ведёт оператора в очередь возражений,
администратора — в управление персоналом.

**Ручное решение.** `manual_override` действует, пока не изменятся желаемые роли кандидата (`desired_role_keys`) или основания категории —
активные факты, утверждения и записи опыта, на которых стоит расчёт (`input_refs`, раздел 12.1). Правка зарплатных ожиданий, формата
работы или видимости в каталоге тоже поднимает `profile_revision` (раздел 13.4), но не меняет ни желаемые роли, ни основания, и на силу
`manual_override` не влияет — соответствие вакансиям при этом пересчитывается как обычно. Как только желаемые роли или основания меняются,
выполняется автоматический расчёт, и кандидат может снова оспорить; та же проверка решает, вправе ли оператор ответить на возражение, или
основания успели уйти вперёд и категорию нужно решать заново. **ТЗ-зависимо.**

### 12.4. Путь к кандидату без категории

Каталог не требует категории. Работодатель находит кандидата:
- по навыкам и тексту (FTS, векторный поиск) без фильтра категории;
- по установленным осям частичной категории (роль и стек без грейда);
- через фасет «уровень ФСП» по дисциплине;
- через фасет «Без категории / недостаточно данных»;
- через соседние категории (та же роль ±1 грейд, та же семья ролей).

Кандидат без сигналов и кандидат с ошибочной категорией остаются доступны этим путём, не зависящим от ML.

### 12.5. Рынок категории

Три показателя разного происхождения — не смешиваются, не усредняются между собой и показываются рядом, каждый со своими выборкой и методом.

## 13. Вакансии, агрегатор, соответствие, приглашения, найм

Вакансия — одна сущность для собственных и внешних предложений, чтобы поиск, соответствие и рынок работали по общей логике. Права
различаются происхождением: приглашать можно только по собственной вакансии проверенной компании; внешняя вакансия — предмет поиска,
рынка и заявки «это наша вакансия».

**Инварианты** (`CHECK` по `origin`).
- `own`: `company_id`, `created_by_member_id`, `role_key`, грейд, полная вилка с известной налоговой базой; `claimed_company_id`,
  `external_org` — `NULL`; публикаций у собственной вакансии нет. Полная вилка следует из карточки задачи: работодатель выходит на
  кандидата «с вакансией и зарплатой».
- `external`: `company_id` и `created_by_member_id` — `NULL`; не меньше одной публикации (раздел 13.2). Внешняя организация не получает
  прав работодателя: ни каталога, ни приглашений, ни карточек кандидатов — ни через `external_org`, ни через `claimed_company_id`.
- **`isInvitable(vacancy)`** — единственная проверка «можно ли приглашать по вакансии»: `origin = own`, компания `verified`, статус
  `published`, `salary_min` и `salary_max` не `NULL`, `salary_tax_base ≠ unknown`. Внешняя вакансия → `policy_violation`
  (`vacancy_not_invitable`), в том числе после одобренной заявки.
- Неизвестные зарплата и грейд внешней вакансии показываются как «не указано», а не как ноль или оценка; односторонняя вилка
  показывается «от» или «до».
- Проверка текста выполняется и для внешних вакансий: `blocked` → `hidden` (в поиске нет, рынок её не учитывает).

**Переходы `own`.** `draft → published` (компания `verified`, полная вилка, проверка текста `clean` или предупреждения подтверждены);
`draft | published | paused → pending_moderation → published | paused | draft | closed` (модерация, ниже); `published ⇄ paused`;
`draft | pending_moderation | published | paused → closed`. Закрытие вакансии сразу убирает из каталога подростков, видимых в её
контексте, и отзывает её неотвеченные приглашения (раздел 13.5).

**Вакансия из текста.** Работодатель вставляет текст, разбор предлагает поля с цитатами, работодатель их подтверждает и сохраняет
черновик. Без модели поля читают детерминированные правила (`ml_results.rules_version = vacancy-text-rules/N+…`): ответ той же формы,
что у модели, с теми же проверками цитат и отрицаний. Черновик помечен `mode = rules`, в `ml_results` — `processing_mode = rules_only`
с кодом отказа модели в `failure`. Альтернативы навыков («C++ или Python», «Go/Rust») разбираются на навык каждый; навыки, названные на
выбор словом «или», «либо», «or», предлагаются желательными: требования «одно из» у вакансии нет, и обязательными оба потребовали бы
того, чего текст не требует. Косая черта без такого слова раздел не меняет — «HTML/CSS» называют вместе.

**Вакансия для несовершеннолетних.** `min_age` сохраняется только при действующем принятии `minor_employment_terms` владельцем
компании (раздел 6.2): более поздняя опубликованная редакция, требующая повторного принятия, его отменяет. Без принятия —
`policy_violation` (`minor_terms_not_accepted`); `minor_terms_acceptance_id` — это принятие.

**Модерация (`pending_moderation`).** Дело открывается, когда проверка текста блокирует публикацию черновика или правку опубликованной
(приостановленной) вакансии; `text_check.moderation` хранит момент открытия, куда вакансия вернётся (`resume_to`: `published` или
`paused`) и решение оператора с причиной. Решения оператора (`vacancy.moderate`): «опубликовать» — требование законно (например,
гражданство для допуска к гостайне), вакансия возвращается в каталог или в паузу; «вернуть на правку» — `draft`, причина обязательна;
«отклонить» — `closed`, причина обязательна, неотвеченные приглашения отзываются. Причина — до 2000 символов; компания видит её на
странице вакансии, в журнал идут только коды (`vacancy.moderation_decided`: решение, новый статус, правила). Автор вакансии и владельцы
компании получают уведомление `vacancy.moderation_decided` (раздел 3.7). Решение по вакансии, которая уже не на модерации, —
`409 conflict` (`vacancy_not_in_moderation`). Правка вакансии на модерации проверяется заново: прошла — вакансия сразу возвращается
туда, откуда ушла (`draft`, если компания не проверена; новые предупреждения подтверждаются), журнал — `vacancy.moderation_cleared`;
заблокирована — остаётся у оператора с новыми фрагментами. Одобрение оператора действует, пока блокирующие фрагменты не меняются:
правка опубликованной вакансии с теми же фрагментами модерации не требует, с другими — открывает новое дело. Смена версии валидатора
тоже считается изменением: фоновая перепроверка (`vacancies.text_recheck`, раздел 17.2) находит вакансии, одобренные по прежней
версии, и при других блокирующих фрагментах открывает дело — как если бы их поправил работодатель. Причина возврата остаётся
на черновике до его публикации.

**Переходы `external`.** `active → stale` (актуальность ни одной публикации не подтверждена дольше `sourcing_policy.stale_after_days`)
`→ active` (подтверждена); `active | stale → closed` (все публикации сняты, раздел 13.2); любой → `hidden` (проверка текста, решение
оператора) `→ active`. Когда публикуется собственная вакансия, созданная по внешней (`derived_from_vacancy_id`), внешняя получает
`superseded_by_vacancy_id` и уходит из поиска; её публикации продолжают отслеживаться, в рынке кластер учитывается один раз.

**Инварианты.**
- **Контакты не хранятся.** ФИО, почта, телефон, мессенджеры рекрутеров и сотрудников отбрасываются адаптером до записи; в
  `original_terms` — только поля белого списка. Сырой ответ источника не хранится, только `raw_sha256`.
- **Склейка дублей сохраняет все публикации:** кластер — внешняя вакансия, у неё столько публикаций, сколько источников и записей её
  назвали. Склейка консервативна: неоднозначная пара остаётся двумя вакансиями (ложная склейка хуже дубля). Оператор может перенести
  публикацию в другой кластер (`method = manual`); у вакансий меняется `revision`.
- Поля внешней вакансии берутся из публикации с наибольшим `source_updated_at`; если публикации расходятся в вилке или грейде,
  вакансия получает признак `terms_conflict`, а интерфейс показывает условия каждой публикации с источником.
- **Снятие публикации** (`freshness = gone`) — только по явному ответу источника «нет такой записи» при проверке одной записи или по
  отсутствию в **полном** снимке (`vacancy_import_runs.completeness = complete`). Неполный импорт снятий не порождает.

**`vacancy_import_runs`**: `id`, `source`, `adapter_version`, `job_id`, `mode enum(full|incremental|check)`, `started_at`, `finished_at`,
`status enum(running|succeeded|failed)`, `completeness enum(complete|partial)` с `incomplete_reason`, `cursor_state jsonb`, `counts jsonb`
(`fetched`, `created`, `updated`, `unchanged`, `gone`, `rejected` с причинами). Задания — `vacancies.import`, `vacancies.freshness_check`
(раздел 17.2).

**Переходы.** `awaiting_company_verification ──(компания verified)──▶ pending_review ──(оператор)──▶ approved | rejected`;
`awaiting_company_verification | pending_review ──(заявитель)──▶ withdrawn`; компания `rejected` → заявка `rejected`.

**Инварианты.**
- Одна одобренная заявка на вакансию. Одобрение ставит `vacancies.claimed_company_id` и предлагает компании создать собственную вакансию
  по внешней (`derived_from_vacancy_id`, поля предзаполнены, вилку работодатель заполняет полностью). Приглашать — только по ней.
- Заявка не даёт прав: до `approved` и после него внешняя вакансия остаётся внешней (`isInvitable = false`).
- Если у публикации есть ИНН и он не совпадает с ИНН компании, `match_evidence` это показывает; одобрить можно только с записанной
  причиной.
- Отзыв — действие заявителя с правом подачи (`vacancy_claim.create`, сессия участника компании): открытая заявка
  (`awaiting_company_verification` или `pending_review`) → `withdrawn`, событие `vacancy_claim.withdrawn` (`vacancy_id`,
  `from_status`). Оператор отозванную заявку не видит; компания может подать новую. Рассмотренная заявка не отзывается.
- Подача заявки — через API и через кабинет — и её отзыв разделяют одно право (`vacancy_claim.create`).
- Одобрение заявки действует в месте заявившей компании. Компания вне демо-сессий записывается в вакансию
  (`claimed_company_id`), и вакансия заявлена для всех. Компания демо-сессии держит одобрение только в своей заявке
  (`vacancy_claims.demo_session_id`). Одна одобренная заявка на вакансию вне сессий и отдельно одна в каждой сессии. Своя
  вакансия на основе внешней вытесняет её для всех, только если компания вне сессий. В сессии внешняя вакансия уходит из
  поиска и ленты лишь для зрителей этой сессии.

**Счётчик «в пуле N подтверждённых кандидатов»** у внешней и собственной вакансии — число кандидатов, для которых одновременно:
`catalogVisibleToAnyVerifiedCompany` (раздел 7.4); соответствие вакансии (раздел 13.4) не ниже порога `match_rulesets.params.pool_threshold`;
хотя бы один обязательный навык вакансии подтверждён выводом с `badge_trust ∈ {fsp_verified, platform_verified}` (публичный профиль
не в счёт — 9.4). Счётчик считается заданием `match.refresh`
по `revision` вакансии, показывается с датой расчёта и порогом «< 5»; у вакансии без распознанной роли и навыков — «недостаточно
данных». Кнопка «Это наша вакансия» рядом со счётчиком ведёт в заявку. При подъёме ревизии вакансии `pool_count` и
`pool_counted_at` сбрасываются, счётчик — «считается» до `match.refresh` новой ревизии.

**«Подходящих без подтверждения M».** Рядом с пулом — кандидаты, чьё сохранённое соответствие текущей ревизии вакансии и
действующего набора правил достигает порога пула, но ни один обязательный навык не подтверждён напрямую. Считается при чтении по
`match_scores`, среди видимых любой проверенной компании, с порогом малых чисел `catalog_policy`. К нему — обязательные навыки
вакансии, которые подтверждает опубликованный тест платформы.

### 13.4. Соответствие вакансия ↔ кандидат

`matchScore(vacancy@revision, candidate@profile_revision, match_ruleset, embedding_space?) → MatchResult` — функция над снимками;
одна и та же в обе стороны: работодатель ранжирует кандидатов под вакансию, кандидат видит своё соответствие вакансиям. Каждый экран
(поиск под вакансию, карточка, `GET /vacancies/{id}/matches/{pseudonym}`, «Вакансии для меня», сравнение) считает соответствие при
чтении этой же функцией, поэтому объяснение есть у любой пары — и у той, что не сохранена («почему не подходит»). Сохраняются только
значимые пары — счёт не ниже `matching_policy.store_threshold` (раздел 13.8): они нужны для счётчика пула и воспроизводимого разложения
счёта, — и пара каждого приглашения. Карточка кандидата у компании считает соответствие одной пары, и реранкер оценивает её отдельно:
в списке он оценивает только первых по счёту.

**`match_scores`**

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `vacancy_id`, `vacancy_revision` | `id`, `bigint` | да | |
| `candidate_id`, `candidate_revision` | `id`, `bigint` | да | `profile_revision` на момент расчёта |
| `categorization_run_id` | `id` | нет | опубликованный расчёт, из которого взяты навыки и грейд; `null` — опубликованной категории не было (нет расчёта или он `blocked`) |
| `match_ruleset_id` | `id` | да | |
| `embedding_space_id` | `text` | нет | пространство семантического компонента, если он вычислен |
| `reranker_model_id` | `text` | нет | модель реранкера, если компонент вычислен |
| `score` | `numeric(4,3)` | да | взвешенная сумма **вычисленных** компонентов |
| `component_statuses` | `text` | да | по букве на компонент в порядке `required, nice, trust, grade, salary, semantic, reranker, role`: `c` computed · `u` unknown · `a` unavailable · `n` not_comparable |
| `required_value` … `reranker_value`, `role_value` | `double precision` | нет | значение компонента; есть ровно у вычисленного (`CHECK`) |
| `computed_at` | `ts` | да | когда строка записана или её результат последний раз изменился |
| `job_id` | `id` | нет | |

`UNIQUE NULLS NOT DISTINCT (vacancy_id, vacancy_revision, candidate_id, candidate_revision, categorization_run_id, match_ruleset_id)`.

**Разложение — коды и числа.** Веса берутся из набора правил строки (`match_ruleset_id`), детали и объяснение — `matches` (что
подходит и чем подтверждено, со ссылками на квитанции), `unknown` (что неизвестно), `to_verify` (что проверить на собеседовании), `gaps`
(каких обязательных требований нет и что подтянуть) — собирает `matchScore` при чтении из снимка той же ревизии; справочные тексты
и идентификаторы фактов в строке не повторяются. Строка весит ≈ 400 байт вместе с индексами против ≈ 2 КБ у прежнего `jsonb`-разложения (замер на демо-засеве 3000 × 1432).

**Запись — инкрементальная** (`match.refresh`, раздел 17). Пересчёт вакансии считает всех кандидатов каталога, пишет пары не ниже
порога и удаляет строки вакансии, которых нет среди записанных: другой ревизии вакансии или кандидата, другого набора правил, упавшие
ниже порога, ушедших из каталога; у закрытой и снятой вакансии удаляются все. Строка того же снимка с тем же результатом не
переписывается (`ON CONFLICT … WHERE … IS DISTINCT FROM`); другой результат того же снимка (окно реранкера, появился вектор) заменяет
её на месте. Пересчёт кандидата пишет его значимые пары без реранкера и не трогает строку того же снимка — реранкер считает сторона
вакансии; он удаляет строки кандидата другого снимка и незначимые пары вакансий, которые посчитал. Кандидат вне каталога не хранится
ни в одной паре. Строка, на которую ссылается приглашение, не удаляется. Порог не выше порога пула набора правил — иначе задание
отказывает: пересчёт кандидата сравнивает участие в пуле «до» по сохранённым строкам, и пара без строки значит «не в пуле».

**Строка приглашения.** Строка соответствия пары пишется при первой отправке приглашения независимо от порога хранения — это ссылка
«почему приглашён» (`invitations.match_score_id`, раздел 13.5). Если пересчёт уже записал строку этого снимка, берётся она; иначе пара
считается так, как её считает сторона кандидата: с семантическим компонентом, без реранкера.

Снимок кандидата — это ревизия профиля **вместе с** опубликованной категорией, которую прочитал расчёт: категория, пересчитанная,
заменённая оператором или заблокированная при той же `profile_revision`, даёт новую строку, а не конфликт со старой; действующей
считается последняя по `computed_at`. Отсутствие категории — одно значение ключа. Изменения `preferences`, видимости в каталоге и статуса
поиска поднимают `profile_revision`: соответствие читает их, и без новой ревизии пересчёт упёрся бы в ту же строку.

**Компоненты.**

| Компонент | Что считает | Когда не вычисляется |
|---|---|---|
| `required` | покрытие обязательных навыков: по навыку — полоса силы, `attestation`, бейдж | у вакансии нет обязательных навыков → `unknown` |
| `nice` | то же для желательных | нет желательных → `unknown` |
| `trust` | доля покрытия обязательных, подтверждённая выводами `direct` | — |
| `grade` | пересечение диапазонов грейда вакансии и кандидата | грейд вакансии или кандидата не установлен → `unknown` |
| `salary` | `compareSalary(ожидания кандидата, вилка вакансии)` | нет ожиданий или вилки → `unknown`; разные валюта, период или база → `not_comparable` |
| `semantic` | косинусная близость внутри активного пространства | нет действительного вектора (раздел 17.3), режим FTS → `unavailable` |
| `reranker` | оценка реранкера (`contracts.md` 3.4) | операция выключена или недоступна → `unavailable` |
| `role` | роль вакансии против ролей кандидата: основная, дополнительная, желаемая | нет роли у вакансии → `unknown`; у кандидата роль не установлена и не совпала с желаемой → `unknown` |

**`trust` и `role`.** `trust` — доля обязательных, покрытая `direct` по ценности полосы, × (1 − `gradeWeight` × (1 − согласованность
грейда)); согласованность — доля диапазона кандидата внутри диапазона вакансии; грейд кандидата не установлен →
`unknownGradeAgreement`; у вакансии нет грейда → 1; доверие 0 ⇔ ни один обязательный не подтверждён напрямую. `role` — основная роль
даёт 1, дополнительная — `role.secondary`, только желаемая — `role.desired`, другая установленная роль — 0. Коды объяснения:
`to_verify` получает `role_not_established` и `role_desired_only`; `gaps` — `role_other`.

**Инварианты.**
- Компонент со статусом не `computed` в сумму не входит, веса вычисленных нормируются; в объяснении он виден с причиной. Неизвестность
  не штрафуется как несоответствие: «грейд не установлен» идёт в `to_verify`, а не снижает счёт.
- Исключение — `required`, `nice` и `trust` у кандидата без действующего расчёта категоризации (категории не было, или доказательства
  под ней отозваны и она пересчитывается): такой компонент не выпадает из суммы, а входит в знаменатель со значением
  `match_rulesets.params.unavailableEvidenceValue` (v7 — 0) — иначе кандидат без категории обгонял бы кандидата с подтверждённой, но
  неполной. `to_verify` получает код `profile_recalculating` (пересчёт идёт) или `profile_insufficient_data` (категории не было).
- Порог хранения не меняет ни счёт, ни объяснение, ни выдачу: поиск и рекомендации ранжируют всех видимых, считая при чтении.
- Строка используется, только пока действительна: `vacancy_revision` равна текущей, `candidate_revision ≥ evidence_floor_revision`,
  расчёт категоризации не `blocked`, пространство активно. Недействительная строка не показывается; интерфейс пересчитывает соответствие
  без недоступных компонентов или показывает «соответствие пересчитывается».
- Строки соответствия — данные о кандидате: читаются только через `canShow` в контексте вакансии, удаляются при очистке аккаунта.
- Реранкер — один явный компонент со своим весом, а не замена счёта; категоризация от соответствия не зависит.

**ТЗ-зависимо:** веса компонентов, порог пула, состав объяснения.

- **Отправленные условия неизменны.** Любое изменение — новая версия через `invitation.revise`; кандидат видит отличия и принимает
  новую версию отдельно. Правка вакансии после отправки не меняет отправленных версий.
- Нижняя граница версии не ниже `salary_min` вакансии на момент версии (одна база по построению).
- **Обхода «отозвать и отправить ниже» нет:** на тройку «компания — вакансия — кандидат» одно приглашение; после `declined`, `expired`
  или `withdrawn` повторное предложение — новая версия того же приглашения (`reopen_count + 1`) не раньше

  `salary_lowered` и показывается кандидату («ниже предыдущего предложения этой компании»). Предложения той же компании по другим её
  вакансиям кандидат видит в истории «Предложения этой компании» со сравнением через `compareSalary`.
- Сравнение вилок между версиями, с ожиданиями кандидата и с рынком — только `compareSalary`: при разных валюте, периоде или налоговой
  базе результат `not_comparable`, а не «ниже» или «выше».
- Каждая отправка версии требует `isInvitable(vacancy)` и `canShow(candidate, viewer, {catalog, vacancyId})`; для 14–17 лет вакансия
  должна подходить по `min_age`.
- Приглашение и его версии видят только члены компании-отправителя и адресат.
- Платформа гарантирует сохранность и прозрачность условий внутри сервиса; фактическую зарплату вне сервиса она не гарантирует —
  исход сообщают стороны (раздел 13.7).

**Переходы `invitations.status`.**

```
sent ──(кандидат открыл)──▶ viewed
sent | viewed ──(принял текущую версию + contact_disclosure)──▶ accepted
sent | viewed ──(отклонил текущую версию с причиной)──▶ declined
sent | viewed ──(response_due_at текущей версии прошёл)──▶ expired
sent | viewed ──(компания отозвала | компания suspended | вакансия closed)──▶ withdrawn
sent | viewed ──(пересмотр: новая версия)──▶ sent            (прежняя версия больше не принимается, новый срок)
declined | expired | withdrawn ──(возобновление после cooldown: новая версия)──▶ sent
accepted ──(пересмотр: новая версия)──▶ accepted            (принятой остаётся прежняя версия до ответа на новую)
```

Ответ на версию, которая уже не текущая, → `409 conflict` с отличиями. После `accepted` непринятая или отклонённая новая версия не
отменяет принятую: `accepted_terms_id` меняется только принятием.

Закрытие вакансии (компанией или отказом модерации) отзывает её неотвеченные приглашения (`withdrawn`, причина `vacancy_closed`,
уведомление кандидату `invitation.withdrawn`); принятые остаются вместе с процессами найма. Принять приглашение по закрытой вакансии
нельзя, в том числе новую версию условий уже принятого: `409 conflict` (`vacancy_closed`).

**Инвариант.** Первое принятие, событие согласия, с которым раскрытие вступает в силу, и строка `disclosures` создаются в одной
транзакции. Без согласия на раскрытие принятие невозможно; поля раскрытия выбирает кандидат (ФИО и почта — обязательный минимум,
телефон и резюме — по выбору). Принятие пересмотренной версии нового раскрытия не создаёт, если кандидат не расширяет поля.

**Принятие кандидата 14–17 лет ждёт представителя.** Раскрытию подростка нужен и `grant` представителя с `authority_verified` по
этому приглашению (раздел 6.3, п. 3). Кандидат принимает версию со своей стороной согласия (`grant` субъекта с выбранными полями);
ответа (`invitation_responses`) ещё нет, статус приглашения не меняется, напоминания о сроке снимаются — принятие **ждёт
представителя**, и тому уходит письмо `representative_disclosure` (компания, вакансия, вилка, раскрываемые поля, срок).
- Ожидание не хранится отдельно, а выводится: приглашение открыто для ответа, у текущей версии нет ответа и не прошёл срок,
  кандидату 14–17, последнее событие раскрытия от субъекта по приглашению — `grant` не раньше создания текущей версии, раскрытие
  ещё не действует. Поэтому пересмотр, срок, отзыв приглашения, отмена кандидатом (его `revoke`) или ответ представителя
  заканчивают ожидание сами, а ссылка прежнего письма перестаёт работать.
- **Срок не продлевается:** представитель отвечает в окне `response_due_at` принятой версии — это срок, на который компания
  держит условия, а согласие представителя — часть ответа стороны кандидата. Ссылка живёт не дольше этого срока; по его
  истечении приглашение закрывается `expired` обычным заданием.
- «Согласен» — `grant` представителя ровно на выбранные кандидатом поля, затем в той же транзакции принятие: строка
  `disclosures`, ответ `accept` (с `consent_event_id` субъекта), `accepted`, процесс найма. «Не согласен» — ответ `decline`
  с `reason_code = representative_declined` (ранее принятая версия остаётся принятой). Кандидату — `invitation.representative_answered`,
  компании — `invitation.answered` с признаком `by_representative`.
- Повторное принятие во время ожидания отвергается (`409 awaiting_representative`); кандидат повторяет письмо (не чаще раза
  в 5 минут) или отменяет принятие отзывом своей стороны. Без представителя с `authority_verified` принятие отвергается
  `422 policy_violation` с кодом `representative_consent_required` и объяснением, чего не хватает.
- Если при принятии пересмотра подросток расширяет поля, раскрываются только поля, на которые согласился и представитель;
  отдельного запроса представителю на расширение в MVP нет.

### 13.7. `hiring_processes` и `hiring_reports` — процесс найма

Процесс найма начинается принятием приглашения и живёт отдельно от него: статус приглашения этапами найма не перегружается.

**`hiring_processes`**: `id`, `invitation_id` (`UNIQUE`), `company_id`, `candidate_id`, `opened_at` (момент принятия),
`outcome_due_at` (`opened_at` + `hiring_policy.outcome_due_days`), `policy_id`.

**`hiring_reports`** — append-only сообщения сторон.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |

| `party` | `enum` | да | `company` · `candidate` |
| `reported_by_user_id` | `id` | да | член компании или пользователь кандидата |
| `kind` | `enum` | да | `stage` · `outcome` |
| `stage` | `enum` | усл. | при `stage`: `interview_scheduled` · `interview_done` · `offer_made` · `offer_accepted` |
| `outcome` | `enum` | усл. | при `outcome`: `hired` · `not_hired` · `candidate_withdrew` · `company_stopped` · `no_contact` |
| `start_date` | `date` | нет | при `hired` — дата выхода |
| `reason_code` | `text` | нет | из справочника `hiring_policy` |

**Производное состояние** `hiringState(process, at)`:
- этап — наибольший этап, о котором сообщила хотя бы одна сторона, с указанием, кто сообщил;
- исход: `pending` (до `outcome_due_at`, сообщений об исходе нет) · `single_party` (сообщила одна сторона) · `confirmed` (обе сообщили
  согласованно: обе `hired` или обе — из группы «не нанят») · `diverged` (одна `hired`, другая — нет) · `unknown` (срок прошёл,
  напоминания исчерпаны, сообщений нет);
- `confirmed_at` — момент второго согласованного сообщения; время подтверждения — `confirmed_at − opened_at`.

**Инварианты.**
- Исход не выводится из молчания: без сообщений процесс остаётся `unknown`, а не «не нанят». Позднее сообщение переводит `unknown`
  в `single_party` или `confirmed`.
- Сообщение стороны не меняет сообщение другой стороны; расхождение видно обеим («другая сторона отметила иначе») без причин другой
  стороны и оператору ФСП в агрегатах.
- Компания в `suspended` сообщений не отправляет; кандидат может всегда. Оператор исходы не ставит.
- Напоминания: `hiring.outcome_request` в `outcome_due_at` обеим сторонам, затем `hiring.outcome_reminder` по расписанию
  `hiring_policy` до максимума повторов (раздел 3.7).

### 13.9. Воронка карьерных исходов (кабинет ФСП)

`careerFunnel(filters, dimensions)` — агрегаты для оператора ФСП, считаются из живых данных по стадиям **раздельно**, не как один
процент «трудоустройства»:

| Стадия | Считается по |
|---|---|
| Приглашены | кандидаты с хотя бы одним приглашением |
| Контакт | принятые приглашения (раскрытие состоялось) |
| Собеседование | процессы, где хотя бы одна сторона сообщила `interview_*` |
| Предложение | процессы с `offer_made` |
| Выход подтверждён | `confirmed` с `hired`; отдельно — подтверждённые одной стороной (`single_party`) и расхождения (`diverged`) |
| Не нанят | согласованный исход из группы «не нанят» |
| Исход неизвестен | `unknown` и `pending` после срока |

Разрезы (`FunnelDimension`): дисциплина ФСП, уровень ФСП (L1–L5), соревнование (любое, где у кандидата есть действующий результат
`competition_result`), роль и диапазон грейда из опубликованной категории (неустановленная ось — группа «не установлена»), регион (код
из предпочтений кандидата в том виде, в каком он указан сейчас; без региона — группа «не указан»), месяц приглашения, участник ФСП или
нет. Итог выборки считается всегда; к нему — до двух разрезов: строки и строки внутри каждой строки (вложенная группировка, а не
матрица: у каждой группы остаются все стадии). Фильтры: период отправки приглашений и значение любого разреза, кроме месяца
(API — параметры с именами разрезов, страница — дисциплина, уровень, роль, регион).

Кандидат с несколькими дисциплинами, уровнями, соревнованиями или месяцами приглашений учитывается вместе со своими процессами в каждой
своей группе; суммы строк таких разрезов не равны итогу, и страница пишет это рядом с таблицей. Дисциплина и уровень берутся парой:
уровень — в этой дисциплине, а при разрезе или фильтре по соревнованию — в дисциплине соревнования.

Малые группы. Порог — `catalog_policy.small_count_threshold` (5). Группа меньше порога отдельно не показывается: малые группы одного
уровня объединяются в строку «Малые группы», и к ней добавляются следующие по размеру, пока в ней не наберётся порог — иначе строку
«< 5» выдало бы вычитание из итога. У объединённой строки нет внутренних строк. Выборка или группа, оставшаяся меньше порога, показывает
все числа как «< 5», включая нули; внутри группы от порога ячейки от 1 до порога − 1 — «< 5». Пустая выборка показывает нули.
Разность между двумя запросами с разными фильтрами или периодами этим не закрывается; воронка доступна только оператору
(`fsp_analytics.read`), чтение в журнал не пишется.

У каждой цифры виден источник подтверждения (кто сообщил). Записи сидов (`seed_batch_id`) дают подпись «синтетика». Расчёт — двумя
запросами на любой объём (приглашения с процессами и отчётами; признаки приглашённых кандидатов) и одним к версиям политики найма.
Рядом — обратная связь «какие навыки ищет рынок ↔ какие даёт ФСП»: частота обязательных навыков вакансий за окно против навыков,
выведенных из фактов ФСП; это корреляция, а не доказанная ценность навыка, и подписана так же.

Удаление кандидата убирает его из воронки: агрегаты не хранятся, а считаются заново.

соревнования» и уровень ФСП; точные сведения и профили до контакта недоступны, `scope_fields` не принимается.

## 17. Задания фона

Все фоновые шаги (разбор, извлечение, эмбеддинги, синхронизация ФСП, импорт вакансий, пересчёт категории и соответствия, уведомления,
очистка) — задания одной таблицы `jobs`.
Модели и `docparse` вызываются из воркера синхронно по HTTP; своих очередей и повторов у них нет.

### 17.1. `jobs`

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | `id` | да | |
| `type` | `text` | да | из реестра типов |
| `type_version` | `integer` | да | версия обработчика; несовместимая смена формата `payload` — новая версия |
| `payload` | `jsonb` | да | параметры по схеме типа; без ПДн (только идентификаторы) |
| `input_version` | `text` | да | версия входа, для которой задание поставлено |
| `dedup_key` | `text` | нет | уникален среди **ожидающих**: `UNIQUE (dedup_key) WHERE status = 'queued'`; одновременно не больше одного `running` с тем же ключом (правило захвата) |
| `status` | `enum` | да | `queued` · `running` · `succeeded` · `discarded_stale` · `failed` · `cancelled` |
| `priority` | `integer` | да | |
| `run_after` | `ts` | да | отложенный запуск и пауза между попытками |
| `attempts`, `max_attempts` | `integer` | да | |
| `lease_owner` | `text` | нет | идентификатор воркера |
| `lease_expires_at` | `ts` | нет | срок владения; продлевается пульсом |
| `last_error` | `jsonb` | нет | код, признак повторяемости, сообщение без ПДн |
| `created_by` | `jsonb` | да | `{kind: user | system | webhook, id}` |
| `finished_at` | `ts` | нет | |

**Механика.**
- Постановка — в **той же транзакции**, что изменение данных, которое её вызвало (`INSERT … ON CONFLICT (dedup_key) WHERE status =
  'queued' DO NOTHING`): изменение без задания или задание без изменения невозможны.
- Захват: `SELECT … FOR UPDATE SKIP LOCKED` среди `queued` с `run_after ≤ now()`, у которых нет `running` с тем же `dedup_key`; установка
  `lease_owner`, `lease_expires_at = now() + срок типа`. Задание читает **текущую** версию входа в момент выполнения, а не версию на
  момент постановки.
- Падение воркера: задание с истёкшей арендой возвращается в `queued`, `attempts + 1`. Попытка сверх `max_attempts` → `failed`
  (видно администратору).
- **Условная запись результата.** Результат записывается одной транзакцией, которая проверяет: аренда всё ещё у этого воркера;
  `input_version` совпадает с текущей версией входа (например, документ всё ещё `is_current`, `profile_revision` не изменился);
  основания действуют (для синхронизации ФСП — согласие `fsp_import` и связь со спортсменом активны **на момент записи**). Несовпадение →
  результат отбрасывается, статус `discarded_stale`, это не ошибка.
- **Идемпотентность.** Эффекты привязаны к `job_id` или естественному ключу (`UNIQUE (job_id, operation)` в `ml_results`,
  `UNIQUE (resume_document_id, extractor_version)` в извлечениях, `source_record_ref` в фактах): повторная доставка не создаёт повторов.
- Отмена: при отзыве основания незавершённые задания этого кандидата и типа → `cancelled`; уже выполняющееся задание остановит условная
  запись.
- **Слияние обновлений.** Пока задание по ключу выполняется, новое изменение ставит одно ожидающее задание с тем же ключом; следующие
  изменения к нему присоединяются (конфликт по ключу). Выполняющееся задание, чья версия устарела, получает `discarded_stale`, а
  ожидающее обработает последнюю версию. Так версия 2, пришедшая во время выполнения версии 1, обрабатывается гарантированно.

### 17.3. Сверка «требуемая ↔ обработанная» и действительность производных

**Сверка.** Для каждого кандидата требуемая ревизия — `profile_revision`, обработанная — `input_revision` опубликованного расчёта
категоризации и ревизия действительных векторов и строк соответствия. Периодическое задание `derivations.reconcile` находит кандидатов,
у которых обработанная ревизия меньше требуемой и нет ожидающего задания, и ставит задание. Это страховка от потерь, а не основной путь:
основной — транзакционная постановка и слияние (раздел 17.1). Прогон, упёршийся в лимит на пачку, ставит своё продолжение под тем же
ключом `reconcile:{period}` — пока есть отставание, оно не ждёт следующего часового тика; публикация нового набора правил ставит
сверку текущего часа в своей же транзакции (`taxonomy/publish.ts`), не дожидаясь расписания.

Обработанная ревизия вида — наибольшая из ревизии сохранённого результата на действующем наборе правил (опубликованный расчёт с
`ruleset_id` действующего набора категоризации; векторы кандидата в пространстве `building`/`active`; строки `match_scores` с
`match_ruleset_id` действующего набора соответствия) и `input_version` успешного задания этого вида, созданного после записи
действующего набора (`jobs.created_at > created_at` набора). Действующий набор категоризации — старшая версия при опубликованной
таксономии, соответствия — старшая версия. Новый выпуск таксономии всегда приносит новые версии обоих наборов. Публикация
записывает набор с `created_at = clock_timestamp()` под блокировкой `jobs` в режиме `SHARE`. Пересчёт, не изменивший результат,
тоже считается обработкой. Сверка берёт кандидатов в статусах `onboarding`, `active`, `ineligible_age` с `profile_revision > 0` и
ставит задание на пару «ревизия + действующий набор» не больше одного раза (`created_by.id = derivations.reconcile`): упавшее видно
администратору и не повторяется каждый час, следующая правка профиля или новый набор делает вид снова должным.

**Пул вакансии после нового набора соответствия.** Вакансия с посчитанным пулом или строками `match_scores` без успешного
`match.refresh` своей стороны после записи действующего набора получает пересчёт вакансии, один раз на пару «ревизия + набор».
Сверка ставит сначала вакансии, затем кандидатов, батчами с общим лимитом. До пересчёта чтение наборы не смешивает.

**Немедленное исключение изъятого вклада.** Изъятие основания (отзыв согласия, отвязка, аннулирование, удаление или замена документа,
отклонение утверждения кандидатом) в своей транзакции:
1. переводит факты и утверждения в `withdrawn` / `annulled` / `invalidated`, увеличивает `profile_revision`;
2. поднимает `candidates.evidence_floor_revision` до новой `profile_revision`;
3. переводит опубликованный расчёт в `blocked`;
4. ставит задания пересчёта.

С этого момента и до пересчёта:
- векторы кандидата с `input_version < evidence_floor_revision` не участвуют в поиске: запрос каталога соединяет `embeddings` с
  `candidates` по этому условию; кандидат находится по FTS, а FTS-индекс строится только из действующих утверждений и обновляется в той
  же транзакции;
- строки `match_scores` с `candidate_revision < evidence_floor_revision` не используются (раздел 13.4);
- объяснения строятся только из вкладов, чьи факты и утверждения `active` на момент чтения; категория не показывается (`blocked`);
- кеши карточек и выдачи в Redis ключуются по `(candidate_id, evidence_floor_revision)` и `profile_revision`; изъятие делает их
  недостижимыми, отдельная инвалидация не требуется.

Добавление основания (новый факт, новое резюме) нижнюю границу не поднимает: прежние производные действительны до пересчёта.

## 19. Отзыв согласий и удаление

Каждый производный результат ссылается на свои основания: утверждение → факт; вывод → факты и утверждения (`contributions`); расчёт →
`input_refs`; вектор → `input_version`; раскрытие → событие согласия. Поэтому отзыв находит всё, на что он влияет.

### 19.1. Что происходит при каждом событии

| Событие | Немедленно (в транзакции отзыва) | Заданием | Что остаётся и почему |
|---|---|---|---|
| Отзыв `catalog_visibility` | `canShow` перестаёт давать `catalog`; кандидат исчезает из поиска и счётчиков | `match.refresh` для счётчиков пула | ранее выполненные раскрытия (компания — самостоятельный оператор); строки `disclosures` как доказательство законности передачи |
| Сужение `scope_fields` каталога (новый `grant`) | проекция `catalog` сразу без снятых блоков; квитанции уровня `exact` для компаний больше не выдаются, выданные отвечают `not_valid` | — | событие согласия |
| Отзыв `partner_pool` | кандидат исчезает из пулов партнёров соревнования | — | событие согласия |
| Отзыв `telegram_notifications` | канал `unlinked`, идентификатор чата стёрт | — | событие согласия |

**Реализация** (`src/lib/server/erasure/`, `src/lib/server/candidates/consents.ts`, `src/lib/server/consent/majority.ts`):
- **Отзыв `fsp_import`** — страница «Согласия» (`/me/consents`). В транзакции отзыва активные связи со спортсменом → `unlinked`
  (без действующего согласия связь не нужна; новое согласие создаёт новую связь, и импорт идёт заново), ожидающие `fsp.sync` →
  `cancelled`, все факты `fsp`, принесённые отозванными `grant`, → `withdrawn` (`status_reason = consent_revoked`), их утверждения
  и группы опыта → `invalidated`, изъятие поднимает ревизию и нижнюю границу (17.3) и блокирует опубликованный расчёт. Задание
  `consent.revocation_cleanup` удаляет физически сами строки этих фактов (с `payload`), их утверждения, группы опыта и квитанции
  (проверка квитанции после этого — «не найдено»), а также производные ревизий ниже `evidence_floor_revision`: векторы профиля,
  их ML-конверты, строки соответствия и неопубликованные расчёты категоризации, на которые не ссылаются возражения и оставшиеся
  строки соответствия; событие `facts.purged` — число фактов и источник. Факты других источников не трогаются.
- **Отвязка ФСП ID** изымает факты своих связей так же и ставит то же задание с `{athlete_link_id}` вместо `{consent_event_id}`
  (у отвязки нет события согласия; ключ — `revocation:link:{athlete_link_id}`): оно удаляет факты этой связи с утверждениями и
  квитанциями и производные ниже границы; `facts.purged` называет связь.
- **Отзыв `pd_processing`** — то же действие, что удаление учётной записи (ниже), с `revoke` от имени субъекта и причиной в
  журнале `processing_revoked`; со страницы «Согласия» ведёт ссылка на страницу удаления. Отзыв представителем подростка по ссылке
  письма (6.4) — `revoke` от имени связи и то же удаление без свежей аутентификации (её у представителя нет; основание —
  одноразовая ссылка на подтверждённый адрес).
- **Отзыв представителем** `catalog_visibility` и `fsp_import` — те же последствия, что у отзыва кандидатом (`consent/representative.ts`).
- **Удаление аккаунта** — `/account/delete`, для кандидата и работодателя. Нужна свежая аутентификация (3.4). Отказ с объяснением:
  последний активный владелец компании (5.3 — сначала передать владение) и учётная запись с действующей ролью персонала (роль
  снимает администратор). В одной транзакции: `revoke` `pd_processing` от субъекта, профиль → `deletion_pending` и `visibility =
  hidden`, незакрытые приглашения → `withdrawn`, связь с представителем → `ended (candidate_deleted)` с отзывом неиспользованных
  ссылок, пересчёт пулов вакансий, где кандидат учитывался, членство в командах → `removed` с отзывом созданных ключей API,
  ожидающие задания, называющие строки человека, → `cancelled`, учётная запись → `deletion_pending`, строка `erasure_ledger`
  (`requested_at`), `account.deletion_requested`, задание `account.purge` без отсрочки (периода отмены модель не задаёт). После
  фиксации — отзыв всех сессий и письмо-подтверждение прямо через почту: уведомление с отложенной доставкой не дожило бы до неё.
- **Совершеннолетие** — 7.3: задание ставит ежедневное расписание воркера.

### 19.2. Очистка аккаунта (`account.purge`)

| Хранилище | Действие |
|---|---|
| PostgreSQL | удаление строк кандидата: анкета, факты, утверждения, группы опыта, выводы, расчёты, назначения, уровни ФСП, квитанции, векторы, строки соответствия, извлечения, резюме, попытки, оценки и артефакты тестов, внешние профили, связи со спортсменом, внешние идентичности, представители и связи (кроме доказательств полномочий до их срока), версии условий приглашений и ответы (сами приглашения — до надгробия `id`, `company_id`, `status`: на них ссылаются `disclosures`), процессы найма и сообщения сторон, уведомления, каналы и доставки, согласия (кроме указанного ниже); `users` → надгробие |
| SeaweedFS | удаление объектов `files`; версионирование бакетов выключено |
| Redis | сессии, счётчики, кеши карточек |
| Временные файлы | `docparse` не хранит файлы после ответа (контракт); временные файлы воркера удаляются в `finally` |
| ФСП ID | внешний сервис: удаляется только связь у нас; учётка ФСП ID не затрагивается |
| Резервные копии | срок хранения копий не больше 30 дней; после восстановления из копии процедура восстановления повторно применяет `erasure_ledger` |

**Остаётся** (с отдельным основанием и сроком):
- `audit_events` — безопасность и учёт действий с ПДн (п. 8 ч. 2 ст. 19); ссылаются на надгробие `user_id`, содержат только
  идентификаторы и коды; удаляются по сроку журнала;
- `disclosures` и события `consent_events`, на которые они ссылаются, — доказательство законности переданного (ч. 3 ст. 9); без ФИО
  и контактов; срок — по `retention_policy`;
- `erasure_ledger`: `user_id`, `requested_at`, `purged_at` — список удалённых для повторного применения после восстановления копии.

**Реализация** (`src/lib/server/erasure/purge.ts`, `plan.ts`). Объекты хранилища удаляются **до** строк: сначала задание удаляет
все объекты файлов человека (резюме, артефакты попыток, копии документов полномочий вне срока), затем одна транзакция удаляет
строки и проверяет, что новых объектов не появилось. Сбой хранилища завершает попытку с `storage_unavailable` при нетронутых
строках — следующая попытка находит те же ключи и повторяет удаление (удаление отсутствующего объекта — успех), так что ни объект
без строки, ни строка без объекта не теряются. В Redis — сессии и счётчик неудачных входов учётной записи. Дополнительно к таблице выше:
соглашения, принятые от имени компании (`document_acceptances.company_id`), и документ полномочий компании остаются у компании;
строки команды (`company_members`) остаются с надгробием `user_id`; копия документа полномочий представителя остаётся до
`evidence_retention_until`, и задание ставит себя на следующий день после этой даты. Решение принято для каждого внешнего ключа
на `users` и `candidates` (`ERASURE_PLAN`); тест падает на ключе без решения и проверяет, что после очистки ни одна удаляемая строка
не называет удалённого человека. **Сроки `retention_policy`** применяет `retention.sweep`: раскрытия старше
`disclosure_retention_months` удаляются, вместе с ними — события согласий удалённых профилей, которые больше ничего не доказывают;
профиль, чья учётная запись не входила `inactive_candidate_purge_days`, получает `purge_after` через `inactivity_notice_days`
(сейчас 30) и уведомление `candidate.inactive_purge_scheduled` (почта — категория `account`); вход до этой даты снимает
`purge_after`, иначе начинается удаление, как по запросу, но согласие на обработку получает `lapse` от системы, а не `revoke`. Оба
срока — в `retention_policy` с версии 3; пока действует более ранняя версия, профили по неактивности не уведомляются и не удаляются. **Выгрузка своих данных** — страница
«Мои данные» (`/me/export`) и `GET /api/v1/me/data`: документ `fsp-career-data-export/v2` со всем, что платформа хранит о кандидате —
учётка со входом, ФСП ID и настройками уведомлений; профиль; резюме с извлечённым текстом; факты с утверждениями, стажем и
квитанциями; вся история расчётов категории (не только опубликованный) с навыками и уровнями ФСП; возражения; заблокированные
компании; соответствия видимым вакансиям; согласия с тем, кто их подписал; принятые соглашения; представители со сроком полномочий и
проверками; приглашения с версиями условий и ответами, кому что раскрыто; процессы найма; тесты с артефактами; уведомления; журнал
действий о кандидате. Не входят: хэш пароля и одноразовые токены, векторы профиля и записи обращений к моделям, очередь заданий —
технические производные того, что уже выгружено. Каждая выгрузка — событие `data.exported`; сотрудники компаний и платформы в
выгрузке названы компанией или ролью.

**Сброс демо-стенда** очищает все таблицы схемы, кроме справочников; тест сверяет список очищаемых таблиц со списком таблиц схемы, чтобы
новая таблица не осталась вне сброса. Настоящий персонал стенда (не засев и не клон) сброс не трогает: его учётки, пароли, роли,
почтовые каналы и настройки уведомлений остаются, очищаются только у засева и демо-сессий.

### 19.3. Демо-сессии

Демо-стенд смотрят несколько посетителей одновременно. Учётки героев сценария общие, поэтому посетитель входит не в них, а в
**демо-сессию** (`/demo`, только при `DEMO_MODE=true`): на первом входе создаётся строка `demo_sessions` и клоны всего состава
сценария (`seeds/demo.json`) — героев К-1…, участников компаний Ю-1…, оператора и администратора — со всем, что принадлежит
оригиналам. Выбор роли открывает сессию входа под клоном этой роли; роли внутри демо-сессии переключаются там же, ссылка с токеном
открывает ту же демо-сессию в другом браузере (работодатель и кандидат одного сценария рядом).

| Поле `demo_sessions` | Тип | Смысл |
|---|---|---|
| `join_token_sha256` | `sha256` | хэш токена ссылки; сам токен — только в куке браузеров посетителей |
| `seed_batch_id` | `text` | партия засева, чей состав склонирован |
| `expires_at` | `ts` | после этого момента сессия со всем своим удаляется |
| `own_resume_at` | `ts` | первая загрузка своего резюме посетителем |

**Что клонируется и что общее.** Решение принято для каждой таблицы и каждого внешнего ключа (`src/lib/server/demo/clone-plan.ts`;
тест падает на таблице или ключе без решения). Строка принадлежит сессии, если это её корень (`users`, `candidates`, `companies` с
`demo_session_id`) или её ссылка-«владелец» указывает на строку сессии; полиморфные владельцы — объект уведомления, владелец вектора,
вход ML-результата. Клон получает копии: учётки (новый адрес `…+demo-<сессия>@…`, без пароля), профили с фактами, утверждениями,
группами опыта, выводами, расчётами, квитанциями (новые идентификаторы), резюме с объектами в хранилище, извлечения, векторы,
строки соответствия, согласия; компании (ИНН оригинала: он уникален вне сессий и отдельно в пределах каждой сессии) с участниками,
вакансиями, приглашениями, версиями условий, ответами, найма,
раскрытиями; возражения, представительства, уведомления. Не копируются пароли, одноразовые ссылки, ключи API, каналы Telegram,
публикации внешних источников. Связь со спортсменом ФСП у клона активна и помечена сессией (`athlete_links.demo_session_id`): профиль клона
показывает «ФСП привязан», а вне сессий у спортсмена по-прежнему одна активная связь — у оригинала. Синхронизация с ФСП (вебхук,
пакет результатов, задание `fsp.sync`) связи сессий не видит: импортированные достижения клона остаются, повторно он не
синхронизируется. **Общие:** справочники, журнал, задания,
фоновые кандидаты и компании, внешние вакансии, представители (человек), рынок.

**Изоляция.** Действия внутри сессии меняют только её строки: приглашения, ответы, найм, возражения одной сессии не видны другой.
Строка, которая принадлежит одновременно оригиналу и другой сессии, в новую сессию не копируется (продукт такую строку
не создаёт — оригиналы из сессии не видны, — правило держит изоляцию и против записи в обход продукта). Внешние вакансии
общие для всех сессий. Действия компаний сессии с ними (заявка «это наша», вытеснение своей вакансией) видны только внутри
сессии и не меняют общую строку (13.3).

**Демо-актор** (`src/lib/server/access/demo-actor.ts`) — учётка засева (оригинал состава или фоновая) или клон демо-сессии. Любой
посетитель стенда действует в своей сессии как оператор ФСП и администратор, а оригиналы — шаблон каждой новой сессии, поэтому
кроме фильтров списков сервер держит второй барьер:

- **Действия, меняющие общее для всех посетителей**, — загрузка и предпросмотр пакета результатов ФСП, роли персонала, режим
  моделей — закрыты любому демо-актору (`requireStandChange`, `403` с объяснением); экран показывает плашку «в демо недоступно».
  Справочники, политики и юридические документы в кабинете администратора только для чтения — действий над ними нет.
- **Досягаемость персонала** (`StaffReach`) — строки своего места: клон достаёт только строки своей сессии, реальная учётка и учётка
  засева — только строки вне сессий. Это очереди и карточки оператора (проверка компаний, справочник компаний и модерация,
  возражения, полномочия представителей, конфликты даты рождения, попытки тестов, заявки «это наша вакансия», партнёрства) и решения
  по ним, файлы дел, аккаунты и роли персонала в кабинете администратора, история загрузок пакетов ФСП и журнал. Строки вне сессий —
  реальные учётки, оригиналы, фон — для клона не существуют вовсе: дело вне досягаемости — «не найдено». Фоновые кандидаты и
  компании остаются общими как объекты каталога (правило видимости ниже), но их дела клону-оператору не достаются: решение по общей
  строке изменило бы её для всех посетителей и реальных людей стенда, а дела сценария — у героев и компаний состава, которые сессия
  копирует.
- **Журнал** клон читает только о своей сессии: события её учёток и компаний, события о её кандидатах и открытие самой сессии.
- **Учётка засева** действует вне сессий: засев ставит сцены сценария действиями самого продукта от имени оригинала оператора.
  Посетителю она недоступна: вход через ФСП ID в учётку засева или клона отклоняется (и привязка ФСП ID клоном состава тоже;
  учётка, зарегистрированная посетителем в сессии, привязывает ФСП ID внутри своей сессии — личность занята или свободна в
  пределах сессии), браузер уходит на `/demo` с объяснением; пароль оригиналов не раздаётся.

**Вход через ФСП ID на демо-стенде.** Личность ФСП без учётки вне сессий входит внутри демо-сессии посетителя: есть сессия в
браузере — в ней, нет — открывается новая, как на `/demo`, в пределах бюджета адреса. Личность, учётка, профиль, связь со
спортсменом и импортированные достижения принадлежат сессии, видны только из неё и удаляются вместе с ней. Адрес хранится в форме
сессии. Другой посетитель тем же спортсменом получает свою учётку в своей сессии. Учётки из набора и клоны участников сценария
(`seed_batch_id` задан) через ФСП ID не входят. Собственная учётка сессии синхронизируется с ФСП по своему согласию. Вебхуки и
пакеты связи сессий не обновляют.

**Регистрация паролем на демо-стенде.** Регистрация по паролю, как и вход через ФСП ID «с нуля», создаёт учётку внутри демо-сессии
посетителя: адрес хранится в форме сессии, учётка видна только из неё и удаляется вместе с ней. Почта такой учётки считается
подтверждённой, письмо не отправляется. Вход и сброс пароля находят учётку сессии браузера первой, затем — вне сессий; учётке
засева сброс не отправляется.

**Видимость.** Зритель внутри демо-сессии S видит строки S и строки вне сессий, кроме **оригиналов состава**; зритель вне сессий
(реальный пользователь, оригиналы состава, анонимный посетитель) видит все строки вне сессий и не видит строк ни одной сессии
(`src/lib/server/demo/scope.ts`). Место строки — её корень: кандидат, компания (у вакансии, заявки, приглашения — компания-владелец),
его `demo_session_id` и `demo_original`; сессия зрителя — сессия его учётки. `demo_original` (у `candidates` и `companies`, только
вне сессий) засев ставит профилям героев и компаниям сценария — тем, кого клонирует сессия; фоновые кандидаты и компании не
помечены и видны из всех сессий. Внутри сессии у посетителя перед глазами клоны, поэтому оригиналы ему не показываются нигде: ни в
каталоге и карточке (`canShow`: профиль не своей сессии или оригинал — «не виден» в любом контексте, кроме своего профиля; отсюда
и отказ клону-работодателю в приглашении оригиналу), ни в выдаче вакансий кандидату, ни в поиске вакансий и вакансии по
идентификатору в API, ни в списке приглашений кандидата (приглашение компании вне досягаемости — «не найдено»), ни в очередях и
карточках оператора (проверка компаний, справочник компаний, возражения, представители, заявки «это наша вакансия», партнёрства)
и в его решениях: дело чужой сессии или оригинала — «не найдено», а клону-оператору и дело вне сессий (досягаемость персонала,
«Демо-актор» выше). Сопоставление и счётчик пула строят пары по тому же правилу со
стороны вакансии: вакансия компании сессии — с кандидатами своей сессии и с неоригиналами вне сессий, вакансия вне сессий — со
всеми кандидатами вне сессий; сторона кандидата строит те же пары (клон — с вакансиями своей сессии, оригинал — только с
вакансиями вне сессий). Скопированная вакансия приходит в сессию со счётчиком оригинала, и открытие сессии ставит ей пересчёт
(`match.refresh`), чтобы пул считался по клонам её сессии. **Агрегаты стенда** — воронка карьерных исходов, рынок категории,
обратная связь «рынок ↔ ФСП», число участников соревнований — считают только строки вне сессий, оригиналы в том числе, для
любого зрителя: сессия — копия состава, который уже посчитан, и её учёт задвоил бы выборки; отдельная воронка сессии не нужна — в
ней единицы людей, все её ячейки ушли бы под порог малых чисел. **Чем платим:** посетитель сессии не встречает оригиналов героев,
даже когда ищет их нарочно (оригинал и его клон неотличимы для посетителя, показывать обоих — путать); реальный пользователь и
оригиналы по-прежнему видят оригиналы. Пометка оригиналов — часть засева: партия с ней — новая версия засева, стенд со старой
партией сбрасывается и засевается заново.

**Пул партнёра в сессии.** Клон компании — та же компания внутри сессии: `companies.demo_clone_of` называет её оригинал (только у
клонов, проверка `companies_demo_clone_of`). Согласие фонового кандидата на пул соревнования (`partner_pool`, партнёры названы в
`choices`) засчитывается клону партнёра, когда называет его оригинал. Согласие, данное другой компании, клону не засчитывается.
Строк согласий сессия не копирует и при удалении не трогает. Отзыв согласия фоновым кандидатом действует во всех сессиях сразу.
Согласия героев — строки их клонов, партнёры в них переписаны на клоны компаний.

**Вход и журнал.** Открытие сессии — событие `demo.session_opened` (анонимный посетитель, адрес запроса; сколько строк и файлов
скопировано; `evicted_session` — сессия, уступившая место), удаление — `demo.session_purged` (сколько строк и файлов удалено,
заданий отменено, ссылок отцеплено). Новые сессии ограничены по адресу (правило `demoSession`: 60 за сутки — объём держит лимит
живых сессий); вход в роль сессии, которая у браузера уже есть (кука или ссылка), этот бюджет не тратит. Сами запросы
`POST /demo` — правило `demo`: 200 за 10 минут, чтобы жюри за одним адресом свободно переключало роли. Живых сессий на стенде не
больше 60; когда мест нет, новый посетитель получает место сессии, которой дольше всех не пользовались, если она молчит не меньше
20 минут, и отказ «попробуйте позже» — только когда заняты все. Сессия входа клона живёт не дольше демо-сессии: каждая
аутентификация сверяет `demo_sessions.expires_at`, сессия входа истёкшей или удалённой демо-сессии завершается. Каждый запрос клона
и заход на `/demo` с живой сессией отмечают её использование (Redis, рядом с сессиями входа; без отметки — время открытия). В
шапке кабинета клона — плашка «Демо-сессия, удалится через …» со ссылкой на `/demo`; она и сама страница `/demo` показывают время
до конца простоя, не позже `expires_at` и ночного сброса (00:00 UTC).

**Письма демо-сессии.** `demo_letters` — письма демо-сессии людям без учётки (законному представителю кандидата сессии) и сброс
пароля учётки, зарегистрированной в сессии: `id`, `demo_session_id` (FK на `demo_sessions`, `on delete cascade`), `kind` ∈
{`consents`, `disclosure`, `password_reset`}, `object_type`, `object_id` (объект письма, как в журнале: `representation`,
`invitation` или `user`), `recipient_masked` (адрес с маской `ab***@домен`), `subject`, `body_enc` (`enc`: текст письма,
зашифрован, контекст `demo_letters.body` — в нём одноразовая ссылка), `created_at`. Письмо представителю пишется только после
успешной отправки и только для кандидата с `demo_session_id`; сброс пароля учётки сессии сохраняется при выдаче токена, до
попытки отправки письма. Письма вне сессий не хранятся. В плане клонирования — корень сессии (`root`, `copy: false`), удаляется
вместе с сессией; при сбросе стенда — `clear`. Уведомления клонов не хранятся: страница собирает их из `notifications` так же,
как собрала бы доставка (у клонов нет `notification_channels`), кроме уведомлений старше сессии. Читает письма вошедшая учётка
сессии — все; гость, у которого есть только кука сессии, — только сбросы пароля; сброс удалённой учётки не показывается.

**Своё резюме посетителя** — отдельное согласие `demo_resume_upload` (взрослый клон-кандидат, отдельный экран); без него загрузка
в клон отклоняется. Профиль при загрузке снимается с показа в каталоге, срок демо-сессии сокращается до
`retention_policy.demo_own_resume_hours` от загрузки.

**Удаление.** Задание `demo.purge` раз в час завершает сессии, которыми не пользовались 8 часов (простой), и удаляет сессии с
истёкшим `expires_at`: все строки сессии, кем бы они ни были созданы
(факты, утверждения, извлечения, ML-результаты, векторы и соответствия своего резюме — тоже), объекты её файлов, сессии входа её
учёток; ожидающие задания по её строкам отменяются, журнал остаётся. Учётка, загрузившая своё резюме, попадает в `erasure_ledger`.
Строка вне сессии, которая ссылается на строку сессии, — утечка изоляции: удаление этой сессии останавливается с названной ссылкой,
кроме ссылок, которые план отцепляет (внешняя вакансия, заявленная клоном компании). Срок сессии — `retention_policy.demo_session_hours`.
Ночной сброс (19.2) очищает и демо-сессии.

## 20. ТЗ-зависимые поля и политики

Столбец «Новое» отмечает строки, добавленные вместе с агрегатором, соответствием, наймом, уведомлениями и квитанциями.

| Где | Что может заменить ТЗ | Как устроено, чтобы замена не ломала схему | Новое |
