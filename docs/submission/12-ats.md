# Интеграция с ATS работодателей

Работодатель ведёт найм в своей ATS (системе учёта кандидатов), и платформа не пытается её заменить: её задача — дать компании
подтверждённого кандидата, который принял предложение, и вернуть в платформу исход найма. Раздел описывает, что для этого есть в
продукте сейчас и что предлагается как следующий шаг.

## Сценарии

| Сценарий | Направление | Статус |
|---|---|---|
| Кандидат принял предложение → карточка кандидата с раскрытыми контактами появляется в ATS | платформа → ATS | данные доступны по API (опрос); доставка событием — развитие |
| Этапы найма (собеседование, оффер, выход) и исход отмечаются в ATS и отражаются в платформе | ATS → платформа | по API: `POST /api/v1/hiring/{process_id}/reports` |
| Вакансия заводится в ATS и публикуется на платформе | ATS → платформа | по API: создание, правка, публикация, пауза, закрытие вакансии |
| Потребность и подборка запрашиваются из ATS | ATS → платформа | по API: потребность текстом, рекомендованные категории, подборка с объяснением |

## Механизм

**Реализовано: публичный API с ключом компании.** Владелец компании создаёт ключ API с нужным подмножеством прав (раздел
«Описание API»); интеграция вызывает `/api/v1` с `Authorization: Bearer fspk_…`. Операции, нужные ATS:

| Операция | Что даёт |
|---|---|
| `GET /api/v1/invitations`, `GET /api/v1/invitations/{id}` | предложения компании со статусом и историей версий условий; курсорная пагинация |
| `GET /api/v1/invitations/{id}/contacts` | раскрытые контакты кандидата — только после принятия, только выбранные им поля, пока действует его согласие; каждое чтение пишется в журнал |
| `GET /api/v1/hiring/{process_id}`, `POST /api/v1/hiring/{process_id}/reports` | состояние процесса найма с расхождениями сторон; сообщение об этапе или исходе со стороны компании |
| `POST /api/v1/vacancies`, `PATCH /api/v1/vacancies/{id}`, `POST …/publish` | собственные вакансии; ответ содержит результат проверки текста |
| `POST /api/v1/needs`, `POST /api/v1/needs/{id}/shortlists`, `GET /api/v1/shortlists/{id}` | потребность и подборка с разложением счёта |

Создающие операции принимают `Idempotency-Key`: повтор запроса интеграцией после сетевого сбоя не создаёт дубль. Ключ действует
от имени членства создателя; приостановка компании или удаление сотрудника закрывает доступ ключу сразу.

**Предлагается: исходящие события с подписью HMAC.** Чтобы ATS не опрашивала API, платформа отправляет события на адрес,
который владелец компании регистрирует в кабинете вместе с секретом:

| Событие | Когда |
|---|---|
| `invitation.accepted` | кандидат принял версию условий и раскрыл контакты |
| `invitation.declined`, `invitation.expired` | кандидат отклонил с кодом причины; истёк срок ответа |
| `invitation.terms_answered` | ответ на новую версию условий после пересмотра |
| `hiring.reported` | кандидат сообщил этап или исход найма |

Устройство повторяет уже работающий в продукте входящий вебхук ФСП, только в обратную сторону:

- тело — только идентификаторы (предложения, процесса найма, псевдоним кандидата) и тип события; данные ATS забирает по API своим
  ключом, поэтому событие не переносит персональных данных и не обходит проверку прав и согласия;
- заголовки `X-Event-Id`, `X-Timestamp`, `X-Signature: sha256=<HMAC-SHA-256 от "{timestamp}.{rawBody}">` секретом подписки;
  получатель отвергает расхождение времени больше 5 минут и повторный `X-Event-Id`;
- доставка — фоновым заданием с повторами по экспоненциальной паузе при сетевой ошибке, `429` и `5xx`; другой `4xx` —
  окончательный отказ; журнал доставок виден владельцу компании;
- подписка — ресурс компании под той же политикой допуска, что ключи API: приостановленной компании события не отправляются.

**Предлагается: адаптер Хантфлоу.** Отдельный модуль-получатель событий для компаний, работающих в Хантфлоу: по
`invitation.accepted` создаёт кандидата в аккаунте компании и прикрепляет его к вакансии в выбранном статусе, по изменению статуса
в Хантфлоу (вебхук Хантфлоу) сообщает этап найма в платформу. Токен Хантфлоу хранит платформа зашифрованным, как остальные секреты
полей. Остальные ATS подключаются тем же путём — подпиской на события и API с ключом — без отдельного адаптера.

## Сопоставление этапов найма

Этапы платформы фиксированы и понятны обеим сторонам; статусы ATS настраивает каждая компания, поэтому сопоставление — настройка
подписки компании, а не код.

| Платформа | Смысл | Типичный статус ATS |
|---|---|---|
| предложение принято (`accepted`) | кандидат согласился на контакт, контакты раскрыты | новый кандидат на вакансии / первичный контакт |
| `interview_scheduled` | собеседование назначено | интервью назначено |
| `interview_done` | собеседование проведено | интервью пройдено |
| `offer_made` | оффер сделан | выставлен оффер |
| `offer_accepted` | оффер принят | оффер принят |
| исход `hired` с датой выхода | вышел на работу | вышел на работу |
| исход `not_hired`, `candidate_withdrew`, `company_stopped`, `no_contact` | найм не состоялся, с причиной | отказ (с причиной) |

Исход в платформе не выводится из молчания: пока ни одна сторона не сообщила, он остаётся «неизвестен»; расхождение сообщений
компании и кандидата видно обеим сторонам. Статус ATS, не сопоставленный ни с одним этапом, в платформу не передаётся.

## Права и согласие кандидата

- В ATS могут попасть только данные, которые кандидат раскрыл **этой** компании по **этому** предложению: раскрытие — согласие
  `contact_disclosure` с областью «компания + предложение + поля». До принятия ATS видит только псевдонимную карточку в той
  проекции, что и интерфейс.
- Каждое чтение раскрытых контактов по API пишется в журнал действий; отзыв согласия на раскрытие закрывает контакты для API так же,
  как для интерфейса. Данные, уже выгруженные в ATS, дальше обрабатывает работодатель как самостоятельный оператор персональных
  данных.
- Ключам API недоступны операции кандидата, персонала и управления ключами; каталог по ключу ограничен тем же лимитом частоты, что
  в интерфейсе, а выгрузка каталога целиком не предусмотрена.

## Что реализовано и что предлагается как развитие

**Реализовано:** ключи API компании с подмножеством прав и проверкой допуска на каждом запросе; операции предложений, раскрытых
контактов, процесса найма, вакансий, потребностей и подборок в `/api/v1` с описанием в OpenAPI; идемпотентность создающих
операций; курсорная пагинация; журнал чтения контактов; входящий вебхук ФСП с HMAC-подписью, дедупликацией и повторами — образец
для исходящих событий.

**Предлагается:** исходящие события для ATS с подписью HMAC и журналом доставок; адаптер Хантфлоу по его публичному API;
настраиваемое сопоставление статусов ATS с этапами платформы в кабинете компании.
