# Интеграция с ATS работодателей

Работодатель ведёт найм в своей ATS (системе учёта кандидатов), и платформа не пытается её заменить: её задача — дать компании
подтверждённого кандидата, который принял предложение, и вернуть в платформу исход найма. Раздел описывает, что для этого есть в
продукте сейчас и что предлагается как следующий шаг.

## Сценарии

| Сценарий | Направление | Статус |
|---|---|---|
| Кандидат принял предложение → карточка кандидата с раскрытыми контактами появляется в ATS | платформа → ATS | событие `invitation.accepted` вебхуком с подписью Standard Webhooks (HMAC-SHA-256); в Хантфлоу — кандидат создаётся адаптером; данные — по API |
| Статусы предложений, откликов и вакансий меняются на платформе → ATS узнаёт сразу, без опроса | платформа → ATS | события `invitation.*`, `application.*`, `vacancy.*` вебхуком по Standard Webhooks; данные — по API |
| Этапы найма (собеседование, оффер, выход) и исход отмечаются в ATS и отражаются в платформе | ATS → платформа | по API: `POST /api/v1/hiring/{process_id}/reports` |
| Вакансия заводится в ATS и публикуется на платформе | ATS → платформа | по API: создание, правка, публикация, пауза, закрытие вакансии |
| Потребность и подборка запрашиваются из ATS | ATS → платформа | по API: потребность текстом, рекомендованные категории, подборка с объяснением |

## Механизм

**Реализовано: публичный API с ключом компании.** Владелец компании создаёт ключ API с нужным подмножеством прав (раздел
«Описание API»); интеграция вызывает `/api/v1` с `Authorization: Bearer fspk_…`. Операции, нужные ATS:

| Операция | Что даёт |
|---|---|
| `GET /api/v1/invitations`, `GET /api/v1/invitations/{id}` | предложения компании со статусом и историей версий условий; курсорная пагинация |
| `GET /api/v1/invitations/{id}/contacts` | раскрытые контакты кандидата — только после принятия, только выбранные им поля, пока действует его согласие; каждое чтение пишется в журнал |
| `GET /api/v1/hiring/{process_id}`, `POST /api/v1/hiring/{process_id}/reports` | состояние процесса найма с расхождениями сторон; сообщение об этапе или исходе со стороны компании |
| `POST /api/v1/vacancies`, `PATCH /api/v1/vacancies/{id}`, `POST …/publish` | собственные вакансии; ответ содержит результат проверки текста |
| `POST /api/v1/needs`, `POST /api/v1/needs/{id}/shortlists`, `GET /api/v1/shortlists/{id}` | потребность и подборка с разложением счёта |

Создающие операции принимают `Idempotency-Key`: повтор запроса интеграцией после сетевого сбоя не создаёт дубль. Ключ действует
от имени членства создателя; приостановка компании или удаление сотрудника закрывает доступ ключу сразу.

**Реализовано: исходящие события (вебхуки) по спецификации Standard Webhooks.** Чтобы ATS не опрашивала API, платформа сама
отправляет события на адрес, который владелец компании регистрирует в кабинете («Профиль → События для ATS») или по API — в сессии
либо ключом, которому он выдал право `company.events.manage` (тогда интеграция регистрирует себя и меняет секрет сама):

| Событие | Когда |
|---|---|
| `invitation.sent` | компания отправила предложение, новую версию условий или открыла предложение заново |
| `invitation.viewed` | кандидат открыл предложение |
| `invitation.accepted`, `invitation.declined` | кандидат принял версию условий; отклонил с кодом причины |
| `invitation.expired`, `invitation.withdrawn` | истёк срок ответа; предложение отозвано компанией, закрытием вакансии или приостановкой компании |
| `contacts.disclosed` | кандидат раскрыл компании контакты (в событии — какие поля) |
| `hiring.reported` | сторона сообщила этап или исход найма |
| `application.received`, `application.status_changed` | кандидат откликнулся на вакансию; отклик просмотрен, отклонён, приглашён предложением или отозван кандидатом |
| `vacancy.published`, `vacancy.closed` | вакансия опубликована (впервые, после модерации, после паузы); закрыта |

- тело — `{id, type, occurred_at, company_id, data}`; в `data` только идентификаторы, статусы, коды и моменты, кандидат назван
  псевдонимом для этой компании. Контакты кандидата событие не переносит никогда: `contacts.disclosed` и `application.received`
  называют раскрытые поля, значения ATS читает по API своим ключом — с проверкой согласия и записью в журнал. Схема каждого события —
  раздел `webhooks` документа OpenAPI (`/api/v1/openapi.json`); она же типизирует код, который создаёт события, поэтому описание и
  отправка не расходятся;
- заголовки `webhook-id` (id события — одинаков при повторах, по нему получатель отбрасывает дубли), `webhook-timestamp`,
  `webhook-signature: v1,<base64 HMAC-SHA-256 от "{id}.{timestamp}.{тело}">`, ключ — секрет `whsec_…`, показанный один раз.
  Подходят готовые библиотеки Standard Webhooks для любого языка; пример проверки на Node.js — в описании API. Соответствие
  спецификации проверено её эталонным вектором в юнит-тесте;
- ротация секрета без простоя: сутки событие подписывается и новым, и прежним секретом (две подписи через пробел); секреты хранятся
  зашифрованными тем же механизмом, что другие чувствительные поля;
- событие создаётся в той же транзакции, что изменение статуса, и доставляется фоновым заданием: таймаут 10 с, повторы через 1, 5,
  15 минут, 1, 2, 4 и 6 часов (до 8 попыток) при сетевой ошибке, таймауте, `429` и `5xx`; другой ответ — окончательный отказ;
- журнал доставок в кабинете и по API: статус, число попыток, код последнего ответа, время последней попытки, ошибка. Недоставленное
  или пропущенное событие повторяется кнопкой «Повторить» или `POST …/deliveries/{id}/retry` — с тем же `webhook-id`; кнопка
  «Отправить тестовое событие» отправляет `ping`;
- адрес — только `https://` во внешней сети: частные, loopback и link-local адреса (в том числе IPv6 и IPv4, записанный как IPv6)
  отвергаются при регистрации и ещё раз при соединении — по адресу, в который разрешилось имя; редиректы не выполняются;
- подписка — ресурс компании под той же политикой допуска, что ключи API: приостановленной компании и подписке на паузе события
  не отправляются (в журнале — «пропущено»).

Ограничения: журнал хранит по каждой доставке последнюю попытку, а не историю всех попыток; API отдаёт 50 последних доставок
подписки. Адреса трансляции NAT64 (`64:ff9b::/96`) и 6to4 отдельно не фильтруются. Удаление учётной записи кандидата отзывает его
предложения без события — доставки по ним удаляются вместе с данными.

**Реализовано: адаптер Хантфлоу.** Модуль-получатель событий для компаний, работающих в Хантфлоу: по `invitation.accepted` создаёт
кандидата в аккаунте компании из контактов, раскрытых ей кандидатом (`POST /accounts/{id}/applicants`), и ставит его на вакансию в
выбранном статусе (`POST …/applicants/{id}/vacancy`); по этапу или исходу, о котором сообщила компания, переводит в сопоставленный
статус (`PUT …/applicants/{id}/vacancy`). Формы запросов сверены с открытым OpenAPI Хантфлоу v2. Токен Хантфлоу хранится
зашифрованным; на стенде адаптер включается переменной `HUNTFLOW_API_URL`, по умолчанию выключен. Talantix, Поток, E-Staff
подключаются тем же путём — подпиской на события и API с ключом — без отдельного адаптера; адаптеры для них — по тому же образцу.

## Сопоставление этапов найма

Этапы платформы фиксированы и понятны обеим сторонам; статусы ATS настраивает каждая компания, поэтому сопоставление — настройка
подписки компании, а не код.

| Платформа | Смысл | Типичный статус ATS |
|---|---|---|
| предложение принято (`accepted`) | кандидат согласился на контакт, контакты раскрыты | новый кандидат на вакансии / первичный контакт |
| `interview_scheduled` | собеседование назначено | интервью назначено |
| `interview_done` | собеседование проведено | интервью пройдено |
| `offer_made` | оффер сделан | выставлен оффер |
| `offer_accepted` | оффер принят | оффер принят |
| исход `hired` с датой выхода | вышел на работу | вышел на работу |
| исход `not_hired`, `candidate_withdrew`, `company_stopped`, `no_contact` | найм не состоялся, с причиной | отказ (с причиной) |

Исход в платформе не выводится из молчания: пока ни одна сторона не сообщила, он остаётся «неизвестен»; расхождение сообщений
компании и кандидата видно обеим сторонам. Статус ATS, не сопоставленный ни с одним этапом, в платформу не передаётся.

## Права и согласие кандидата

- В ATS могут попасть только данные, которые кандидат раскрыл **этой** компании по **этому** предложению: раскрытие — согласие
  `contact_disclosure` с областью «компания + предложение + поля». До принятия ATS видит только псевдонимную карточку в той
  проекции, что и интерфейс.
- Каждое чтение раскрытых контактов по API пишется в журнал действий; отзыв согласия на раскрытие закрывает контакты для API так же,
  как для интерфейса. Данные, уже выгруженные в ATS, дальше обрабатывает работодатель как самостоятельный оператор персональных
  данных.
- Ключам API недоступны операции кандидата, персонала и управления ключами; каталог по ключу ограничен тем же лимитом частоты, что
  в интерфейсе, а выгрузка каталога целиком не предусмотрена.

## Что реализовано и что предлагается как развитие

**Реализовано:** ключи API компании с подмножеством прав и проверкой допуска на каждом запросе; операции предложений, раскрытых
контактов, процесса найма, вакансий, потребностей и подборок в `/api/v1` с описанием в OpenAPI; идемпотентность создающих
операций; курсорная пагинация; журнал чтения контактов; входящий вебхук ФСП с HMAC-подписью; исходящие события для ATS по
Standard Webhooks — предложения, отклики, вакансии, найм — с повторами, журналом доставок, ручным повтором, ротацией секрета и
управлением подписками по ключу API; адаптер Хантфлоу по его открытому API v2.

**Предлагается:** обратный вебхук Хантфлоу (статус в ATS → этап на платформе) и обновление его токена; адаптеры Talantix, Поток,
E-Staff по образцу Хантфлоу; настраиваемое сопоставление статусов ATS с этапами платформы для вебхуков.
