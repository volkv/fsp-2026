# Сборка, развёртывание и локальный запуск

## Требования к машине

| Что | Требование |
|---|---|
| ОС | Linux с cgroup v2 (`stat -fc %T /sys/fs/cgroup` → `cgroup2fs`): песочнице исполнения кода нужны пространства имён и cgroup ядра. Остальные сервисы от ОС хоста не зависят |
| Инструменты | Docker с Compose v2, `make`, `git`. Node и Python на хосте для запуска не нужны — всё собирается в образах |
| Память | без нагрузки стек занимает около 1,4 ГБ вместе с моделью эмбеддера; прогон кода (до 512 МБ на программу) и разбор резюме добавляют около 1,2 ГБ. Ориентир — 4 ГБ свободной памяти |
| Диск | образы — около 6,5 ГБ (песочница с тулчейнами 2,6 ГБ, сервис разбора с LibreOffice 1,2 ГБ, рантайм эмбеддера 0,8 ГБ, приложение 0,7 ГБ, имитатор 0,5 ГБ, плюс образы PostgreSQL, Valkey, SeaweedFS, nginx, Mailpit), файл модели эмбеддера — 635 МБ, база демо-данных — около 0,3 ГБ |
| Сеть при первом запуске | загрузка базовых образов и файла модели эмбеддера с Hugging Face (по закреплённому коммиту, с проверкой SHA-256) |
| Модели `extract` и `rerank` | отдельно и по желанию: видеокарта NVIDIA с 12 ГБ памяти (раздел «Подключение моделей»). Без них продукт работает в режиме без модели |

## Локальный запуск одной командой

```sh
git clone <адрес репозитория> fsp-career
cd fsp-career
make up
```

`make up` создаёт `.env` из шаблона `.env.example` (если его нет; локальные секреты в шаблоне — только для этой машины), собирает
образы с хэшем текущего коммита и поднимает весь стек: PostgreSQL с pgvector, Valkey, хранилище SeaweedFS, Mailpit, сервис
разбора `docparse`, песочницу `sandbox` (оба — за своими шлюзами), имитатор ФСП `fsp-mock`, эмбеддер, приложение и воркер. Команда
ждёт, пока каждый сервис станет healthy (`docker compose up --wait`). Первая сборка занимает несколько минут: образы тулчейнов
песочницы и LibreOffice, первый старт эмбеддера скачивает модель.

Контейнер приложения при каждом старте до запуска сервера выполняет шаги, каждый из которых идемпотентен: миграции базы,
публикация справочников таксономии (роли, навыки, грейды, правила проекции ФСП), правовых документов, продуктовых политик,
выпусков банка заданий теста, регистрация пространства векторов. Упавший шаг не даёт приложению стать healthy и называет
причину в журнале. Воркер стартует из того же образа после приложения.

**Проверка, что всё поднялось.**

```sh
docker compose --profile app ps          # все сервисы — healthy
curl -s http://localhost:57300/api/health
```

| Адрес | Что |
|---|---|
| http://localhost:57300 | приложение |
| http://localhost:57300/api/docs | интерактивная документация API |
| http://localhost:57825 | Mailpit: письма подтверждения адреса и сброса пароля |
| http://fsp-mock.localhost:57610 | имитатор ФСП ID (страница входа с демо-учётками) |

Все порты хоста опубликованы только на `127.0.0.1` в диапазоне 57xxx. Если имя `fsp-mock.localhost` на хосте не разрешается
(`getent hosts fsp-mock.localhost` пусто), — строка `127.0.0.1 fsp-mock.localhost` в `/etc/hosts`. Остановить — `make down`
(тома сохраняются).

## Демонстрационные данные и учётные записи

Демо-режим включается в `.env` до запуска: `DEMO_MODE=true`, затем `make up`. Воркер сам засевает стенд после старта:
3000 синтетических кандидатов (около половины — с результатами ФСП на реальных соревнованиях, около половины — с текстовым
резюме), около 1400 вакансий и 24 компании; люди и компании вымышленные. Засев идёт по ходу — локально около 12 минут, данные
появляются в интерфейсе постепенно. Вернуть стенд к засеянному состоянию — `make demo-reset`.

Вход для проверки — страница `/demo`: выбор роли сценария (кандидаты, работодатели, оператор ФСП, администратор). Каждый
посетитель получает свою демо-сессию — копию героев сценария, компаний и их данных, поэтому действия одного проверяющего не видны
другим. Сессия без действий удаляется через 8 часов, в режиме экспертизы (`DEMO_REVIEW_MODE=true`) — через 7 суток. Роли и что в каждой есть — `README.md`, раздел «Демо-учётки».

Вход через ФСП ID с нуля — демо-спортсмен «Длинная история» на странице входа имитатора: учётки на платформе у него нет, он
проходит регистрацию. Регистрация по почте и паролю доступна всегда; письма стенда — в Mailpit.

Настоящий администратор (не демо) создаётся из окружения: `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` в `.env` — при
каждом старте приложение создаёт учётку или подтверждает её роль; пароль существующей учётки не меняется.

## Развёртывание на сервере

Демонстрационный стенд собран из отдельного файла `docker-compose.prod.yml`. Отличия от локального:

- на хост ничего не публикуется: трафик приходит через обратный прокси с TLS во внешней сети `proxy` — путь `/realms/fsp/*` ведёт на
  имитатор ФСП ID, всё остальное — на приложение;
- все сети стенда внутренние, выход наружу — только у `app`, `worker` и `embedder` через сеть `egress`;
- у каждого сервиса явный лимит памяти без свопа, Valkey — с паролем, песочница и разбор файлов исполняют по одному заданию;
- образы собираются на машине разработчика из закоммиченного HEAD (`git archive`) и доставляются на сервер `docker save | docker
  load` с тегом — коротким хэшем коммита; сервер ничего не собирает.

**Порядок.**

1. Сервер: Linux с cgroup v2, Docker с Compose v2, обратный прокси с автоматическим TLS (на стенде — Caddy) во внешней сети
   `proxy` с маршрутами выше.
2. Переменные: `.env.prod` на сервере (режим 600) создаёт `scripts/deploy/init-env.sh` из шаблона `.env.prod.example` —
   секреты (ключи шифрования полей, HMAC-секрет, ключ подписи квитанций, пароли PostgreSQL, Valkey и хранилища, секреты клиента
   ФСП ID, вебхуков и утверждений, пароль начального администратора) генерируются `openssl rand`. Имеющиеся строки скрипт не
   меняет никогда: ключи шифрования и подписи привязаны к записанным данным. Домен задаёт `PUBLIC_ORIGIN`.
3. Выкатка — `scripts/deploy/deploy.sh` с машины разработчика: сборка образов, доставка, файлы выкатки, `docker compose -f
   docker-compose.prod.yml --env-file .env.prod --env-file release.env up -d --wait` и проверка `GET /api/health` (ответ 200 с хэшем
   нового коммита). При провале скрипт сохраняет журналы и поднимает прошлую выкатку; `deploy.sh rollback` — откат вручную.
   Миграции не откатываются, поэтому откат образа допустим, пока между выкатками нет миграций, меняющих существующее.

**Основные переменные.**

| Переменная | Смысл |
|---|---|
| `PUBLIC_ORIGIN` | публичный адрес стенда; issuer имитатора ФСП ID — `{адрес}/realms/fsp` |
| `FIELD_ENCRYPTION_KEYS`, `FIELD_ENCRYPTION_ACTIVE_KEY`, `FIELD_HMAC_SECRET` | ключи шифрования полей (AES-256-GCM) и поиска по HMAC |
| `RECEIPT_SIGNING_KEYS`, `RECEIPT_ACTIVE_SIGNING_KEY` | ключи Ed25519 подписи квитанций; открытые части публикуются |
| `POSTGRES_*`, `REDIS_PASSWORD`, `S3_*` | хранилища |
| `FSP_ID_ISSUER`, `FSP_ID_CLIENT_ID`, `FSP_ID_CLIENT_SECRET`, `FSP_ID_REDIRECT_URI` | вход через ФСП ID; смена issuer переключает с имитатора на настоящий ФСП ID |
| `FSP_ACHIEVEMENTS_ADAPTER`, `FSP_ACHIEVEMENTS_BASE_URL`, `FSP_WEBHOOK_SECRET`, `FSP_ASSERTION_SECRET` | реестр достижений ФСП |
| `LLM_*`, `EMBED_*`, `RERANK_*` | адреса и сроки моделей; пустой адрес выключает операцию |
| `COMPANY_REGISTRY` | `egrul` — подсказка оператору из реестра юрлиц |
| `TELEGRAM_BOT_*`, `TELEGRAM_WEBHOOK_SECRET` | Telegram-уведомления; пусто — канал выключен |
| `DEMO_MODE`, `DEMO_NIGHTLY_RESET`, `DEMO_REVIEW_MODE` | демо-режим, ночной сброс, режим экспертизы (сессии живут 7 суток после последнего действия; только без ночного сброса) |
| `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_PASSWORD` | начальный администратор; пароль после первого старта убирается из окружения |

Полный перечень с комментариями — `.env.example` и `.env.prod.example`; приложение проверяет окружение схемой при старте и
останавливается с именем неверной переменной, не печатая значений.

**Бюджет памяти стенда.** Сервер общий с другими проектами: 4 CPU, 5,7 ГБ памяти. Лимиты (МБ, без свопа): песочница 1024, эмбеддер
896, `docparse` 768, приложение 640, PostgreSQL 640, воркер 512, имитатор 256, хранилище 256, Valkey 128, Mailpit 64, шлюзы по 32,
туннель 32 — всего 5280. Лимиты — потолки, а не резерв: без нагрузки стек занимает около 1,4 ГБ. Настройки PostgreSQL заданы явно
(`shared_buffers=128MB`, `work_mem=4MB`, `max_connections=40`); демо-засев 3000 × 1500 под этим лимитом проходит без нехватки
памяти с запасом около 235 МиБ.

**Valkey** (BSD-3-Clause, совместим с Redis по протоколу) заменяет Redis: клиент и переменные `REDIS_*` те же, на стенде — с паролем
`requirepass`.

**Ночной сброс демо-стенда.** В демо-режиме воркер каждую ночь в 00:00 UTC (03:00 МСК) возвращает стенд к засеянному состоянию:
всё, что сделали за день, включая регистрации, уходит; справочники, правовые тексты, политики и прогоны оценки качества остаются.
Выключить — `DEMO_NIGHTLY_RESET=false` в `.env.prod` (по умолчанию включён) и `docker compose up -d`: тогда сброс не планируется,
демо-сессии живут до своего срока, а стенд чистится вручную командой `node build/demo/main.js reset` в контейнере воркера.
Ночь, поставленная в очередь до выключения, при запуске перепроверяет флаг и ничего не сбрасывает.

**Резервные копии.** Ежесуточный `pg_dump -Fc` базы и зеркало тома хранилища вне сервера. Восстановление сначала выгружает реестр
удалений из живой базы и применяет его к восстановленной до старта приложения — удалённые после снятия копии учётки не
возвращаются. Дамп читается только с тем же `.env.prod`: зашифрованные поля требуют тех же ключей.

## Подключение моделей

Продукт работает и без моделей (раздел «Описание решения и архитектура», «Модели и обработка текста»). Эмбеддер входит в стек и
работает на CPU. Разбор текста (`extract`) по умолчанию идёт во внешнюю модель Gemini Flash через OpenAI-совместимый шлюз — нужен
только ключ в `LLM_API_KEY`, без него текст разбирают правила (`docs/models.md`, «Три режима»). Своя модель вместо внешней и
реранкер (`LLM_RUNTIME=vllm`, `RERANK_*`) поднимаются отдельно — на машине с GPU в закрытом контуре:

| Операция | Модель | Рантайм | Память |
|---|---|---|---|
| `rerank` | `BAAI/bge-reranker-v2-m3` | vLLM 0.30.0, `vllm serve … --runner pooling` | 1,6 ГБ видеопамяти |
| `extract` | `Qwen/Qwen3-8B-AWQ` | vLLM 0.30.0, structured output по JSON Schema | 8,9 ГБ видеопамяти |
| `embed` | bge-m3 GGUF Q8_0 | llama.cpp server (сервис `embedder`) | до 896 МБ ОЗУ |

**Порядок запуска — сначала реранкер, потом `extract`:** холодный старт `extract` оставляет около 1 ГБ временной памяти компиляции,
после чего реранкер на карту 12 ГБ уже не помещается. Флаги запуска и их обоснование — `docs/models.md`. Подключение к приложению —
переменные `LLM_BASE_URL`, `LLM_MODEL`, `RERANK_BASE_URL`, `RERANK_MODEL` (пустой адрес — операция выключена). На стенде модели
приходят через обратный SSH-туннель в отдельную внутреннюю сеть; машина с GPU выключена — порты закрыты, продукт сразу идёт по пути
без модели. Администратор выключает и включает каждую операцию на странице моделей без перезапуска.

## Сборка из исходников и проверки качества кода

Для разработки нужны Node 24 (`.nvmrc`) и pnpm 12 через corepack:

```sh
corepack enable
pnpm install
make infra          # инфраструктура без приложения
make db-migrate
make db-seed-taxonomy
pnpm db:seed-legal && pnpm db:seed-policies && pnpm db:release-bank
make dev            # http://localhost:57173
```

| Команда | Что проверяет |
|---|---|
| `pnpm check:fast` | Prettier и ESLint, `svelte-check` (TypeScript strict, предупреждения — ошибки), unit-тесты Vitest |
| `pnpm test:integration` | integration-тесты на настоящих PostgreSQL, Valkey, песочнице и Keycloak в контейнерах Testcontainers |
| `pnpm test:e2e` | сквозные сценарии Playwright на собранном приложении со своей базой |
| `pnpm check:image` | образ приложения запускается стартовой командой на пустой базе и становится healthy |
| `pnpm check:docparse`, `pnpm check:fsp-mock`, `pnpm check:eval` | ruff и pytest сервиса разбора и стенда оценки, tsc и тесты имитатора — в своих образах без сети |
| `make check-all` | полный гейт: всё перечисленное подряд, остановка на первом красном |

## Сборка этой документации

```sh
pnpm docs:build
```

Команда собирает `build/docs/fsp-career-documentation.pdf` и `.docx` из разделов `docs/submission/*.md`: таблица технологий
генерируется из lock-файлов с проверкой лицензий (сборка останавливается на запрещённой лицензии), перечень операций API — из
документа OpenAPI приложения (рядом кладётся `openapi.json`), диаграммы Mermaid отрисовывает mermaid-cli, разметку переводит pandoc,
PDF печатает Chromium из Playwright. pandoc и mermaid-cli запускаются в закреплённых по дайджесту контейнерах без сети, поэтому
сборке нужны только Docker и установленные зависимости проекта.
