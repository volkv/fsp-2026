# Оценка качества ML

Стенд измеряет, как продукт читает резюме, нормализует навыки, категоризирует кандидатов и ранжирует их под вакансию, и
что в этом меняют данные ФСП и тесты платформы: на синтетической выборке с независимой разметкой, со сравнением с
базовыми вариантами и порогами, зафиксированными заранее. Продукт настраивается на части dev; отложенная часть (holdout) —
для итоговой меры, и каждое обращение к ней записывается в журнал до прогона. Итог прогона — строка `eval_runs` с файлом
отчёта, которую показывает панель качества (`/admin/quality`). Итоги прогонов и выводы — [`REPORT.md`](REPORT.md).

Стенд не содержит копии продуктовой логики. Разбор, извлечение, нормализация, категоризация и ранжирование выполняются
кодом приложения через мост `src/eval` (сборка `.eval-build/main.js`): Python генерирует документы, вакансии и разметку,
считает метрики и базовые варианты, мост прогоняет продукт.

## Что измеряется

`n` у каждой метрики — число объектов, на которых она посчитана. Формат ключей и записи — шапка
`src/lib/server/admin/quality.ts`; подписи панели — `src/lib/components/admin/model.ts`, тест
`src/eval/panel-labels.test.ts` сверяет их с ключами закоммиченных отчётов (`reports/`).

`n` — вакансии, под которые в пуле есть хоть один релевантный человек. Все варианты ранжируют один и тот же пул (все люди
выборки) под одни и те же вакансии. Отчёт добавляет парные бутстреп-интервалы разностей (95 %, 2000 повторов по
вакансиям), разбивку на «алгоритмические» и прочие вакансии, те же ранжирования против прочтения рубрики без роли и по
каждой вакансии — первые десять каждого варианта с релевантностью и оценкой продукта по компонентам.

## Разметка независима от продукта

Сначала генератор решает, кто человек: роль, стек, грейд, стаж, карьера с датами, строки достижений с навыками, раздел
навыков, языки, образование, строки ответственности. Документ только показывает этот профиль; разметка читается из
профиля (`src/fsp_eval/gold.py`), а не из ответа системы.

- Написания навыков (`src/fsp_eval/lexicon.py`) собраны для стенда вручную — так пишут в резюме, — а не взяты из
  синонимов таксономии. Оба списка описывают одну практику, поэтому многие написания совпадают с алиасами: прогон меряет
  долю (`skills.lexicon_overlap`) и отдельно — срез незнакомых таксономии написаний (`.unfamiliar`).
- Грейд задаёт рубрика стенда (`GRADE_MONTHS`: месяцы опыта в роли для каждого грейда; ведущий ещё и руководит людьми),
  а не правила категоризации продукта.
- Отрицания («Планирую изучить Rust») в разметку навыков не входят; опечатки — входят с исходным ключом.
- Недостаточные резюме заданы явно: `no_dates` — опыт без дат, `skills_only` — студент с двумя общими навыками.
- Люди, организации и учебные заведения вымышлены; контакты — `example.com` и номера `+7 900 000-…`.

## Абляция с данными ФСП

Слой `datasets/fsp-achievements-v2` лежит поверх выборки резюме (`base_dataset`) и решает для каждого профиля, выступает
ли человек в спортивном программировании и что о нём знает федерация: результаты с нормами, присвоенные разряды, сборная.
Запись идёт в формате источника — одна страница `fsp-achievements/v1`, — мост читает её схемой адаптера продукта, а факты
и утверждения строит так же, как синхронизация ФСП. Запись следует за человеком (`src/fsp_eval/fsp.py`).

Разметка читается из записи рубрикой стенда: уровень дисциплины — наивысший по опубликованной шкале (МС и выше или
основной состав сборной — L5, КМС или резерв — L4, I разряд — L3, II–III — L2, юношеский разряд или любой официальный
результат — L1); роль запись обосновывает, когда в ней есть официальный результат продуктовой дисциплины с личной
специализацией, называющей роль; грейд запись не обосновывает.

Прогон категоризирует людей с записью ещё раз — снимок из резюме плюс достижения. Обе строки метрики считаются **на одних и
тех же людях**: знаменатель задан разметкой, а не тем, что обосновывают основания варианта.

| Метрика (`categorization.<метрика>.without_fsp` / `.with_fsp`) | Что это                                                                                               |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `role_established`, `grade_established`                        | доля людей с установленной осью                                                                       |
| `role_found`                                                   | доля людей, поставленных в их собственную роль: находимость по роли                                   |
| `role_accuracy`                                                | роль человека среди людей, чью роль обосновывают полные основания (резюме или запись); отказ — промах |
| `role_wrong_rate`                                              | доля людей, поставленных в чужую роль (меньше — лучше)                                                |
| `refusal_rate`                                                 | доля людей без роли                                                                                   |
| `grade_in_range`                                               | как в таблице резюме, на людях с датированным опытом                                                  |

Уровень ФСП в абляцию не входит: без записи уровня нет по построению, «прирост» был бы тавтологией. Он измеряется отдельно:
`categorization.fsp_level_accuracy` и `categorization.fsp_level_coverage`. Порогов у абляции нет: это измерение пользы, а
не планка приёмки.

## Соответствие: слой вакансий и истины

Слой `datasets/synthetic-matching-v1` лежит поверх выборки резюме и слоя ФСП (`src/fsp_eval/matching.py`). До любого
ранжирования он решает по своей рубрике, не глядя на продукт:

- **какие навыки у человека есть на самом деле**: использованный в работе (строка достижения, должность) — есть; только
  перечисленный в разделе навыков — есть с вероятностью 0,7; навык роли, не написанный нигде, — с вероятностью 0,15;
  «планирую изучить» — нет. Алгоритмы есть у человека с официальным алгоритмическим результатом уровня L2 и выше, с
  вероятностью 0,5 — на L1 и 0,1 — без записи: это модель мира, в которой посылка продукта «результат соревнования говорит
  о навыке» верна, и единственное место, где слой ФСП входит в истину;
- **грейд** — генератора; студент без опыта — стажёр;
- **тесты платформы**: половина людей проходит один-два теста банка (`assessments/`) по навыкам, которые заявляет или
  имеет; тест сдан на уровне человека с вероятностью 0,9, если навык есть, и на junior с вероятностью 0,05, если нет. В
  продукт попадает только сданный тест.

Вакансии — из ролей и стеков словаря: язык стека и ещё два навыка обязательны, два желательны, диапазон грейда из одного
или двух грейдов; часть инженерных вакансий требует ещё алгоритмы. **Релевантность** человека для вакансии, 0–3: 0, если
на самом деле есть меньше половины обязательных навыков; иначе 1, плюс 1, если есть все обязательные, плюс 1, если грейд
внутри диапазона; человек другой роли — не выше 1. Выигрыш позиции — `2^rel − 1`, дисконт — `1/log2(i + 2)`.

Мост ранжирует в своём каталоге: команда `rank` создаёт временную базу рядом с базой приложения (`eval_rank_<hex>`
на том же сервере; пользователю базы из `.env` нужно право `CREATEDB`), мигрирует её миграциями checkout, публикует
таксономию и банк заданий checkout, заводит каждого человека кандидатом по разу на набор оснований (резюме; резюме и
ФСП; резюме и тесты; всё) — строками, которые пишет `resume.extract`, фактами и утверждениями ФСП, как синхронизация, и
тестами через начисление баллов модуля заданий, — категоризирует обработчиком `categorization.compute` из очереди задач и
для каждой вакансии вызывает `scoreCandidatesForVacancy` с реранкером адаптера моделей или без него. База удаляется в
конце команды при любом исходе. Равные оценки продукт упорядочивает по id кандидата; стенд выдаёт id по порядку запроса,
так что повторный прогон без реранкера даёт те же числа. Реранкер на vLLM сам по себе даёт разброс порядка ±0,01–0,02
nDCG между прогонами: варианты сравниваются внутри одного прогона.

С `--semantic` каталог получает векторы так же, как стенд: мост регистрирует пространство `EMBED_SPACE_ID` и выполняет
задание `embedding.reindex` продукта с настроенным эмбеддером (`EMBED_*`, сервис `embedder` из `make infra`), затем
ранжирует каждый вариант с активным пространством или без него (режим «только слова»). Векторы продукт строит только для
кандидатов с действующим согласием на обработку, поэтому в таком каталоге каждый кандидат — совершеннолетний, давший
согласие по документу, который мост публикует во временной базе. Без эмбеддера `--semantic` — ошибка прогона, а не
ранжирование без семантики; компонент, посчитанный лишь для части вакансий, тоже.

## Выборка и разбиение

Манифест `datasets/<id>/manifest.json` фиксирует сид, размер, дату отсчёта (`as_of`), долю holdout и хеш всех профилей с
разметкой. Разбиение — по исходным профилям: профиль целиком в dev или в holdout (по хешу сида и id). Семейство шаблонов
принадлежит dev, holdout или обоим:

| Семейство       | Формат                                         | Язык | Даты                                 | Выборка       |
| --------------- | ---------------------------------------------- | ---- | ------------------------------------ | ------------- |
| `pdf_classic`   | PDF, одна колонка                              | ru   | «Март 2021 — настоящее время»        | dev           |
| `docx_headings` | DOCX, заголовки-стили, должность до периода    | ru   | «03.2021 – н. в.»                    | dev           |
| `pdf_sidebar`   | PDF, боковая колонка с навыками и языками      | ru   | «2019 — 2021» (только годы)          | dev           |
| `docx_table`    | DOCX, опыт таблицей                            | en   | «Jan 2020 – Present»                 | dev и holdout |
| `pdf_hh`        | PDF в духе выгрузки hh.ru: период и стаж слева | ru   | «Сентябрь 2019 — по настоящее время» | holdout       |

`pdf_hh` на dev не встречается никогда; табличная вёрстка DOCX есть и там, и там: её проблемы ищутся и чинятся на dev, а
меряются на профилях holdout. Мера честна, пока на holdout не смотрели при правках, — сколько раз смотрели, показывает
журнал (раздел ниже).

Текущие версии: выборка `synthetic-resumes-v2` (400 профилей, генератор 2), слой `fsp-achievements-v2`, слой
`synthetic-matching-v1` (по 40 вакансий на dev и holdout). Выборка v1 и её слой ФСП выведены: holdout v1 использовался
для правок продукта, и генератор 2 его не воспроизводит; записанные на v1 прогоны остаются в `eval_runs` со своим id.

Документы в репозиторий не кладутся: генерация детерминирована (сид, фиксированные даты в метаданных файлов, закреплённые
версии библиотек в `uv.lock`), документы рендерятся при каждом прогоне в `out/`, а проверка хеша разметки отказывает
генератору, который её больше не воспроизводит. Изменился генератор — новый id выборки или слоя и новый манифест:
`python -m fsp_eval manifest …`, `fsp-manifest …`, `matching-manifest --id … --seed … --dataset … --fsp-layer …
--vacancies …`.

## Журнал holdout

Каждый прогон на holdout показывает его числа тому, кто запускает; после этого настройка продукта уже не независима от
них. Поэтому обращения к holdout считаются: `reports/holdout/journal.json` перечисляет их — набор, режим, ревизия, дата,
кто, зачем, файл отчёта и что он показал. Стенд не запускает прогон на holdout, пока в журнале нет его записи: тот же
набор и режим, ревизия, которую сообщает сборка моста (не короче 12 знаков), сегодняшняя дата (UTC), непустые «кто» и
«зачем». Ревизия — коммит и только он: мост, собранный из дерева с незакоммиченными правками (изменённые, добавленные
в индекс или неотслеживаемые файлы; игнорируемые — `out/`, `.env`, сборки — не в счёт), сообщает коммит с суффиксом
`-dirty` (`src/eval/bundle.config.ts`), и на holdout такой прогон не пускается при любой записи в журнале. `APP_COMMIT`
из окружения сборка моста берёт, только если дерево чистое или значение само помечено `-dirty`. Прогон на dev идёт и с
такой сборкой; ревизия пишется в отчёт и в `eval_runs` как есть. Порядок:

1. внести запись (`report` и `seen` — `null`) и прогнать `--split holdout`; сводка прогона печатает, каким по счёту
   обращением к набору он стал, отчёт хранит его в `holdout_access`;
2. положить `summary.json` в `reports/holdout/`, вписать в запись файл и главные числа, закоммитить вместе.

`--split` обязателен: голый `run` не выбирает holdout сам. Набор, на holdout которого правили продукт, объявляется
просмотренным (`status` в журнале), и его числа перестают быть независимой оценкой; следующая независимая мера — новый
holdout.

## Пороги

`thresholds.json` — планка, зафиксированная заранее (дата и основание — в файле). У ранжирования два порога: абсолютный
nDCG@10 и относительный — нижняя граница интервала разности с поиском по ключевым словам не ниже нуля: продукт, который
хуже этого поиска на той же выборке, не проходит, какой бы ни была абсолютная величина. Прогон записывает пороги
вместе с метриками; порог метрики, которую прогон не считает, — ошибка прогона. Метрика вне порога или не посчитанная при
заданном пороге — провал: панель показывает её как «порог не пройден» или «порог задан, не посчитано», а `run` после
записи отчёта (и строки, если просили) завершается с кодом 1 и перечисляет провалы. Пороги меняются отдельной правкой и
только до первого прогона на новом holdout.

## Запуск

Нужны инфраструктура (`make infra`: PostgreSQL, хранилище, `docparse`, эмбеддер), мигрированная база (`pnpm db:migrate`)
и `.env`.
Стенд работает в своём образе (Python 3.13, зависимости из `uv.lock`, шрифт DejaVu, Node той же версии, что у приложения)
с сетью хоста: мост ходит в `docparse`, базу, хранилище и модели по адресам из `.env`.

```sh
pnpm eval:build                                                   # сборка моста .eval-build/main.js
pnpm eval:run --split dev --mode rules_only --semantic            # прогон, отчёт в tools/eval/out/runs/
pnpm eval:run --split dev --mode rules_only --semantic --record admin@…  # и строка eval_runs с файлом отчёта
pnpm eval:run --split holdout --mode rules_only --semantic        # только с записью в журнале holdout
pnpm check:eval                                                   # ruff и pytest в тестовом образе, без сети
```

Прямой вызов образа — `python -m fsp_eval run --repo <checkout> --out <каталог> --split dev|holdout
[--mode rules_only|model] [--semantic] [--record <почта администратора>] [--fsp-layer <id>|none] [--matching <id>|none]
[--env-file <файл>] [--concurrency N]`; `render --split …` пишет документы выборки для просмотра.

Режим `model` вызывает модель через адаптер приложения (`LLM_*` в `.env`); документ, по которому модель не ответила,
продукт читает правилами, и прогон это пишет: `processing_mode` — `model`, `rules_only` или `partial`, сколько
документов прочитано каждым путём — `documents_by_mode` отчёта (и первая строка сводки), у документа — `model_failure`. Реранкер ранжирования — `RERANK_*` в `.env`; без него `.without_reranker` не считается. Эмбеддер —
`EMBED_*` (для моста на хосте — `http://127.0.0.1:57820`, `bge-m3`, пространство из `docs/development.md`, «Эмбеддер»);
векторы каталога dev (≈ 1100 кандидатов) считаются на четырёх потоках CPU несколько минут. Concurrency прогона в режиме
`model` — 8 (не выше `LLM_MAX_CONCURRENCY`). Модели стенда на машине с GPU — `docs/models.md`.

Каталог прогона `out/runs/<время>-<выборка>-<split>-<режим>/`:

- `report.json` — строка `eval_runs`, провалы порогов, время извлечения, раздел соответствия (интервалы, разбивки, первые
  десять по вакансиям) и по каждому документу — семейство, хеш файла, итог разбора, разметка, что извлёк продукт, основная
  категория, не прошедшие проверку цитаты, для человека с записью ФСП — её разметка и категория с ней;
- `summary.json` — то же без документов и разбора по вакансиям: его кладут в `reports/` рядом с кодом;
- `recorded.json` — с `--record`: id строки `eval_runs` и файла отчёта.

С `--record` мост кладёт `report.json` в хранилище файлом назначения `export`, владелец — администратор с указанной
почтой (активная роль `admin`), и связывает его со строкой (`report_file_id`): ссылка «Скачать отчёт» на панели отдаёт
этот файл после проверки прав. Объект пишется до строк; если вставка не удалась, он удаляется.

## Мост

`node --env-file=.env .eval-build/main.js` читает один JSON-запрос из stdin и пишет один JSON-ответ в stdout; ошибка —
код 1 и текст в stderr, прогон останавливается, частичные числа не пишутся.

| Команда      | Что делает                                                                                                                                                                                                                                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `info`       | ревизия сборки и версии: таксономия (метка и хеш содержимого), правила категоризации, правила разбора резюме, схема извлечения                                                                                                                                                                                         |
| `extract`    | файлы → `docparse` (клиент приложения) → извлечение (модель или правила) → строки доказательств → снимок для категоризации; цитата каждого утверждения с блоками разбора, отказы по причинам, время шагов                                                                                                              |
| `normalize`  | написания → ключи навыков                                                                                                                                                                                                                                                                                              |
| `categorize` | снимки профилей, при необходимости с записью ФСП → роль, диапазон грейда, стек, уровни ФСП, недостающие основания                                                                                                                                                                                                      |
| `rank`       | кандидаты (строки резюме, запись ФСП, сданные тесты) и вакансии → ранжирование продукта каждого набора кандидатов под каждую вакансию во временной базе, с реранкером и семантической близостью по варианту; по каждому варианту — для скольких вакансий компонент посчитан и почему нет, первые десять с компонентами |
| `record`     | строка `eval_runs` с файлом отчёта, проверенная схемами панели качества до вставки и прочитанная ими после                                                                                                                                                                                                             |

Таксономия и банк заданий берутся из того же checkout — тех же файлов, из которых публикуются версии в базе.
