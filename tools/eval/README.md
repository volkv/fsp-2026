# Оценка качества ML

Стенд измеряет, как продукт читает резюме, нормализует навыки, выводит уровни ФСП и собирает подборку под потребность,
и что в этом меняют данные ФСП и тест на грейд: на синтетической выборке с независимой разметкой, со сравнением с
базовыми вариантами и порогами, зафиксированными заранее. Продукт настраивается на части dev; отложенная часть (holdout) —
для итоговой меры, и каждое обращение к ней записывается в журнал до прогона. Итог прогона — строка `eval_runs` с файлом
отчёта, которую показывает панель качества (`/admin/quality`). Итоги прогонов и выводы — [`REPORT.md`](REPORT.md).

Стенд не содержит копии продуктовой логики. Разбор, извлечение, нормализация, расчёт доказательств и подборка выполняются
кодом приложения через мост `src/eval` (сборка `.eval-build/main.js`): Python генерирует документы, вакансии и разметку,
считает метрики и базовые варианты, мост прогоняет продукт.

## Что измеряется

`n` у каждой метрики — число объектов, на которых она посчитана. Формат ключей и записи — шапка
`src/lib/server/admin/quality.ts`; подписи панели — `src/lib/components/admin/model.ts`, тест
`src/eval/panel-labels.test.ts` сверяет их с ключами закоммиченных отчётов (`reports/`).

### Подборка по потребности

Методика v3 — раздел «Методика v3» ниже: ключи `shortlist.*`, их базовые варианты и как устроен путь. `n` — потребности,
под которые в пуле есть хоть один подходящий человек (релевантность 2–3), у проверок соответствия ТЗ — позиции, люди или
пары «человек — навык». Отчёт добавляет парные бутстреп-интервалы разностей (95 %, 2000 повторов по потребностям),
разрезы и по каждой потребности — первые десять каждого варианта с релевантностью.

## Разметка независима от продукта

Сначала генератор решает, кто человек: роль, стек, грейд, стаж, карьера с датами, строки достижений с навыками, раздел
навыков, языки, образование, строки ответственности. Документ только показывает этот профиль; разметка читается из
профиля (`src/fsp_eval/gold.py`), а не из ответа системы.

- Написания навыков (`src/fsp_eval/lexicon.py`) собраны для стенда вручную — так пишут в резюме, — а не взяты из
  синонимов таксономии. Оба списка описывают одну практику, поэтому многие написания совпадают с алиасами: прогон меряет
  долю (`skills.lexicon_overlap`) и отдельно — срез незнакомых таксономии написаний (`.unfamiliar`).
- Грейд задаёт рубрика стенда (`GRADE_MONTHS`: месяцы опыта в роли для каждого грейда; ведущий ещё и руководит людьми),
  а не правила категоризации продукта.
- Отрицания («Планирую изучить Rust») в разметку навыков не входят; опечатки — входят с исходным ключом.
- Недостаточные резюме заданы явно: `no_dates` — опыт без дат, `skills_only` — студент с двумя общими навыками.
- Люди, организации и учебные заведения вымышлены; контакты — `example.com` и номера `+7 900 000-…`.

## Данные ФСП

Слой `datasets/fsp-achievements-v3` лежит поверх выборки резюме (`base_dataset`) и решает для каждого профиля, выступает
ли человек в спортивном программировании и что о нём знает федерация: результаты с нормами, присвоенные разряды, сборная.
Запись идёт в формате источника — одна страница `fsp-achievements/v1`, — мост читает её схемой адаптера продукта, а факты
и утверждения строит так же, как синхронизация ФСП. Запись следует за человеком (`src/fsp_eval/fsp.py`).

Разметка читается из записи рубрикой стенда: уровень дисциплины — наивысший по опубликованной шкале (МС и выше или
основной состав сборной — L5, КМС или резерв — L4, I разряд — L3, II–III — L2, юношеский разряд или любой официальный
результат — L1). Прогон считает доказательства людей с записью командой моста `evidence` — снимок из резюме плюс
достижения — и сравнивает уровни. Вклад ФСП в подборку меряет вариант `shortlist.ndcg_at_10.without_fsp`.

## Мир стенда (генератор 3)

Слой `datasets/synthetic-matching-v3` (`src/fsp_eval/matching.py`) лежит поверх выборки резюме и слоя ФСП и до любого
ранжирования решает по своей рубрике, не глядя на продукт, кто человек, чего он хочет, какие тесты сдаёт и какие
потребности пишут работодатели. Все параметры заданы в генераторе и вместе с ним зафиксированы до прогона; изменился
генератор — новый id слоя.

- **Какие навыки у человека есть на самом деле.** Использованный в работе (строка достижения, должность) — есть; только
  перечисленный в разделе навыков — с вероятностью 0,7; навык своего стека, не написанный нигде, — 0,15; «планирую
  изучить» — нет. Алгоритмы — у человека с официальным алгоритмическим результатом ФСП уровня L2 и выше, 0,5 — на L1,
  0,1 — без записи: единственное место, где слой ФСП входит в истину. Навыки повседневной работы роли, которые её резюме
  редко называют (SQL и REST у бэкенд-разработчика на Django, CSS через Sass у фронтенда на Vue, ручное тестирование у
  автоматизатора), есть с вероятностью из таблицы `IMPLICIT_REAL` — только вне собственного стека человека.
- **Завышенные резюме** — ось с уровнями, зафиксированными до прогона: `honest` 0,7, `skills` 0,15 — 0,4 заявленных
  навыков, кроме языка стека, на деле нет, `skills_and_grade` 0,15 — то же, и настоящий грейд на один ниже того, что
  показывает резюме. Студент без опыта — стажёр без роли.
- **Чего человек хочет** (ответы опроса, `candidates.preferences`): форматы работы, регион города резюме, готовность к
  переезду, ожидание по зарплате от рынка грейда, который человек себе приписывает.
- **Тест на грейд.** 0,8 людей роли с тестируемой специализацией (бэкенд и фулстек — Backend, фронтенд — Frontend,
  тестировщики — QA, data scientist и ML-инженер — Data Science / ML) сдают тест своей специализации на грейд, который
  показывает их резюме (ведущий — на senior: Lead в каталоге нет); 0,7 неподтвердивших пересдают на грейд ниже. Исход
  решается, когда известен каталог продукта (команда моста `info`), моделью честного теста: определяющий блок проходит
  только тот, у кого на деле есть каждый навык блока, который мир моделирует (блок без таких навыков — тот, у кого есть
  половина своего стека), и никогда — человек, проверяемый выше своего настоящего грейда; баллы блока тянутся из полосы
  «владеет» (0,65–1,0 баллов блока) или «не владеет» (0,3–0,59), принудительного подъёма до порога нет. Практика сдана с
  вероятностью 0,85 у того, кто владеет одним из её языков: язык — язык стека человека, если практика его предлагает,
  иначе первый предложенный, которым он владеет; без такого языка практика не сдана. Практика QA прогоняет кейсы в
  языке обвязки, и знать его человеку не нужно. Подтверждение = все определяющие блоки не ниже порога и практика сдана.
  Поэтому честное подтверждение никогда не утверждает навык, которого у человека по миру нет.
- **Сценарий ложных подтверждений** — отдельный и явный: 0,3 людей без честного подтверждения подтверждены первой
  попыткой всё равно. Их ранжирует свой вариант (`false_confirmations`); в основную меру они не входят.
- **Потребности** пишутся так, как пишет работодатель: заголовок с уровнем и ролью («Middle/Senior …», «Стажёр …»),
  обязательные навыки (язык стека и ещё два, у части инженерных — алгоритмы), два желательных, формат работы с городом,
  вилка «на руки». Стратификация: по ролям (`NEEDS_PER_ROLE`: 54 потребности ролей с выпущенным тестом, 14 — ролей без
  него: аналитики, дата-инженеры, DevOps, мобильная разработка, системные аналитики), нижний грейд диапазона обходит все
  грейды от стажёра до ведущего; диапазон из двух грейдов — 0,7; формат: удалённо 0,6, гибрид 0,2, офис 0,2; вилка ниже
  рынка — 0,2.

## Методика v3

Зафиксирована 2026-10-05 до первого прогона по ней (контракт — `docs/contracts.md`, 11.2). Причина новой версии —
диагностический прогон по методике v2 2026-10-05: одна nDCG смешивала качество выбора подходящих с полнотой выдачи
частично подходящих, рубрика давала положительный выигрыш людям, которые работодателю не нужны (другая роль, грейд вне
диапазона), а базовый поиск получал готовый эталонный список требований. v3 разделяет три вопроса и меряет каждый своей
проверкой (`src/fsp_eval/selection.py`):

**(а) Соответствие ТЗ** (`shortlist.tz.*`, пороги — ровно ноль нарушений):

| Ключ                                    | Что это                                                                                                                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `shortlist.tz.uncategorized_positions`  | позиции категорийной выдачи у людей без подтверждённой по миру категории                                                                                                                         |
| `shortlist.tz.category_mismatch`        | люди, чьи категории в продукте не те, что дают их решения тестов (наивысший подтверждённый грейд)                                                                                                |
| `shortlist.tz.outside_need_categories`  | доля позиций первой десятки вне категорий, которые допускает потребность: специализация её роли и грейды её диапазона (Lead — Senior каталога); роль без выпущенного теста не допускает ни одной |
| `shortlist.tz.confirmation_consistency` | доля пар «человек — подтверждённый навык», где навык у человека по миру есть (навыки, которые мир моделирует)                                                                                    |

**(б) Подбор целиком** (`shortlist.*`). Пул — все люди части выборки с честным подтверждением, а не те, кого выбрал
продукт: пропуски категорий в оценке остаются. Релевантность — рубрика v3 потребности так, как её заявил работодатель:

- **0 — работодателю не нужен**: другая роль; настоящий грейд вне диапазона; формат или место, которых человек не примет
  (формат не из его; офис или гибрид не в его регионе и без переезда); ожидание выше верхней границы вилки; не хватает
  двух обязательных навыков и больше;
- **1** — не хватает одного обязательного, остальное подходит;
- **2** — все обязательные; **3** — все обязательные и хотя бы один желательный.

Подходящий — релевантность 2–3. Потребность без подходящих в пуле не оценивается, их доля — отдельно
(`shortlist.needs_without_suitable`, «честно пусто»), с разбивкой: роль без выпущенного теста или нет, пуста ли подборка.

| Ключ                                                                  | Что это                                                                                              | Базовый вариант               |
| --------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- | ----------------------------- |
| `shortlist.ndcg_at_10`                                                | nDCG@10 подборки (выигрыш `2^rel − 1`, идеальный порядок — по всему пулу)                            | поиск по тому же тексту       |
| `shortlist.precision_at_10`                                           | доля подходящих среди десяти позиций, знаменатель 10                                                 | поиск по тому же тексту       |
| `shortlist.recall_at_10`                                              | доля подходящих людей пула в первой десятке                                                          | поиск по тому же тексту       |
| `shortlist.mrr`                                                       | 1 / позиция первого подходящего во всём порядке, 0 — если его нет                                    | поиск по тому же тексту       |
| `….keywords_same_text`, `…_same_requirements`, `…_manual_query`       | то же для каждого базового варианта                                                                  | —                             |
| `shortlist.ndcg_at_10.lift_over_keywords_same_text`                   | нижняя граница 95 % интервала разности «продукт минус поиск по тому же тексту», порог — не ниже нуля | —                             |
| `shortlist.ndcg_at_10.random`                                         | ожидаемая nDCG@10 случайного порядка пула                                                            | —                             |
| `shortlist.ndcg_at_10.without_fsp`, `.without_semantic`               | подборка без ФСП; без смысловой близости (только с `--semantic`)                                     | подборка целиком              |
| `shortlist.ndcg_at_10.ceiling_admitted`                               | nDCG@10 лучшего порядка тех, кого допустили категории подборки: потолок сортировки внутри них        | подборка целиком              |
| `shortlist.precision_at_10.ceiling`, `shortlist.recall_at_10.ceiling` | потолок пула: `min(10, подходящих) / 10` и `min(10, подходящих) / подходящих`                        | —                             |
| `shortlist.recall_at_10.admitted`                                     | доля подходящих людей пула внутри категорий подборки: что теряет выбор категорий                     | —                             |
| `shortlist.needs_without_suitable`                                    | доля потребностей без подходящих в пуле                                                              | —                             |
| `shortlist.inflated_share_top10`                                      | доля людей с завышенным резюме в первой десятке подборки                                             | та же доля у поиска по тексту |
| `shortlist.without_fsp_share_top10`                                   | доля людей без результатов ФСП в первой десятке подборки                                             | их доля во всей подборке      |
| `shortlist.false_confirmed.ndcg_at_10`, `.share_top10`                | сценарий ложных подтверждений: nDCG@10 на пуле с ложно подтверждёнными и их доля в первой десятке    | поиск по тому же тексту       |

**(в) Сортировка** (`shortlist.sorting.*`): продукт и базовый вариант сортируют один и тот же набор, определённый до
прогона, — людей пула с категорией, которую допускает потребность. Продукт ранжирует его своим ранжированием подборки
(вариант моста `given`), базовый — поиск по тем же требованиям; nDCG@10, Precision@10 и MRR с идеалом по этому набору,
нижняя граница интервала разности nDCG — `shortlist.sorting.ndcg_at_10.lift_over_keywords_same_requirements`.

**Базовые варианты** названы по тому, что им дано, и работают на том же пуле:

- `keywords_same_text` — **автоматизация: тот же исходный текст**: BM25 текста потребности по текстам резюме (k1 1,2,
  b 0,75); сравнение с ним отвечает, лучше ли продукт поиска, которому дали то же, что и продукту;
- `keywords_same_requirements` — **сортировка при одинаковых требованиях**: названия навыков, которые продукт прочитал
  из потребности (обязательные — вес 2, желательные — 1), ищутся целыми словами в текстах резюме; ошибки разбора
  потребности у обоих одни и те же, разница — только порядок;
- `keywords_manual_query` — ручной запрос рекрутёра: названия навыков, которые печатает сама потребность, тем же поиском
  (так считался единственный базовый вариант v1/v2);
- `random` — случайный порядок пула.

**Разрезы** (раздел `slices` отчёта, все четыре системы, все четыре меры): роль, специализация, нижний грейд диапазона
(Frontend и Intern в выборке есть), диапазон с Lead и без, формат, регион (офис или гибрид в городе — или удалённо),
вилка (рынок или ниже рынка), алгоритмическая потребность (относящийся ФСП) или нет.

**Пул как в продукте** (contracts 11.1): категорийная выдача продукта по ТЗ формируется по категориям из теста, поэтому
человек без подтверждённого теста в пул не входит и пропуском подборки не считается. Он — предмет отдельного эксперимента
`resume_only` режима оценки жюри, а не качества продукта.

Мост ранжирует фактическим путём подборки: команда `rank` создаёт временную базу рядом с базой приложения
(`eval_rank_<hex>` на том же сервере; пользователю базы из `.env` нужно право `CREATEDB`), мигрирует её миграциями
checkout, публикует таксономию checkout, заводит каждого человека кандидатом — с достижениями ФСП и без, а человека
сценария ложных подтверждений ещё и с его решениями — строками, которые пишет `resume.extract`, фактами и утверждениями
ФСП, как синхронизация, ответами опроса и решениями тестов через единственного владельца категорий
(`applyGradeDecisions`) — с баллами блоков и заданием практики на её языке; считает доказательства обработчиком
`evidence.compute`. Каждая потребность читается правилами продукта (`parseNeedText` без модели), берёт категории, которые
подборка берёт по умолчанию, и кандидатов с действующей категорией из них, и ранжирует их `rankForNeed`. База удаляется в
конце команды при любом исходе. Реранкер ранжированием подборки не используется.

С `--semantic` каталог получает векторы так же, как стенд: мост регистрирует пространство `EMBED_SPACE_ID` и выполняет
задание `embedding.reindex` продукта с настроенным эмбеддером (`EMBED_*`, сервис `embedder` из `make infra`), и смысловая
близость кандидата к тексту потребности упорядочивает почти равных в подборке. Векторы продукт строит только для
кандидатов с действующим согласием на обработку, поэтому в таком каталоге каждый кандидат — совершеннолетний, давший
согласие по документу, который мост публикует во временной базе. Без эмбеддера `--semantic` — ошибка прогона, а не
ранжирование без семантики; близость, посчитанная лишь для части потребностей, тоже.

## Выборка и разбиение

Манифест `datasets/<id>/manifest.json` фиксирует сид, размер, дату отсчёта (`as_of`), долю holdout и хеш всех профилей с
разметкой. Разбиение — по исходным профилям: профиль целиком в dev или в holdout (по хешу сида и id). Семейство шаблонов
принадлежит dev, holdout или обоим:

| Семейство       | Формат                                         | Язык | Даты                                 | Выборка       |
| --------------- | ---------------------------------------------- | ---- | ------------------------------------ | ------------- |
| `pdf_classic`   | PDF, одна колонка                              | ru   | «Март 2021 — настоящее время»        | dev           |
| `docx_headings` | DOCX, заголовки-стили, должность до периода    | ru   | «03.2021 – н. в.»                    | dev           |
| `pdf_sidebar`   | PDF, боковая колонка с навыками и языками      | ru   | «2019 — 2021» (только годы)          | dev           |
| `docx_table`    | DOCX, опыт таблицей                            | en   | «Jan 2020 – Present»                 | dev и holdout |
| `pdf_hh`        | PDF в духе выгрузки hh.ru: период и стаж слева | ru   | «Сентябрь 2019 — по настоящее время» | holdout       |

`pdf_hh` на dev не встречается никогда; табличная вёрстка DOCX есть и там, и там: её проблемы ищутся и чинятся на dev, а
меряются на профилях holdout. Мера честна, пока на holdout не смотрели при правках, — сколько раз смотрели, показывает
журнал (раздел ниже).

Текущие версии: выборка `synthetic-resumes-v3` (2000 профилей, генератор документов 2, holdout — половина: 1025 на dev,
975 на holdout, чтобы отложенная часть дала столько же оцениваемых потребностей, сколько dev), слой `fsp-achievements-v3`,
слой `synthetic-matching-v3` (генератор 3, по 68 потребностей на dev и holdout). Holdout v3 новый и по исходным профилям,
и по потребностям: ни профиль, ни потребность не бывают в обеих частях, и на его числа никто не смотрел. Выборка v2 и её
слой ФСП остаются ради воспроизведения прогонов разбора R и M ([`REPORT.md`](REPORT.md)), её holdout просмотрен; слои
соответствия v1 и v2 выведены вместе со своими генераторами; выборка v1 выведена; записанные на них прогоны остаются в
`eval_runs` со своим id.

Документы в репозиторий не кладутся: генерация детерминирована (сид, фиксированные даты в метаданных файлов, закреплённые
версии библиотек в `uv.lock`), документы рендерятся при каждом прогоне в `out/`, а проверка хеша разметки отказывает
генератору, который её больше не воспроизводит. Изменился генератор — новый id выборки или слоя и новый манифест:
`python -m fsp_eval manifest …`, `fsp-manifest …`, `matching-manifest --id … --seed … --dataset … --fsp-layer …`.

## Журнал holdout

Каждый прогон на holdout показывает его числа тому, кто запускает; после этого настройка продукта уже не независима от
них. Поэтому обращения к holdout считаются: `reports/holdout/journal.json` перечисляет их — набор, режим, ревизия, дата,
кто, зачем, файл отчёта и что он показал. Стенд не запускает прогон на holdout, пока в журнале нет его записи: тот же
набор и режим, ревизия, которую сообщает сборка моста (не короче 12 знаков), сегодняшняя дата (UTC), непустые «кто» и
«зачем». Ревизия — коммит и только он: мост, собранный из дерева с незакоммиченными правками (изменённые, добавленные
в индекс или неотслеживаемые файлы; игнорируемые — `out/`, `.env`, сборки — не в счёт), сообщает коммит с суффиксом
`-dirty` (`src/eval/bundle.config.ts`), и на holdout такой прогон не пускается при любой записи в журнале. `APP_COMMIT`
из окружения сборка моста берёт, только если дерево чистое или значение само помечено `-dirty`. Прогон на dev идёт и с
такой сборкой; ревизия пишется в отчёт и в `eval_runs` как есть. Порядок:

1. внести запись (`report` и `seen` — `null`) и прогнать `--split holdout`; сводка прогона печатает, каким по счёту
   обращением к набору он стал, отчёт хранит его в `holdout_access`;
2. положить `summary.json` в `reports/holdout/`, вписать в запись файл и главные числа, закоммитить вместе.

`--split` обязателен: голый `run` не выбирает holdout сам. **Holdout открывается один раз**: одна ревизия и по одному
прогону каждого режима на ней. Вторую запись того же набора в том же режиме, запись другой ревизии и любой прогон на
наборе, который журнал называет в `status` (просмотрен, выведен), стенд отклоняет до прогона: их числа уже не были бы
независимой оценкой, следующая независимая мера — новая выборка.

## Пороги

`thresholds.json` — планка, зафиксированная заранее (дата и основание — в файле). У подбора пороги методики v3: в проверке
соответствия ТЗ — ноль нарушений по каждому из четырёх ключей `shortlist.tz.*`, в подборе целиком — нижняя граница
интервала разности nDCG@10 с поиском по тому же тексту не ниже нуля: продукт, который хуже этого поиска на тех же входах,
не проходит. Абсолютного порога nDCG нет: число зависит от пула и рубрики, а не только от продукта. Прогон записывает пороги
вместе с метриками; порог метрики, которую прогон не считает, — ошибка прогона. Метрика вне порога или не посчитанная при
заданном пороге — провал: панель показывает её как «порог не пройден» или «порог задан, не посчитано», а `run` после
записи отчёта (и строки, если просили) завершается с кодом 1 и перечисляет провалы. Пороги меняются отдельной правкой и
только до первого прогона на новом holdout.

## Запуск

Нужны инфраструктура (`make infra`: PostgreSQL, хранилище, `docparse`, эмбеддер), мигрированная база (`pnpm db:migrate`)
и `.env`.
Стенд работает в своём образе (Python 3.13, зависимости из `uv.lock`, шрифт DejaVu, Node той же версии, что у приложения)
с сетью хоста: мост ходит в `docparse`, базу, хранилище и модели по адресам из `.env`.

```sh
pnpm eval:build                                                   # сборка моста .eval-build/main.js
pnpm eval:run --split dev --mode rules_only --semantic            # прогон, отчёт в tools/eval/out/runs/
pnpm eval:run --split dev --mode rules_only --semantic --record admin@…  # и строка eval_runs с файлом отчёта
pnpm eval:run --split holdout --mode rules_only --semantic        # только с записью в журнале holdout
pnpm check:eval                                                   # ruff и pytest в тестовом образе, без сети
```

Режим оценки жюри — раздел ниже.

Прямой вызов образа — `python -m fsp_eval run --repo <checkout> --out <каталог> --split dev|holdout
[--mode rules_only|model] [--semantic] [--record <почта администратора>] [--fsp-layer <id>|none] [--matching <id>|none]
[--env-file <файл>] [--concurrency N]`; `render --split …` пишет документы выборки для просмотра.

Режим `model` вызывает модель через адаптер приложения (`LLM_*` в `.env`); документ, по которому модель не ответила,
продукт читает правилами, и прогон это пишет: `processing_mode` — `model`, `rules_only` или `partial`, сколько
документов прочитано каждым путём — `documents_by_mode` отчёта (и первая строка сводки), у документа — `model_failure`. Эмбеддер —
`EMBED_*` (для моста на хосте — `http://127.0.0.1:57820`, `bge-m3`, пространство из `docs/development.md`, «Эмбеддер»);
векторы каталога dev (≈ 2100 кандидатов) считаются на четырёх потоках CPU несколько минут. Concurrency прогона в режиме
`model` — 8 (не выше `LLM_MAX_CONCURRENCY`). Модели стенда на машине с GPU — `docs/models.md`.

Каталог прогона `out/runs/<время>-<выборка>-<split>-<режим>/`:

- `report.json` — строка `eval_runs`, провалы порогов, время извлечения, раздел подбора (интервалы, разрезы, нарушения ТЗ
  поимённо, по каждой потребности — первые десять каждой системы) и по каждому документу — семейство, хеш файла, итог разбора, разметка, что извлёк продукт, основная
  категория, не прошедшие проверку цитаты, для человека с записью ФСП — её разметка и категория с ней;
- `summary.json` — то же без документов и разбора по потребностям: его кладут в `reports/` рядом с кодом;
- `recorded.json` — с `--record`: id строки `eval_runs` и файла отчёта.

С `--record` мост кладёт `report.json` в хранилище файлом назначения `export`, владелец — администратор с указанной
почтой (активная роль `admin`), и связывает его со строкой (`report_file_id`): ссылка «Скачать отчёт» на панели отдаёт
этот файл после проверки прав. Объект пишется до строк; если вставка не удалась, он удаляется.

## Режим оценки жюри

Жюри проверяет подбор на своих потребностях и кандидатах (`docs/contracts.md`, 11.1): JSONL, одна строка на
потребность — её текст и кандидаты, у каждого резюме текстом или файлом, при желании решения тестов на грейд, страница
ФСП, ответы опроса и метка жюри 0–3. Образец — [`jury/example.jsonl`](jury/example.jsonl). Нужны база из `.env` (право
`CREATEDB`) и `docparse`; данных приложения прогон не трогает — ранжирует во временной базе моста и удаляет её.

```sh
pnpm eval:build && pnpm eval:image
docker run --rm --network host -u "$(id -u):$(id -g)" -v "$PWD:/repo:ro" -v "$PWD/tools/eval/out:/out" fsp-eval:local \
  jury-run --repo /repo --out /out --input /repo/tools/eval/jury/example.jsonl
docker run --rm --network none -u "$(id -u):$(id -g)" -v "$PWD:/repo:ro" -v "$PWD/tools/eval/out:/out" fsp-eval:local \
  jury-metrics --run /out/jury/<прогон> --labels /repo/<разметка>.jsonl
```

`jury-run` пишет в `out/jury/<время>/`:

- `results.json` — по каждой потребности, что продукт из неё прочитал, и три выдачи, каждая подписана: `as_product` —
  как в продукте, категория только из подтверждённого теста, кандидаты без неё — отдельным списком «категория не
  подтверждена»; `resume_only` — эксперимент без теста, категория из подсказки грейда по резюме, не подтверждена;
  `keywords_same_text` — поиск по тому же тексту потребности (BM25) среди тех же кандидатов. У первой десятки дорожек
  продукта — балл, разложение, основания с источником, пробелы и «проверить на интервью»;
- `judging.jsonl` — лист слепой разметки: объединение первых десяток всех трёх выдач по каждой потребности,
  перемешанное, без позиции, балла, системы и объяснений (`need_id`, `candidate_id`, `label: null`);
- `metrics.json` — если во входе есть метки.

`jury-metrics` читает размеченный лист (или любой JSONL с `need_id`, `candidate_id`, `label`) и считает для каждой
выдачи Precision@10 со знаменателем 10, nDCG@10, MRR первого подходящего (метка 2–3) и `judged@10` — долю размеченных в
первой десятке: неразмеченная карточка считается неподходящей, поэтому Precision@10 обеих систем честна, только если
размечено всё объединение. Разность «дорожка продукта минус поиск по тексту» — с парным бутстреп-интервалом по
потребностям. Потребность без подходящих по разметке не оценивается.

## Мост

`node --env-file=.env .eval-build/main.js` читает один JSON-запрос из stdin и пишет один JSON-ответ в stdout; ошибка —
код 1 и текст в stderr, прогон останавливается, частичные числа не пишутся.

| Команда     | Что делает                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `info`      | ревизия сборки и версии: таксономия (метка и хеш содержимого), правила расчёта доказательств, справочник категорий, правила разбора резюме, схема извлечения; определяющие блоки каждой категории с заданиями и навыками; языки практики каждой специализации с навыком, который каждый подтверждает                                                                                                                                                                                                                                                       |
| `extract`   | файлы → `docparse` (клиент приложения) → извлечение (модель или правила) → строки доказательств → снимок для расчёта доказательств; цитата каждого утверждения с блоками разбора, отказы по причинам, время шагов                                                                                                                                                                                                                                                                                                                                          |
| `normalize` | написания → ключи навыков                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| `evidence`  | снимки профилей, при необходимости с записью ФСП → уровни ФСП и выведенные навыки (категорию даёт только тест)                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `rank`      | кандидаты (строки резюме, запись ФСП, ответы опроса, решения тестов по порядку с блоками и языком практики) и потребности текстом → подборка продукта под каждую потребность во временной базе: разбор правилами, категории по умолчанию, допуск (`categories` — по категориям, `given` — заданный набор, `grade_hint` — по подсказке грейда, эксперимент без теста), ранжирование подборки, без категории — отдельно; категории каждого кандидата с подтверждёнными навыками; первые десять со вкладами, основаниями, пробелами и «проверить на интервью» |
| `record`    | строка `eval_runs` с файлом отчёта, проверенная схемами панели качества до вставки и прочитанная ими после                                                                                                                                                                                                                                                                                                                                                                                                                                                 |

Таксономия берётся из того же checkout — тех же файлов, из которых публикуются версии в базе; тест на грейд стенд не проводит, а записывает решения синтетического мира туда же, куда их пишет движок (попытки помечены `seeded`).
